# ADR-0011：`/api/v1/auth` 认证接口对接与令牌轮换

> **层级**：Tier 5 记录层 —— 正文不可修改（append-only）；变更须新开 ADR 并登记 `supersededBy`。
>
> **与 0009 的关系**：本文**承接并替代** `NMCPS-ADR-0009`（0009 已登记 `supersededBy: NMCPS-ADR-0011`）。0009 裁定的「Web httpOnly cookie / 桌面 Bearer / 令牌只由 BFF 签发 / `GATEWAY_RESOURCES` 不放认证端点」四条结论全部保留；被替代的是它未覆盖的接口级细节 —— 具体路由名、刷新语义、登出幂等性与错误信封字段。
>
> **接口事实来源**：`http://192.168.1.55:10000/swagger/specs/auth.json`（后端 OpenAPI）＋ 2026-10-31 对同一实例的实测（seed 账号 `admin` / `tenantadmin`）。

- **背景**：
  1. `NMCPS-ADR-0009` 的决策 1~3 只给出了会话模型的**形状**（两枚 cookie + 桌面 Bearer + 单一上游 `Authorization`），决策 7 只写了「登录 / 刷新 / 登出是显式 BFF 路由」而没有落任何一条路由；仓库里一直没有 `/api/auth/*` 与 `useAuth`，登录态实际不可用。
  2. 新后端的认证面已从 v1 的 `/iam/login` 收敛为 `/api/v1/auth/*` 六个端点，并引入了 v1 没有的**刷新令牌**与**会话 ID**：`login` 同时下发 `accessToken` / `refreshToken` / `sessionId`，`whoami` 也返回 `sessionId`。
  3. 实测发现三条会直接改变实现策略的行为差异：
     - **刷新即轮换**：`token/refresh` 成功后 `sessionId` 变更，**旧访问令牌立刻失效**（实测用旧 AT 调 `whoami` → 401）。任何「按 `expiresIn` 预刷新」或「刷新期间的并发请求继续带旧令牌」的策略都会把用户打成登出态。
     - **登出不幂等**：同一令牌二次 `logout` 返 401 `10201`，而登出是 UI 上的高频重复动作（多标签页、双击、令牌已过期），直接透传会把「成功登出」显示成报错。
     - **错误信封用 `msg`**：失败体是 `{code,msg,traceId}`，`message` 字段不存在，`code` 是**业务码**（如 20201、20205）而非 HTTP 状态；`NMCPS-ADR-0007` 落地的 `ApiResponse` 只看 `message`、并默认 `code` 等于 HTTP 状态，两者会把「账号或口令错误」全部泛化成 `401 unauthorized`。
  4. 另外两处细节：`login` 的 `data` 里**没有** `accountName` / `displayName` / `mfaEnabled`（只有 `accountCode`），单靠登录返回拼不出完整用户；`login` 缺字段或空 body 时后端返 **500 `10509`**（内部错误），属上游入参校验缺失，BFF 不应把它当真实故障透传。
  5. `/api/auth/*` 若登记进 `GATEWAY_RESOURCES`，就会与 `server/api/[...slug].ts` 的通用代理抢同一路径，且通用代理只做无状态透传，无法写 cookie。

- **决策**：
  1. **BFF 自有认证路由，不进白名单**：新增 `POST /api/auth/login`、`POST /api/auth/refresh`、`POST /api/auth/logout`、`GET /api/auth/session`、`POST /api/auth/mfa/bind`、`POST /api/auth/mfa/confirm`、`POST /api/auth/password`，放在 `server/api/auth/` 下，由 `server/utils/bff/auth.ts` 统一实现。`/api/auth/*` **不登记** `GATEWAY_RESOURCES`，避免与 `[...slug].ts` 冲突（沿用 0009 决策 2 的结论，此处明确到路由级）。
  2. **Web 双 cookie**：`nmcps_at`（访问令牌，`Path=/`）+ `nmcps_rt`（刷新令牌，`Path=/api/auth`），均 `HttpOnly` / `SameSite=Lax` / `Secure`（生产或 HTTPS 请求时）。`Max-Age` 取上游 `expiresIn`，刷新令牌取 `bff.refreshTtlMs`（默认 7 天，与上游 JWT exp 实测一致 —— 上游**不返回**刷新令牌 TTL，只能由配置兜底）。
  3. **桌面回传 tokens**：请求头 `x-nmcps-client: desktop` 时，`login` / `refresh` 的 `data.tokens` 返回 `{accessToken, refreshToken, expiresIn, sessionId}`，由 `useAuthTokens()` 写入 `tauri-plugin-store`；不写 cookie，也不让令牌出现在日志或 HTML 里。客户端标识只影响**返回形态**，不参与鉴权判定 —— 鉴权入口仍是「显式 `Authorization` 优先，其次 cookie」。
  4. **刷新只在 401 后单飞触发**：因背景 3 的轮换行为，前端**禁止**按 `expiresIn` 预刷新。`useApi` 命中 401 且有刷新令牌时，通过模块级共享 Promise **单飞**调用 `/api/auth/refresh`，成功后重放原请求一次；刷新失败即清会话并跳登录页。`/api/auth/*` 自身不参与该重试，避免递归。
  5. **登录响应补齐用户**：`login` 成功后 BFF 立即用新令牌调一次上游 `whoami` 取得权威用户（`displayName` / `mfaEnabled` 只有它有）；`whoami` 失败时降级为登录返回字段 + `displayName: null`（契约禁伪造真值，不拿 `accountName` 冒充 `displayName`）。
  6. **`/api/auth/session` 是前端唯一会话事实源**：Web 侧会话恢复不能读 cookie（`HttpOnly` 正是为了不可读），只能由 BFF 调 `whoami`。上游 401 → 返回 **HTTP 200** + `{authenticated:false, user:null}`，让 SPA 启动期的「未登录」成为正常分支而不是控制台报错；其它上游错误照常按信封上报。
  7. **登出对上游失败免疫**：先取令牌（cookie 或显式头）→ 调上游 `logout`（**空 body + `application/x-www-form-urlencoded`**，实测 JSON body 会被拒）→ 无论上游 200 / 401 / 超时，一律清 cookie 并返回 `{ok:true}`。上游非 401 的失败写入响应头 `x-nmcps-logout-upstream` 供排障，不回传业务失败。
  8. **CSRF 用同源判定**：cookie 模式的非安全动词（无显式 `Authorization` 的 POST）校验 `Origin`：与请求 `Host` 同源即放行，其次命中 `bff.allowedOrigins` 白名单，其余 403 `bff_csrf_rejected`。缺 `Origin` 直接拒绝（浏览器对非安全动词必带）。这样内网 IP 直连的开发场景无需逐台加白名单，跨站伪造仍被挡住。`login` 无 cookie 可借，不做 CSRF 校验。
  9. **入参先自校验**：`login` / `refresh` / `mfa/*` / `password` 用 zod 校验必填字段，缺失即 400 `bff_invalid_body`，把上游那记 500 `10509` 挡在 BFF 之外（上游 5xx 属实现缺陷，不该被当成契约）。
  10. **网关信封归一化补齐 `msg` 与业务码**：`server/utils/bff/proxy.ts` 的归一化在 `message` 缺失时取 `msg`；非 2xx 且上游 `code > 599` 时**保留业务码**（20201 等），否则维持 HTTP 语义（沿用 `NMCPS-ADR-0007` 的 `code === HTTP 状态` 约定，`>599` 与 HTTP 状态码天然不撞）。这样 `useApi` 的 `ApiError.code` 能区分「口令错」「会话失效」「未认证」。
  11. **`x-nmcps-client` 纳入 CORS 白名单**：`server/middleware/cors.ts` 的 `Access-Control-Allow-Headers` 增加该头，否则桌面端预检直接失败。

- **影响**：
  - 新增 `server/api/auth/{login,refresh,logout,password}.post.ts`、`server/api/auth/session.get.ts`、`server/api/auth/mfa/{bind,confirm}.post.ts`、`server/utils/bff/auth.ts`、`shared/types/auth.ts`。
  - 修改 `server/utils/bff/{proxy,config}.ts`（`msg` / 业务码归一化、`accessTtlMs` / `refreshTtlMs` / cookie 名配置）、`server/middleware/cors.ts`、`app/composables/useApi.ts`（401 单飞刷新 + 桌面注入令牌 + `x-nmcps-client`）。
  - 新增前端：`app/composables/useAuth.ts`、`app/composables/useAuthTokens.ts`、`app/middleware/auth.ts`、`app/pages/auth/sign-in.vue`；`AppHeader` 的用户菜单接上「登录 / 退出登录」，`i18n/locales/{cn,en}.json` 增补 `auth.*` 键。
  - `.env.example` 增加 `NUXT_BFF_ACCESS_TTL_MS`、`NUXT_BFF_REFRESH_TTL_MS`、`NUXT_BFF_ACCESS_COOKIE`、`NUXT_BFF_REFRESH_COOKIE` 说明。
  - `scripts/check-bff.mjs` 增加认证组断言：登录写双 cookie 且响应体不含令牌、`x-nmcps-client: desktop` 回传 tokens、重复登出仍 200、`/api/auth/session` 未登录返回 200 + `authenticated:false`、cookie 模式跨站 `Origin` 的 POST 被 403、上游 `msg` / 业务码归一化。

- **备选方案（未采用）**：
  - **前端直连 `/api/v1/auth`**：令牌必须存 JS 可读的位置（localStorage），XSS 即可窃取；也绕开了 BFF 的 CSRF 与入参校验。
  - **保持「按 `expiresIn` 预刷新」**：与实测轮换行为冲突 —— 预刷新会把仍在并发中的请求所用的旧访问令牌打成 401，反而制造抖动。
  - **登出透传上游 401**：用户看到「退出失败」，但本地 cookie 已清，界面与实际状态矛盾。
  - **把业务码压平成 HTTP 状态**：UI 无法区分「口令错」与「会话失效」，只能统一提示「请重新登录」，登录页的错误文案因此失效。
  - **用 `accountName` 充当 `displayName`**：违反 `NMCPS-CONTRACT-001` 的「未知即 `null`，禁伪造真值」。
  - **`/api/auth/*` 走 `GATEWAY_RESOURCES` 白名单**：通用代理无状态，无法写/清 cookie，且路径会与 `[...slug].ts` 抢匹配。

- **遗留**：
  - `password` 成功后上游是否立即作废当前会话，尚未实测（改口令会污染 seed 账号）；前端按「成功后重取 session，若 401 则跳登录页」处理，不预设结论。
  - `mustResetPassword` / `firstReset` 的完整流程（首次登录强制改密）未接 UI。
  - MFA 只落了 `mfa/bind` + `mfa/confirm` 的接口层，二维码渲染与恢复码未做。
  - 登录守卫已升级为全局（`NMCPS-ARCH-003` §7.6）：除落地页 `/` 与 `/auth/**` 外，未登录访问一律跳登录页并带回跳目标；页面内引导态只作兜底。
  - 多标签页登出同步（`BroadcastChannel`）未处理；Web 侧 cookie 由服务端统一清理，影响仅限桌面端。
