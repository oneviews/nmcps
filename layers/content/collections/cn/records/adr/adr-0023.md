# ADR-0023：实验网络台账与上游对账（显式接管）

> **层级**：Tier 5 记录层 —— 正文发布后只追加；后续修正用 `##` 追加节，不回改已发布结论。
> **与 ADR-0021 / ADR-0022 的关系**：ADR-0021 P2 把「台账资源清单」定为租户可见边界，ADR-0022 让写路径在成功后维护清单。两者都没有回答「清单之外发生了写」的情况：旧 Vite 前端退役前仍可直连 `:8000`、运维脚本也能直接调上游，此时台账不会收到任何通知。
> **现场（2026-11-17）**：某示例实例上游有 8 台主机 + 7 台交换机 + 14 条链路，台账却登记着前一天的 9 个节点 / 8 条链路，交集只剩 `h1 h2 h3 h8 s1 s2` 与 4 条链路；同时台账里的 `r1 c1 h9` 在上游已不存在。画布因此「显示不全」，与画布 / 坐标 / `kind` 归一无关。

---

## 一、裁决（速览）

| 编号 | 裁决 | 说明 |
| :--- | :--- | :--- |
| **D1** | 对账是**显式动作**，不做隐式自动收敛 | 读路径仍按清单过滤，不因为「上游多了一个节点」就自动扩大租户可见面。上游漂移只由人触发对账，避免越权数据借漂移混入。 |
| **D2** | 端点只在 BFF：`POST /api/mininet/networks/{id}/sync` | 它不转发任何上游写，只读上游再改台账，因此**不进** `MININET_ROUTES`、不占写端点白名单；静态路由优先于 `[...slug].ts`。 |
| **D3** | 双权限位 `lab:create` + `lab:delete` | 与 `import_json` / `full_reset` 同档：对账会把清单之外的节点纳入租户边界，等价于一次「接管」，缺任一权限一律 `403 lab_permission_denied`。 |
| **D4** | 逐字确认闸门 `{ confirm: "<network_id>" }` | 与 `full_reset` 同一实现：缺失、类型不对、值不符统一 `400 lab_confirm_required`，且**不触达上游**、不写台账。 |
| **D5** | 先审计、后执行；同一网络单写锁 | 审计 outbox 先落 `allowed`，读上游、写台账后再落 `succeeded` / `failed`；锁冲突 `409 lab_operation_in_progress`。审计写盘失败 `503 audit_unavailable`。 |
| **D6** | **读失败不落盘**，空上游写空清单 | 任一类节点或链路读取失败 → 原样回上游状态码与 message，台账保持原状（不能把「读不到」收敛成「没有」）。六类都成功且全空 → 写 `{ nodes: [], links: [] }`，这是事实而不是失败。 |
| **D7** | 清单按**整体重写**，不做增量并集 | 对账的语义是「以当前上游为准」，并集会永久留下已经消失的幽灵 id。出参同时给 `adopted` / `dropped` 两个差集，供页面说清「多接管了什么、清掉了什么」。 |
| **D8** | 入口只在 `lab:create` + `lab:delete` 时渲染 | 「文件」菜单新增一项，弹窗沿用逐字输入网络 id；没有双能力位时**不渲染**，不先渲染再等 403。 |
| **D9** | 边界不变 | 租户只来自签名会话；`upstream_id` 不参与鉴权；对账不修改 `engine` / `tenant_id` / `state`，也不创建、删除上游对象。 |

## 二、端点契约

```
POST /api/mininet/networks/{id}/sync
body: { "confirm": "<id>" }
```

| 阶段 | 结果 |
| :--- | :--- |
| 无会话 / 凭据不同源 | `401 bff_auth_required`；会话密钥缺失 `503 bff_auth_not_configured` |
| 缺 `lab:create` 或 `lab:delete` | `403 lab_permission_denied`，零上游请求 |
| 网络不在台账（含跨租户） | `404 lab_resource_not_found` |
| 通道未配置 / 租户无实例 | `503`（沿用 `mininet_not_configured` / `tenant_runtime_unavailable`） |
| 确认值不符 | `400 lab_confirm_required`，零上游请求 |
| 已有在途写 | `409 lab_operation_in_progress` |
| 上游任一读取失败 | 原状态码 + 上游 message；台账不变 |
| 成功 | `200`，`data: { network, nodes, links, adopted, dropped }` |

成功响应里的 `network` 是 `LabNetworkSummary`（不含 `upstream_id`）；`nodes` / `links` 是**对账后**的清单，`links` 键为无向归一形式 `a--b`。

## 三、读侧口径

- 节点来源：`GET /hosts`、`/switches`、`/routers`、`/nats`、`/controllers` 五类；字典取键，数组取 `id` / `name`。
- 链路来源：`GET /links` 的 `{ from, to }`（真实后端已用接口侧节点名反解）；同时兼容 `identity.source/target` 的旧形状。
- 控制器 ↔ 交换机是**关联**不是链路（ADR-0022 `import_json` 同口径）：上游 `/links` 不含关联边，因此不额外剪枝；若将来出现，按节点清单内的普通链路处理并在文档里补一条。
- 对账结果按 id 去重、按字典序排序，链路键按 `normalizedLabLinkKey()` 归一，保证同一事实两次对账得到同一份清单。

## 四、为什么不做「自动对账」

1. 自动对账会让一次直连写立刻扩大租户可见面，等于绕过 `lab:create` / `lab:delete` 的门禁。
2. 读路径分布在 hosts / switches / links / flows / stats 多个端点，隐式收敛需要每个读都触发写台账，代价与竞态都远大于收益。
3. 显式动作可以把「是谁、什么时候、把什么纳入了边界」写进审计，出问题时可回放。

## 五、范围之外（本轮不解决）

1. **控制器关联**：对账只修可见性。现场那张网的 7 台交换机 `controller` 全为 `null`，`pingall` 100% 丢包是上游没有控制器（`OVSSwitch` 默认 `failMode='secure'`），不是台账问题；新前端目前也没有 `associate_switch` 入口，需另立工作项。
2. **多实例 / 多副本**：锁仍是进程内实现（ADR-0022 D5 边界），对账端点继承同一限制。
3. **状态字段**：对账不校正 `state`；运行态仍由 `GET /start` 决定。

## 六、验收

- `check:lab-bff` 新增 ⑭ 组：双权限 403 / 缺确认 400 / 错误确认 400（三者零上游请求）、成功 200 且台账清单等于上游事实、幽灵 id 被清掉、上游 500 时台账不变、审计两条（`allowed` + `succeeded`）。
- `check:ui` 11.6b 组：有双能力位才渲染入口（缺 `lab:delete` 时禁用）、弹窗输入不匹配时确认按钮不可点、确认后只读上游六类集合且零写，并把台账清单整体重写成上游事实、画布保持不变。
- `pnpm check:doc-system` / `pnpm check:governance` / `pnpm typecheck` / `pnpm lint` / `pnpm check:i18n` 全绿。
