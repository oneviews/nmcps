# ADR-0010：BFF 上游就绪探针与 SSE 流式透传

> **层级**：Tier 5 记录层 —— 正文不可修改（append-only）；变更须新开 ADR 并登记 `supersededBy`。
>
> **编号说明**：跳过 `ADR-0009` —— `NMCPS-ADR-0008` 的遗留项已把 0009 预留给「会话 / 令牌模型」。

- **背景**：
  1. `NMCPS-ADR-0007` 的决策 6 只落了 `GET /health`：它只证明 BFF 进程可服务，**不依赖上游**；上游就绪探针被记入「遗留」，等部署规范确定。结果是上游不可达时 Pod 仍被判为健康，新流量继续被导进一个只会回 502/504 的实例。
  2. 同一 ADR 的遗留项点名：网关当前按 JSON 处理响应，v1 的 SSE/流式端点（`text/event-stream`）不能走统一 JSON 代理。`server/utils/bff/proxy.ts` 用 `response.text()` 读完整报文，SSE 会被攒到流结束才一次性回客户端 —— 心跳与实时推送因此彻底失效。
  3. `/health` 与 `/ready` 混用会让故障放大：上游短暂抖动时 k8s 若按同一探针重启 Pod，重启又打断已在处理中的请求，形成雪崩。
- **决策**：
  1. **`/ready` 与 `/health` 职责分离**：`/health` 继续做 liveness（进程存活），新增 `GET /ready` 做 readiness（上游可达）。`/ready` 命中且上游在 `readinessTimeoutMs` 内回 2xx → `200`；否则 `503`。
  2. **失败原因收敛为四个枚举**：`upstream_missing`（未配基址）→ `upstream_unreachable`（连接失败）→ `upstream_timeout`（探针超时）→ `upstream_unhealthy`（上游非 2xx）。判定顺序固定，便于告警按 `upstream.reason` 分桶。
  3. **探针不回显上游地址、不套信封**：响应体只含 `status` / `service` / `upstream.{configured,status,latencyMs,reason}` / `uptime` / `timestamp`，不出现上游 URL（内网拓扑不外泄）；形态是探针专用扁平对象而非 `ApiResponse` —— k8s probe 与负载均衡器只认状态码，信封包装没有收益。
  4. **探针只读状态码**：拿到响应头即 `response.body.cancel()` 释放连接，不把上游 body 读进内存；超时由独立的 `AbortController` 控制，不复用业务超时。
  5. **SSE 走流式透传**：`proxy.ts` 命中 `2xx` + `text/event-stream` 时直接返回 `Response`（h3 `sendWebResponse` → `sendStream`），逐块转发；同时下发 `cache-control: no-store` 与 `x-accel-buffering: no`，避免反向代理攒包；客户端断开时 `AbortController.abort()` 中止上游请求。
  6. **信封契约不变**：非 2xx 与非 SSE 的 2xx 仍走 `ApiResponse<T>`；业务超时只约束首包（收到响应头即清定时器），长连接不会在中途被打断。
  7. **可配置**：`runtimeConfig.bff.readinessPath`（默认 `/health`）与 `bff.readinessTimeoutMs`（默认 2000，下限 200），可由 `NUXT_BFF_READINESS_PATH` / `NUXT_BFF_READINESS_TIMEOUT_MS` 覆盖。
- **影响**：
  - 新增 `server/routes/ready.get.ts`、`server/utils/bff/readiness.ts`；`server/utils/bff/proxy.ts` 的返回类型放宽为 `ApiResponse<T> | Response`，`server/api/[...slug].ts` 同步放宽。
  - `scripts/check-bff.mjs` 的断言从 25 项增至 38 项：① 组 +2（未配上游的 `/ready`、探针禁止缓存）、⑤ 组 +6（成功态 3 项 + 三种失败原因）、⑥ 组 +5（content-type、增量到达、事件完整、不套信封、禁止缓存）。
  - 部署侧：`readinessProbe` 指向 `/ready`、`livenessProbe` 指向 `/health`；`/ready` 返回 503 期间不应把新流量导入该实例。
  - `.env.example` 增加两个就绪探针变量。
- **备选方案（未采用）**：
  - **复用 `/health` 做 readiness**：liveness 与 readiness 混用，上游抖动会触发重启，反而放大故障面。
  - **`/ready` 返回 `ApiResponse` 信封**：probe 与 LB 只看状态码，多一层解包徒增复杂度，还会让「探针不是业务接口」的边界变模糊。
  - **`/ready` 回显上游 URL 或上游错误原文**：任何能访问 `/ready` 的人都能拿到内网拓扑与上游细节。
  - **SSE 继续 `response.text()` 后手动分片**：解包与切片都在整包到达之后，实时性已丢失。
  - **用 `proxyRequest` 直接直通 SSE**：绕过 Header 白名单与 CORS 显式化，等于放弃网关收敛目标。
- **遗留**：
  - 探针只做单次探测，未聚合多副本或将结果接入负载均衡摘流逻辑。
  - SSE 未实现 `Last-Event-ID` 断线重连语义与显式背压策略（慢客户端目前由 TCP 背压兜住）。
  - 会话 / 令牌模型仍待 **ADR-0009**（`NMCPS-ADR-0008` 遗留项预留该编号）。
  - 仓库暂无 k8s 清单，探针配置尚未进入部署产物。
