# ADR-0024：无控制器的交换机默认 standalone（实验网连通性）

## 1. 背景（实测）

2026-11-17 现场：上游 8 主机 / 7 台 OVS 交换机 / 14 条链路，`POST /pingall` **100% 丢包**，`iperf` 无吞吐。台账与画布都是对的 —— 排在图上就是连不起来。

根因在数据面，与台账无关（台账清单缺席是 `NMCPS-ADR-0023`（`layers/content/collections/cn/records/adr/adr-0023.md`）的事）：

- Mininet 的 `OVSSwitch` 默认 `failMode='secure'`。secure 模式下**没有已连接的控制器**时，交换机没有流表、也没有 NORMAL 兜底动作，收到的帧全部丢弃。
- 新建交换机的请求体里 `controller` 恒为 `null`（`layers/scenario/shared/types/labNodes.ts` 的草稿映射），`POST /start` 于是走 `switch.start([])`，等价于「secure + 零控制器」，于是 `pingall` 必然 100% 丢包。
- 旧前端能通，是因为它默认关联控制器（Ryu / reference controller）后再起网；新页面目前还没有关联入口。

## 2. 裁决

fail mode 由**控制器关联**推导，不新增字段、不新增端点、不改权限：

- `switch_fail_mode(controller)`：有控制器 → `secure`；无控制器 → `standalone`。
- 三处统一应用：
  1. `add_switch_to_net()`：OVS 系四类（`OVSSwitch` / `OVSKernelSwitch` / `OVSBridge` / 默认）创建时都传 `failMode`。
  2. `POST /start` 起网前：按此刻的关联重设 `failMode`，因为交换机可能在创建后被关联、也可能停网期间改过。
  3. `POST /associate_switch`：关联成功并重启该交换机前设为 `secure`。
- `schema.py::Switch.format_switch()` 生成导出脚本时同样带上 `failMode`，保证「导出的脚本跑起来」与「在线网络」行为一致。

明确不做：

- **不自动拉起控制器进程**。那要 `ryu` / `pox` 之类外部依赖，装不上时会把「没有控制器」伪装成「控制器启动失败」，比现状更难排查。
- **不改 `POST /flows` 语义**。standalone 交换机上 OVS 会拒绝写流表，错误原样透出（400 + `ovs-ofctl` 原文）—— 这是可见事实，不吞、不改写成 200。

## 3. 后果

- 无控制器的实验网**开箱即通**：standalone 即传统自学习交换机，`pingall` 不再 100% 丢包。
- 关联了控制器的网络仍是 secure：OpenFlow 流表（`flow_rules.py`）继续生效，`simple_switch_13` 这类 L2 学习控制器能正常转发。
- 局限（写进文档而不是藏起来）：standalone 下交换机忽略 OpenFlow 规则，想「被编排 + 写流表」必须先关联控制器；多交换机环路在 standalone 下没有 STP，仍要靠控制器或拓扑规划。
- 权限、审计、租户边界完全不变：这是上游数据面的默认值，不经 BFF，也不扩大任何可见面。

## 4. 验收

- `pnpm lab:check` 新增三条静态断言：`switch_fail_mode()` 的映射、`add_switch_to_net()` 的四个 OVS 分支都带 `failMode`、`Switch.format_switch()` 的输出随 `controller` 变化。三者都不需要 root，也不创建 Mininet 网络。
- `pnpm check:lab-bff` / `pnpm check:ui` 用假上游，不覆盖真实数据面，保持绿即可（它们校验的是 BFF 与页面，不是 OVS 行为）。
- 真机验证（需 root + Mininet，手工执行）：2 主机 + 1 交换机 → `POST /start` → `GET /pingall` 应为 0% 丢包；再 `POST /associate_switch` 关联控制器 → `pingall` 仍通且 `POST /flows` 成功。
