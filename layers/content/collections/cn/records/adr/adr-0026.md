# ADR-0026：长时操作的出站预算与台账运行态对账

> **层级**：Tier 5 记录层 —— 正文发布后只追加；后续修正用 `##` 追加节，不回改已发布结论。
> **与 ADR-0022 的关系**：`NMCPS-ADR-0022`（`layers/content/collections/cn/records/adr/adr-0022.md`）W3 只回答了「运行控制要按能力位渲染、状态读 `GET /api/mininet/start`」，没有回答「一次 pingall 比出站预算还长时，浏览器、BFF、上游三者该各自等多久」，也没有回答「台账 `state` 与上游运行态漂移时谁纠正谁」。两处缺口在上线后合并成两个用户可见的故障，因此写成裁决。

## 1. 背景（现场实测）

2026-11-21 在真后端（`127.0.0.1:8000`，9 节点：1 控制器 / 1 路由器 / 7 主机）上复现两条故障：

- **「启动后 pingall / 停止失败」**：`POST /api/mininet/pingall` 直接对上游耗时 **42.6 秒**；而 BFF 的出站超时是 `mininet.timeoutMs`（默认 **15 秒**），于是 BFF 在第 15 秒 abort 并回 `504 mininet_timeout`，浏览器侧 `useApi` 的默认 20 秒也早已越过，页面上表现为一条没有正文的失败（`<no response> Failed to fetch`）。**上游此时仍在逐对 ping**。
- **「停网把后端打崩」**：在上一条的窗口里点「停止」，`stop_network()` 立刻 `_stop_mininet_with_timeout()`，把 `pingFull()` 正在遍历的节点接口拆掉，上游以
  `AttributeError: 'NoneType' object has no attribute 'IP'`（`mininet/node.py::IP`）中断 —— 复现命令与输出见 §4。
- **「导入的拓扑没启动就显示运行中」**：台账 `.data/lab-ledger.json` 里 `state: "running"`（seed 值），而上游 `GET /api/mininet/start` 回 `false`。页面按台账渲染「网络」读数，于是**没启动的网显示运行中**。这个字段此前只在 `start` / `stop` / `full_reset` 成功之后才写回（`markLabNetworkState()`），seed、进程重启、上游被外部 `mn -c` 清掉都不会触发写回。

## 2. 裁决

| 编号 | 裁决 | 说明 |
| :--- | :--- | :--- |
| **D1** | **长时端点用独立的出站预算** | `MININET_LONG_OPERATION_TEMPLATES`（`layers/scenario/shared/constants/mininetRoutes.ts`）登记 `POST /start` `/stop` `/reset` `/full_reset` `/import_json` `/pingall` `/iperf` 七条；命中的端点走 `config.longTimeoutMs`（默认 180000，`NUXT_MININET_LONG_TIMEOUT_MS` 覆盖，租户实例可带 `longTimeoutMs`），其余读端点仍是 `timeoutMs`（15 秒）。表格放在 shared 常量里而不是 server 工具里：BFF 与浏览器侧要**同一份**名单，不允许两处各写一份然后漂移。 |
| **D2** | **浏览器侧与 BFF 同口径** | 页面调这七条端点时显式传 `timeoutMs: LAB_LONG_OPERATION_TIMEOUT_MS`（与 D1 同值）。默认 20 秒继续服务普通读写：把全局默认调大等于让「上游挂了」的读操作也挂 3 分钟。`<no response>` 的成因正是客户端先于 BFF abort —— 客户端预算必须 ≥ BFF 预算，否则用户永远看不到 BFF 的 `504` / 上游原话。 |
| **D3** | **停网前先等测试收尾** | 上游 `stop_network()` / `full_reset_network()` 在拆节点之前 `await _await_idle_operations()`：`pingall_running` 或 `iperf_running` 为真就每 200ms 轮询一次，最长 180 秒；超时后**继续停网**并 `info()` 记录，不把运维卡死。`pingFull()` 不可中断（Mininet 没有取消接口），所以选择「等」而不是「杀」：在它遍历的中途重建拓扑是唯一会产生 `AttributeError` 的路径。 |
| **D4** | **台账 `state` 在读路径与上游对账** | `GET /api/lab/networks` 在出口前对每个有实例的租户读一次 `GET /api/mininet/start`：读到 `true` 把 `stopped` 改成 `running`，读到 `false` 把 `running` 改成 `stopped`（只动这两个值，`creating` / `error` 不猜）；读不到、非布尔、或租户没有实例时**保持原值**。改判走 `markLabNetworkState()`（仍在 `enqueueWrite` 串行链上），失败只记日志、不影响列表返回。这条把「两个状态不是同一个真源」的既有裁决补全：两个真源都必须各自正确，不能靠用户点「对账」才发现。 |
| **D5** | **本轮不把长操作改成异步任务（job + 轮询）** | 一次 pingall 几秒到一分钟，转成 job 会带来任务表、TTL、清理与前端轮询三套新机制，而 D1+D2 已经把「假失败」消掉。重估触发条件（任一满足则新开 ADR）：① 单次 pingall 稳定超过预算上限（180 秒）；② 需要中途查看进度 / 取消的操作（例如大拓扑 `iperf` 长跑）；③ 并发用户数上来后单实例长操作排队明显。 |

## 3. 影响面与验收

- **改动面**：`mininetConfig.ts`（新字段 + 环境变量）、`mininet.ts`（`proxyToMininet()` 按端点选预算）、`mininetRoutes.ts`（名单 + 纯函数）、页面（七条调用点传预算）、`services/mininet-api/mininet_gui_backend/api.py`（`_await_idle_operations()`）、`networks.get.ts` + 新增 `labStateReconcile.ts`。
- **机器断言**：`pnpm check:lab-bff` ⑮ 用「短预算 1.2 秒 / 长预算 3 秒 + 上游延迟 2 秒」证明读端点 504、长时端点 200；同日还把台账对账（读 `running` + 上游 `false` → 列表回 `stopped`，上游读取失败 → 原值）一并钉住。`pnpm lab:check` 断言 `stop_network` / `full_reset_network` 都 await 了空闲等待。`pnpm check:ui` 11.3 的台账 seed 仍是 `state: "running"` 而上游 `false`，期望值改为「已停止」—— 这条就是「没启动却显示运行中」的回归用例。
- **真机**：`pnpm check:lab-real` 的 pingall 用例在真后端上要跑满 40 秒以上，D1 之前它只能假失败；跳过（无 `CHECK_REAL_MININET`）仍不算通过。

## 4. 复现记录（2026-11-21）

```bash
curl -s -m 600 -X POST http://127.0.0.1:8000/api/mininet/stop      # 2.6s / 200，但 pingall 线程死于：

```
