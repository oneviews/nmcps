# ADR-0009：会话与令牌模型（web httpOnly cookie / 桌面 Bearer）

> **层级**：Tier 5 记录层 —— 正文不可修改（append-only）；变更须新开 ADR 并登记 `supersededBy`。

- **背景**：
  1. `NMCPS-ADR-0007` 的决策 7 明确「鉴权只做透传」，把登录 / 刷新 / 会话存储留给新 ADR；其遗留项写作「需 ADR-0008」，而 0008 被下载落地页占用，`NMCPS-ADR-0008` 又把该主题顺延为 **0009**。本 ADR 即补上这一条。
  2. v1 的鉴权组合不可复制：BFF 用 **httpOnly** cookie 写 `auth_token`，前端却用 `useCookie('auth_token')` 读取 —— httpOnly 对 JS 不可见，`isSignedIn` 只活在内存里，页面刷新即登出。v2 必须先定「令牌由谁写、谁能读」，否则同类缺陷会原地复现。
  3. v2 是两个宿主：浏览器 SPA（与 BFF 同源或经 `public.bffBase` 跨源）与 Tauri WebView（`tauri://localhost` / `http://tauri.localhost` 自定义协议）。cookie 在两个宿主里的可靠性与属性约束不同，单一载体必然在其中一端妥协。
  4. 现状（`server/utils/bff/proxy.ts` 的 `buildUpstreamHeaders`）已经写好落地形态：优先透传客户端 `Authorization`，缺失时读 `bff.tokenCookieName`（默认 `nmcps_at`）并拼成 `Bearer ${token}`。本 ADR 只需裁决「谁来写这个 cookie / 桌面用什么」，proxy 无需改结构。
- **决策**：
  1. **双模会话**：**web** 用 BFF 签发的 cookie 会话；**桌面**用 Bearer 令牌。不做「全站统一 Bearer」，也不做「桌面也用 cookie」。
  2. **web 双 cookie**：`nmcps_at`（访问令牌，短寿命，`Path=/`）与 `nmcps_rt`（刷新令牌，长寿命，`Path=/api/auth`，只发给刷新端点）。两者恒为 `HttpOnly`（JS 不可读，从根上消除 v1 的读写错配）、生产恒为 `Secure`、`SameSite=Lax`（同源 SPA 足够，且兼容桌面 WebView 未启用 https 的开发场景）、不设 `Domain`（避免子域串味）。
  3. **桌面 Bearer**：登录接口把 `access_token` / `refresh_token` 一并回给桌面客户端（web 登录响应**不含**令牌明文，只有 cookie），桌面用 `tauri-plugin-store` 落盘在应用数据目录，由 `useApi` 注入 `Authorization: Bearer`；刷新令牌轮换时同步覆写。
  4. **令牌只由 BFF 签发**：`/api/auth/login` / `/api/auth/refresh` / `/api/auth/logout` / `/api/auth/session` 是 Nitro 显式路由（`server/api/auth/*.ts`），**不**把 `auth` 加进 `GATEWAY_RESOURCES`。理由：cookie 属性（HttpOnly / Secure / SameSite / Path）必须由 BFF 决定，不能让上游或浏览器上下文参与；显式路由同时挡住 `/api/auth/**` 的任意路径透传。
  5. **出口统一**：两种模式最终都由 `proxy.ts` 转成上游 `Authorization: Bearer`（现状逻辑保留：header 优先、cookie 兜底）。上游只认 Bearer，不接触浏览器 cookie。
  6. **CSRF 只对 cookie 模式设防**：`SameSite=Lax` 之外，对使用 cookie 鉴权的非安全动词（POST / PUT / PATCH / DELETE）校验 `Origin` 是否在 `bff.allowedOrigins` 白名单内（复用 `server/middleware/cors.ts` 的判定），缺失或不在白名单 → `403 bff_csrf_rejected`。Bearer 模式天然免疫，不做额外校验。
  7. **不做服务端会话存储**：BFF 保持无状态（多副本、无 Redis）。吊销依赖短寿命访问令牌 + 刷新令牌轮换（由上游裁决），登出时清 cookie 并调用上游吊销端点。
  8. **配置面**：`bff.tokenCookieName`（默认 `nmcps_at`）从「只读」转为「BFF 写入」；新增 `bff.refreshCookieName`（默认 `nmcps_rt`）、`bff.accessTtlMs`、`bff.refreshTtlMs`，均可由 `NUXT_BFF_*` 覆盖。
- **影响**：
  - 预计新增 `server/api/auth/{login,refresh,logout,session}.ts` 与 `server/utils/bff/session.ts`（cookie 读写 + CSRF 校验），`shared/types/api.ts` 增加会话相关类型。
  - `app/composables/useApi.ts` 需要补两条路径：桌面注入 `Authorization`、401 时触发一次单例刷新后重放；web 侧继续 `credentials: "include"`（现状已如此）。
  - `app/composables/useAuth`（尚不存在）作为唯一登录态来源：web 通过 `GET /api/auth/session` 拿用户信息（**不读 token**），桌面读 store 里的令牌状态。
  - `scripts/check-bff.mjs` 需新增鉴权断言组（cookie 属性、CSRF 拒绝、Bearer 透传、401 → 刷新路径），断言数将从 38 继续上升。
  - `.env.example` 与 `nuxt.config.ts` 增加上述四个配置项。
- **备选方案（未采用）**：
  - **全站 Bearer + `localStorage`（连 web 一起）**：XSS 一行脚本即可导出长期令牌，且与 v1「刷新丢登录态」的教训同源，安全性最差。
  - **桌面复用 cookie**：自定义协议下 cookie jar 行为随平台（WebView2 / WKWebView / WebKitGTK）而异，`SameSite=None` 还要求 https，跨源请求是否带上 cookie 无法稳定保证。
  - **`nmcps_at` 存不透明 session id + BFF 会话表**：需要共享存储（Redis）与清理任务，当前副本数未定、没有 Redis，收益不足以抵消运维成本。
  - **把 `auth` 加进 `GATEWAY_RESOURCES` 让上游统管登录**：cookie 属性决策被推到上游，BFF 失去对 `HttpOnly` / `SameSite` 的控制，且放开了一整段路径的透传面。
  - **继续 v1 的「httpOnly 写 + `useCookie` 读」**：本 ADR 的背景 2 已证明其在刷新时必然失效。
- **遗留**：
  - 桌面令牌目前落 `tauri-plugin-store`（应用数据目录的明文 JSON），未接 OS 钥匙串；后续引入 `tauri-plugin-keyring` 或 Stronghold 需新 ADR。
  - 服务端吊销（主动「登出所有设备」、刷新令牌重放检测）依赖上游能力，BFF 侧尚无令牌黑名单。
  - `useApi` 的 401 单例刷新、`useAuth` 组合式、`/api/auth/*` 路由均**尚未落码** —— 本 ADR 只定模型，实现按「先文档、再落码」另起 PR。
  - 多租户与令牌的绑定（`x-tenant-id` 与令牌里的租户声明是否必须一致、切换租户是否重签）未定。
