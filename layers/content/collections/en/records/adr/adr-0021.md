# ADR-0021: Tenant isolation and access decisions for simulation networks

> **Layer**: Tier 5 record layer — the body is append-only after publication; later corrections are appended as new `##` sections, never by rewriting a published verdict.
> **Relation to ADR-0020**: ADR-0020 only solved "the browser must not reach Mininet directly" for a read-only channel and explicitly left multi-user isolation open. This ADR answers that open question and extends it to the simulator at `/api/sim/**`.
> **Relation to ADR-0009 / ADR-0018**: the client-forwarded `x-tenant-id` from ADR-0009 and the "identity cookie is only visible under `/api/auth`" model from ADR-0018 are tightened here: the tenant of a simulation resource **must** come from the BFF session and never from a request body, query parameter or `x-tenant-id`.
> **Status**: on 2026-11-15 the requester selected **one runtime instance per tenant** (option A). Cross-tenant runtime access by platform administrators is **denied by default**; if support access is ever needed, it requires a separate time-boxed support-session ADR and must not be opened here directly.

---

## 一、Verdicts at a glance

| # | Verdict | Detail |
| :--- | :--- | :--- |
| **D1** | Adopt **one runtime instance per tenant** (option A) | Each tenant gets its own Mininet instance / container / network namespace. Multiple tenants must never share one `app.net` process. The simulator is isolated per tenant by instance or namespace as well. |
| **D2** | Every simulation resource carries `tenant_id`, derived only from the BFF session | Request bodies, query parameters and `x-tenant-id` never decide ownership; a client-supplied tenant header is stripped before egress. |
| **D3** | Permission bits and role baselines are fixed | `lab:read` / `lab:create` / `lab:operate` / `lab:delete` / `lab:terminal` / `lab:sniffer`. Tenant users default to `lab:read`; tenant admins additionally get create / operate / delete; terminal and sniffing require explicit grants. |
| **D4** | Cross-tenant access is always **404**, never 403 | Do not reveal that another tenant's resource exists; unknown and unauthorised resources share one rejection. |
| **D5** | Platform administrators have **no** tenant runtime access by default | They may read platform metadata / quotas / audit only. Runtime access requires a separate, time-boxed, fully audited support session explicitly approved by the supported tenant's administrator. |
| **D6** | At most one running network per tenant per engine | A second create / start returns `409 lab_network_already_running`; never queue-then-overwrite. |
| **D7** | The BFF owns a resource ledger; upstream IDs are not a permission boundary | Each record carries `id`, `tenant_id`, `engine`, `upstream_id`, `state`, `created_by`, `created_at`; every `{sim_id}` / `{network_id}` / `{node_id}` / `{link_id}` is resolved through the ledger before the upstream is touched. |
| **D8** | Authentication must land before writes, and must fail closed | A signed BFF session plus IAM role resolution is required; missing secret, missing session and role-lookup failure return 401 / 403 / 503 respectively, never "globally visible". |
| **D9** | Every high-risk operation is audited | Create, start, stop, reset, delete, terminal open/close and sniffer start/stop record tenant, actor, network, action, result, `request_id` and client IP. |
| **D10** | Writes, terminal, sniffing and WebSockets stay closed until P1–P3 | No "render the button and wait for 405"; `/api/lab/channel` reports `writeEnabled: false` until permissions and isolation land. |

## 二、Why data-plane isolation is mandatory

Mininet's `app.net` is a **process-wide singleton**: one process holds one network at a time. UI filtering, a BFF ledger or checking a `sim_id` cannot stop tenant B's process from seeing tenant A's nodes, flow tables, captures and terminal.

Isolation in this ADR therefore means:

1. **Control-plane isolation**: the BFF routes a request only to the tenant's own instance; the routing table lives in the BFF and clients cannot name an address.
2. **Data-plane isolation**: each tenant instance has its own process, network namespace / container, bridge and veth namespace; packets between tenants never traverse one bridge.
3. **Storage isolation**: capture files, exported scripts and terminal logs live in tenant-scoped directories or volumes; object paths must not be enumerable across tenants.
4. **Resource isolation**: each tenant instance has CPU / memory / process / network quotas so one tenant cannot starve the others.

If a deployment can only provide a single instance, it must be named a **global lease** and marked "not isolated, demo only" in both UI and API. Option C (single-instance global lock) is rejected because it does not satisfy D1.

## 三、Resource model and the BFF ledger

### 3.1 Resource record

Minimum ledger shape (recommended contract; lands in `shared/types` during implementation):

```ts
type LabEngine = "simulator" | "mininet";

interface LabNetworkRecord {
  id: string;                 // BFF-owned ID; the only ID exposed outside
  tenant_id: string;          // from the signed session only
  engine: LabEngine;
  upstream_id: string;        // ID inside the upstream instance; not a credential
  state: "creating" | "stopped" | "running" | "error";
  created_by: string;         // subject ID
  created_at: string;
  updated_at: string;
}
```

### 3.2 Lookup order

Every request carrying a resource ID follows this order:

1. read `tenant_id` and `subject_id` from the signed session;
2. look up `(tenant_id, engine, id)` in the ledger;
3. no hit → `404 lab_resource_not_found` (do not distinguish "missing" from "someone else's");
4. check the permission bit;
5. only then append `upstream_id` to the tenant's own instance base URL.

**Never** treat an upstream `sim_id`, node ID or link ID as an authorisation credential; it is a routing parameter only after a ledger hit.

### 3.3 List filtering

When an upstream returns a global list, the BFF must filter it at the egress by the `tenant_id` in the ledger; records whose owner cannot be established are dropped and logged. The frontend never performs this filtering and never receives cross-tenant records as greyed-out placeholders.

## 四、Identity and tenant binding

### 4.1 Session source

The simulation channels do not accept an unsigned JSON cookie such as `nmcps_ui` as a tenant boundary. P1 must add a BFF-signed session cookie (recommended `nmcps_sess`, `HttpOnly`, `SameSite=Lax`, `Path=/`):

- payload contains at least `sub` (user ID), `tid` (tenant ID, `null` for platform users), `iat` and `exp`;
- HMAC-SHA256 over the payload with `runtimeConfig.bff.sessionSecret` (env `NUXT_BFF_SESSION_SECRET`, at least 32 bytes);
- invalid signature, expiry or missing `tid` is treated as unauthenticated;
- when the secret is absent, `/api/lab/**` and `/api/sim/**` return `503 bff_auth_not_configured`; **never** fall back to an unsigned cookie.

The access token still comes from `nmcps_at` / `Authorization` and is used for IAM and upstream calls. The session cookie only answers "which user and tenant logged in on this browser"; it does not replace the access token.

### 4.2 Role resolution

Roles are never read from the client, and a role code alone is not enough. P1 resolves them from IAM:

1. `GET /iam/subject-roles?subject_id=<session sub>` lists the subject's role relations;
2. for each `role_id`, `GET /iam/roles/{id}` returns `code` and `tenant_id`;
3. a tenant role must satisfy **`role.tenant_id === session tid`**, otherwise it is discarded; this is the BFF-side backstop for `UP-RBAC-09` (a tenant admin can bind a user to `platform_admin`);
4. a platform role (`platform_admin`, `tenant_id: null`) is recognised only when `session tid === null`; platform users get no runtime permissions;
5. a role lookup failure or timeout returns `503 bff_role_resolution_failed`; it must not degrade to "no roles but readable".

Role results may be cached for ≤ 60 seconds keyed by `subject_id + access-token hash`; logout, password change and role-change events invalidate the cache. The cache lives in one BFF process only and is never a shared mutable ledger.

### 4.3 Permission baseline

| Role code | Applies to | Default permissions |
| :--- | :--- | :--- |
| `tenant_user` (default semantics, binding optional) | Tenant user | `lab:read` |
| `tenant_admin` | Tenant administrator (`role.tenant_id` matches) | `lab:read` + `lab:create` + `lab:operate` + `lab:delete` |
| `lab_terminal` | Explicit grant | `lab:terminal` (implies nothing beyond `lab:read`) |
| `lab_sniffer` | Explicit grant | `lab:sniffer` (does not imply `lab:operate`) |
| `platform_admin` | Platform administrator (`tenant_id: null`) | No runtime permission; platform metadata / quotas / audit only |

Permission meanings:

- `lab:read`: view the tenant's networks, topology, nodes, links, runtime state and statistics;
- `lab:create`: create a network for the tenant (subject to D6);
- `lab:operate`: start, stop, reset, pingall, modify the tenant's network;
- `lab:delete`: delete the tenant's network and associated artefacts;
- `lab:terminal`: open a terminal on a tenant node;
- `lab:sniffer`: start/stop captures and read/export them.

`lab:terminal` and `lab:sniffer` are **never** implied by `lab:read` or `lab:operate`; they need an explicit role or permission claim.

## 五、Isolated instances and routing

### 5.1 Instance registry

The BFF owns a **read-only** tenant-to-instance registry (from deployment configuration or service discovery) containing at least:

```ts
interface LabInstance {
  tenant_id: string;
  engine: LabEngine;
  base_url: string;        // server-only; never sent to a browser
  capacity: number;        // networks allowed for this tenant; currently 1
  healthy: boolean;
}
```

Clients only carry BFF resource IDs; `base_url` never appears in a response, a frontend config or an unredacted log.

### 5.2 Routing rules

- reads: select the instance by session `tenant_id`; missing or unhealthy → `503 tenant_runtime_unavailable`;
- writes: check `lab:create` / `lab:operate` / `lab:delete` before selecting an instance;
- upstream 404 stays 404; it is never remapped to 403;
- upstream 401/403 is a BFF-to-instance configuration error → `502 upstream_auth_misconfigured` plus an alert; it must never refresh the user session;
- a request for one tenant is never forwarded to another tenant's instance.

### 5.3 One network per tenant

At most one `running` network per tenant per `engine`:

- creating a second → `409 lab_network_already_running`;
- starting a second → the same;
- after stopping, a new network may be created; the old one stays `stopped` until deleted or quota-reclaimed;
- concurrent creates are serialised by a tenant-level mutex in the ledger (database unique constraint or transaction lock), not by disabling a button in the UI.

## 六、Failure semantics

| Case | Status / message |
| :--- | :--- |
| Missing or expired signed session | `401 bff_auth_required` |
| Valid session without the permission bit | `403 lab_permission_denied` |
| Resource not owned by this tenant / missing | `404 lab_resource_not_found` |
| Another network is already running for this tenant | `409 lab_network_already_running` |
| Tenant instance missing / unhealthy | `503 tenant_runtime_unavailable` |
| `sessionSecret` missing | `503 bff_auth_not_configured` |
| IAM role lookup failed | `503 bff_role_resolution_failed` |
| Write capability not open | `405 bff_method_not_allowed` (same as ADR-0020) |
| Upstream authentication misconfigured | `502 upstream_auth_misconfigured` |

**Forbidden**: 403 for cross-tenant access; an empty list pretending success without a session; treating a role-lookup failure as `tenant_user`; using `x-tenant-id` as the tenant source.

## 七、Audit

High-risk operations write to an audit outbox **before** the action and append the result afterwards. If the audit write fails, the high-risk action returns `503 audit_unavailable`; never "do it first, log later".

Minimum fields:

| Field | Meaning |
| :--- | :--- |
| `tenant_id` | Session tenant; never empty |
| `actor_id` / `actor_username` | Session subject |
| `engine` | `simulator` / `mininet` |
| `network_id` | BFF ledger ID |
| `action` | `create` / `start` / `stop` / `reset` / `delete` / `terminal_open` / `terminal_close` / `sniffer_start` / `sniffer_stop` |
| `result` | `allowed` / `denied` / `succeeded` / `failed` |
| `reason` | Rejection or failure reason (no sensitive payloads) |
| `request_id` | Upstream / BFF correlation ID |
| `client_ip` | Required for audit; redacted in UI per deployment policy |
| `created_at` | Server time |

Terminal and capture events must record session start/end, target node and duration; terminal input and capture payloads must never be recorded.

## 八、Implementation order and gates

| Phase | Content | Done when |
| :--- | :--- | :--- |
| **P0** | This ADR + `shared/constants/labPermissions.ts` + `check:lab-tenancy` | Pure-function assertions green; document indexes updated |
| **P1** | Signed session cookie + IAM role resolution + `/api/lab/**` read guard + `x-tenant-id` stripping | Unauthenticated 401, missing secret 503, cross-tenant 404; `check:lab-bff` gains an auth group |
| **P2** | Resource ledger + list egress filtering + read pages receive tenant context | Two tenants cannot see each other's read-only data; a ledger miss never touches the upstream |
| **P3** | Per-tenant instance deployment + create / start / stop / delete + one-network 409 | Two tenants can run networks concurrently without interference; data-plane isolation drill passes |
| **P4** | Terminal / sniffing / WebSocket ticket + audit + support session (if approved) | Ticket is short-lived, one-shot and bound to tenant and node; audit is replayable |

**Gate**: until P1 and P2 are complete, P3 write endpoints must not be added to `MININET_ROUTES` or the simulator whitelist; until P4 is complete, terminal, sniffing and the four WebSockets stay closed. No phase may substitute "it is on the intranet" for an authorisation check.

> Status (2026-11-15): P0–P2 are implemented — signed session, IAM role resolution, `/api/lab/**` read guard, tenant-instance registry, `x-tenant-id` stripping, the BFF ledger and list egress filtering; `check:lab-bff` passes 51/51. Cross-tenant resource access (nodes / links) returns `404 lab_resource_not_found` on a ledger miss or when the resource is absent from the tenant's manifest, without touching the upstream; a tenant without an instance still gets `503 tenant_runtime_unavailable`. The read-only simulation page now lives in the scenario layer at `/scenario/simulator`.

## 九、Rejected options

| Option | Why rejected |
| :--- | :--- |
| **C: single-instance global lock** | Only guarantees "one user at a time", not tenant isolation; one tenant's topology, captures and terminal remain visible to another. If used temporarily, it must be named a global lease and marked as non-isolated in the UI. |
| Using `x-tenant-id` as the tenant source | The client can forge it; ADR-0009 already records that tenant-to-token binding is undecided. This ADR derives the tenant from a signed session and strips the header. |
| Using the unsigned `nmcps_ui` cookie as a boundary | It can be injected or tampered with and is only visible under `/api/auth`. |
| Checking only the `tenant_admin` role code | `UP-RBAC-09` proves a role can be bound across tenants; `role.tenant_id` must be checked too. |
| Treating an upstream `sim_id` / node ID as a credential | Upstream IDs can be guessed or returned across tenants; the boundary is the BFF ledger plus the session tenant. |
| Returning 403 for cross-tenant access | It leaks existence; use one 404. |
| Giving platform administrators default cross-tenant read/write | Violates least privilege; support must go through a time-boxed support session. |

## 十、Residual risks and later decisions

1. **Instance orchestration is outside this repository**: creating containers / namespaces, quotas and teardown belongs to deployment; the BFF only consumes the registry. Who writes the registry and how health is checked must be added to deployment documentation.
2. **IAM role lookup cost**: per-role detail calls can be slow; P1 starts with a 60-second cache and replaces it if the upstream offers a batch endpoint.
3. **Signing key rotation**: `NUXT_BFF_SESSION_SECRET` needs a dual-key verification window so rotation does not log everyone out; the window is implemented in P1.
4. **Support sessions**: if the requester later needs platform-administrator troubleshooting, a separate ADR must define the approver, time limit, allowed operations and audit retention; this ADR does not open it.
5. **Simulator capability gap**: if port 8001 cannot provide per-tenant instances, `/api/sim/**` writes stay closed and only ledger-scoped reads are exposed; a single instance must never pretend to be isolated.

## 十一、Appendix: transition from the read-only channel

- `GET /api/lab/channel` keeps returning `readOnly: true` / `writeEnabled: false` until this ADR is implemented;
- from P1, the channel endpoint itself requires a signed session (or is explicitly documented as an unauthenticated probe that leaks neither instance addresses nor tenant information);
- the 17 read-only entries in `GET /api/lab/**` stay unchanged, but each one first passes the tenant and ledger checks;
- the existing `check:lab-bff` assertions stay; P1 grows the suite to 39 (signed session, 401/403/503, tenant-instance isolation and `x-tenant-id` stripping), and P2 grows it to 51 (ledger tenant isolation, list egress filtering, node / link resource 404 with zero upstream hits) instead of deleting the old ones.
