# ADR-0028: the minimal shape of the SNMP collection face (first M2 increment)

> **Layer**: Tier 5, the record layer — published text is append-only; corrections arrive as a new `##` section, never by rewriting a published conclusion.
> **Relationship to the existing baselines**: `NMCPS-DESIGN-008` (`layers/content/collections/cn/architecture/2.domain/simulation.md`) states the M2 acceptance as "an external `snmpwalk` reads consistent OIDs"; `NMCPS-ARCH-007` (`layers/content/collections/cn/architecture/1.architecture/lab-deployment-architecture.md`) leaves "SNMP `:161` versus the host `snmpd`" undecided; `NMCPS-ADR-0027` D5 / R6 says an SNMP write face needs its own `lab:snmp` and that `snmp/onboard` is not rebuilt as a forwarding channel. None of them says what the first increment looks like — this ADR fills that gap.

## 1. Context (why the reference cannot be copied)

- **The reference implementation depends on third-party system components**: `engines/mininet_wifi/snmp_agent.py` writes an `snmpd.conf` per node namespace, starts net-snmp's `snmpd`, and bridges enterprise OIDs through AgentX / `pass`; the wireless side ships 21 MIB texts. Neither premise holds here: redistribution is unlicensed (`NMCPS-ADR-0027` D7), and whether the host has net-snmp installed must not decide whether the simulated network is collectable.
- **Collection is an external behaviour, not a page behaviour**: the NMS polls simulated nodes with its own `snmpwalk` / exporter, so the face must answer standard OIDs. The acceptance stays `snmpwalk -v2c -c public <node> 1.3.6.1.2.1.1`; only the implementation stops being `snmpd`.
- **The port conflict is a host-face problem, not a node-face problem**: each Mininet node is its own netns, so binding `:161` **inside that namespace** never touches the host `snmpd`. Only a single root-namespace proxy would contend for the port, and that shape cannot work anyway — node IPs are not routed in the root namespace.

## 2. Decisions (D1–D7)

| ID | Decision | Detail |
| :--- | :--- | :--- |
| **D1** | **A self-written stdlib agent, one per node** | BER encoding, the MIB projection and the UDP server live in `services/mininet-api/mininet_gui_backend/snmp/` and use the Python standard library only. No `net-snmp` import, no generated `snmpd.conf`, no MIB text in the package: only the numeric OID arcs from RFC 1213 / 2863, resolved by the NMS's own MIBs. |
| **D2** | **The agent runs inside the node's own netns** | After a successful start, `nsenter -t <node.pid> -n --` puts the agent process into that node's network namespace and it binds `0.0.0.0:<port>`. Node IPs are reachable by construction; the host `snmpd` and the host port table are untouched. Without root or `nsenter` the node is reported `unavailable` — there is no fallback root-namespace proxy. |
| **D3** | **Read-only v2c, community from the environment** | Only GET / GETNEXT over `SNMPv2c` (version encoding 1); no SET, no v3 USM, no traps. Community is `LAB_SNMP_COMMUNITY` (default `public`), port is `LAB_SNMP_PORT` (default 161, inside the node netns); both are deployment configuration, not page input. The write face (onboard / rotate / revoke) needs the independent `lab:snmp` bit per `NMCPS-ADR-0027` D5 — **this increment exposes no SNMP write endpoint**. |
| **D4** | **Lifecycle follows network start/stop, off by default** | With `LAB_SNMP_ENABLED=1` the agents start after a successful `POST /api/mininet/start` and are reaped by `stop`, `reset`, `full_reset` and process exit. A collection failure **must not** fail the network start; a node that cannot be served is only visible in the state reading. Off by default because M2 is still experimental and 161 must be opened deliberately by the deployer. |
| **D5** | **Three MIB groups plus the enterprise type OID** | `SNMPv2-MIB` system (`1.3.6.1.2.1.1`, including `sysName` / `sysDescr` / `sysObjectID` / `sysUpTime` / `sysServices`), `IF-MIB` `ifTable` with the basic columns (including `ifName` / `ifAlias`), and the `IP-MIB` `ipAddrTable` (including `ipAdEntNetMask`). `sysObjectID` uses the same enterprise numbering as the reference, `1.3.6.1.4.1.99999.<type>` (1 switch / 2 ap / 3 router / 5 station / 7 host …), so NMSs that classify by `sysObjectID` still recognise node types. Counter columns (`ifInOctets` / `ifOutOctets`) are zero in this increment — see §4. |
| **D6** | **Adjacency comes from the ledger projection, not LLDP** | The LLDP face was retired in `NMCPS-ADR-0027` R8, so the agent serves no `lldpRemTable`. An NMS that needs topology uses `GET /api/mininet/snmp/topology` (same path behind the BFF, `lab:read`), which projects ledger nodes / links into a collectable target list (node IP, port, community, sysObjectID, interfaces) for its seed configuration. This is **semantically different** from the reference `POST /snmp/topology` (subnet scan + LLDP inference): that one discovers the host network, this one publishes the simulated one. |
| **D7** | **No credential orchestration or exporter wiring yet** | `snmp/onboard` (v2c/v3 onboarding, rotate / revoke / export), `nms/*` (vmagent, snmp-exporter-reset) and `GET /snmp/tools` are out of scope: they need `lab:snmp` plus the IAM `lab_snmp` role first, or belong to an external monitoring stack. The BFF whitelist grows by two read-only entries only. |

## 3. Deliverables and acceptance

| Item | Location | Acceptance |
| :--- | :--- | :--- |

| MIB projection | `snmp/mib.py`: an ordered OID table built from the node profile, with `get()` / `getnext()` semantics (`noSuchObject` for a missing object, `endOfMibView` past the last) | same check: system / ifTable / ipAddrTable OIDs exist and `getnext` is monotonic |
| Node profile | `snmp/inventory.py`: node and interface facts (IP / MAC / prefix / MTU) read from `app.net`; no page state | same check: a stub node yields a complete profile; nodes without IP or pid are skipped |
| Agent | `snmp/agent.py`: `respond()` (pure) + `serve()` (UDP); v2c GET / GETNEXT only; a wrong community is dropped | same check: a server on `127.0.0.1:0` answers a loopback client with the system group; a wrong community gets no response; plus a **real subprocess** `python -m … snmp.agent --profile … --port … --community …` asserting that all three flags take effect, SIGTERM exits 0 and the port is bindable again afterwards |
| Runtime | `snmp/runtime.py`: `LAB_SNMP_ENABLED` / `LAB_SNMP_PORT` / `LAB_SNMP_COMMUNITY`, profiles under `.data/snmp/` (0600), process table, start/stop/status | same check: `start` is a no-op when disabled; state is three-valued (running / stopped / unavailable) |
| Upstream endpoints | `GET /api/mininet/snmp/state` (runtime + per-node status) and `GET /api/mininet/snmp/topology` (ledger projection) | `pnpm lab:check` route list + source guard (both read endpoints may only pass `runtime.status()` through — no `community` in the route layer; `check:snmp` only exercises the runtime, so this can only be pinned in source) + `pnpm check:lab-bff` counts / forwarding |
| Lifecycle hooks | started from `start_network()`; reaped by `stop_network()` / `full_reset_network()` and lifespan shutdown; failures only logged | `pnpm lab:check` source guard (group 4, "SNMP collection hooks"): all four hook points plus the `try/except` in `_start_snmp_collection()` are present |
| Real acceptance | On 90: root backend + `LAB_SNMP_ENABLED=1`, `snmpwalk -v2c -c public <h1-ip> 1.3.6.1.2.1.1` / `…1.3.6.1.2.1.2.2.1` | closed 2026-11-26 with net-snmp on the host — see §5 for the measured walks, the cross-node check and the stop/start reaping |

## 4. Explicitly out of scope for this increment

- **Real counters**: `ifInOctets` / `ifOutOctets` / error counters are zero; feeding real traffic needs periodic interface sampling or IPC with the backend (P1).
- **64-bit counters and `ifXTable`**: `ifHCInOctets` and friends need Counter64 and the same statistics source; they land with real counters.
- **Dynamic topology**: after adding / removing nodes or links at runtime the agent view refreshes only on the next `start` (`/snmp/topology` reads the live ledger, so the two differ briefly). No page exposes this; it is booked as "restart the network to refresh".
- **Credential orchestration**: `LAB_SNMP_COMMUNITY` is a single deployment value; per-node / per-tenant communities, v3 users and rotate / revoke wait for `lab:snmp` and the IAM `lab_snmp` role.
- **MIB files**: not shipped; the NMS brings standard MIBs. Shipping them later requires resolving redistribution first (`NMCPS-ADR-0027` D7).

## 5. Acceptance and known limits

- Machine side: `pnpm check:snmp` (stdlib, no root, no mininet; 41 assertions today) covers the codec / MIB / profile / loopback UDP / the **real subprocess entry** (the `--profile` / `--port` / `--community` flags of `python -m … snmp.agent` all take effect, SIGTERM exits 0, the port is reclaimable — a self-check of the command line `runtime.py` builds, not a netns acceptance) / the credential store and the `apply_credentials()` restart face; `pnpm lab:check` covers the upstream routes, the lifecycle hooks and the source guards for "read endpoints pass `runtime.status()` through / write endpoints share one persist-then-restart body"; `pnpm check:lab-bff` covers the whitelist counts and forwarding. In CI it is its own step, `SNMP agent self-check` (conclusion key `snmp`, regex `结果：N 通过 / 0 失败`, sample `scripts/fixtures/ci-logs/snmp.log`), no longer appended to the `lab-api` step's log — mixed in there, "which layer went red" was only answerable by reading the whole log.
   - CI evidence (2026-11-26): on commit `5145a0f`, run `45734309550` kept this step in the `lint / typecheck / governance` job, which went green in 1m2s; the artifact `check-logs-quality/snmp.log` ends with `结果：28 通过 / 0 失败` and the sealed sample was refilled from that run (its `PYTHONPATH` line reads `/home/runner/work/…`, so it cannot be a local paste). All nine samples were then re-synced and re-sealed with `--from-ci 45734309550` (commit `9428de0`), and the run that push triggered, `45736307204`, went green as well — a sample byte refresh does not turn the step red.
- Real side (closed on 90, 2026-11-26): back up the ledger with `GET /api/mininet/export_json`, `mn -c`, restart the backend as root with `LAB_SNMP_ENABLED=1`, rebuild the same topology (3 switches / 4 hosts / 6 links) and `POST /start`; `GET /api/mininet/snmp/state` reported all four hosts `running`. With net-snmp installed on the host (`apt-get install snmp` → `/usr/bin/snmpwalk`) the measured results were:
  - `nsenter -t <h1 pid> -n snmpwalk -v2c -c public 127.0.0.1 1.3.6.1.2.1.1` → `sysName=h1`, `sysObjectID=1.3.6.1.4.1.99999.7`, `sysServices=72`;
  - `…1.3.6.1.2.1.2.2.1` → `ifDescr=h1-eth0`, `ifType=6`, `ifMtu=1500`, `ifPhysAddress=00 00 00 00 00 01` (matching the ledger MAC), admin/oper up;
  - `…1.3.6.1.2.1.4.20.1` → `ipAdEntAddr=10.0.0.1` with `ipAdEntNetMask=255.0.0.0`, the same value `addressing_plan` reports as `10.0.0.1/8` (the agent serves the node netns' real prefix, not an assumed ledger prefix);
  - walking from **h2's netns** against `10.0.0.1` returned the same system group, so the agent binds the node's real IP and is reachable across the simulated fabric, not just on loopback;
  - `-c private` got no response (timeout) and an unregistered OID answered `No Such Object`;
  - `POST /stop` left zero agent processes with `running=false`, and `POST /start` brought back four `running` entries (both directions of the lifecycle hooks exercised).
  All three assertions hold: `sysName` equals the ledger node id, and `ifDescr` / `ipAdEntAddr` agree with `GET /api/mininet/interfaces` / `addressing_plan`. Cleanup followed `09-local-sudo.md`: both `.data` and `services/mininet-api/.data` were chowned back to the current user, because the agent profiles are 0600 files written by root.
- Ports: binding 161 inside each node netns needs no host port mapping, and the host `snmpd` may keep the root namespace's 161. This closes the `NMCPS-ARCH-007` §7 "port conflict" item: there is no node-face conflict, and the only conflicting shape (a root-namespace proxy) is rejected by D2.

## 6. The credential face (appended 2026-11-26, D8–D12)

> This section only appends; §2 stays as published. Three of its conclusions are **superseded here**: D3's "community comes from the environment", D6's "`topology` carries the community", and D7's "no write face in this increment" — so the §4 "credential orchestration" item is closed. The second M2 increment is therefore "the community string becomes manageable", not a copy of the reference `POST /snmp/onboard` subnet scan + hop-by-hop push: the nodes already live in the simulated network, so onboarding only writes one credential **on this instance** and restarts the agents.

### 6.1 Decisions

| ID | Decision | Detail |
| :--- | :--- | :--- |
| **D8** | **One credential, at `.data/snmp/credentials.json`** | Directory `0700`, file `0600`, written atomically (temp file + `os.replace`); fields `version` (v2c, always `2`), `community`, `credential_version` (monotonic from 1), `created_at`, `rotated_at`, `actor_id`. No per-node / per-tenant credentials: one instance runs one network, and several credentials only create a second source of truth for "which string does this node use". |
| **D9** | **The secret is shown once, in the onboard / rotate response** | `POST …/onboard` and `POST …/rotate` return the `community` in clear; afterwards `GET /snmp/state` only reports `onboarded` / `credential_version` / `credential_created_at` / `credential_rotated_at`, and `GET /snmp/topology` sets `community` to `null` and reports `credential_version` instead. Both reads only need `lab:read`, so turning them into a credential read face would hand the whole network's community string to a read-only session. Losing the secret costs one `rotate` — that is the deliberate price. Audit records the action and the permission bits, **never the secret**. |
| **D10** | **Three write endpoints, all `lab:snmp` only** | `NMCPS-ADR-0027` D5 requires an independent bit for the SNMP write face: `lab:snmp` is the seventh matrix bit, and the IAM role `lab_snmp` grants that one bit only — it is **not** implied by `lab:operate` / `lab:create` / `lab:delete` (same tier as `lab:terminal` / `lab:sniffer`). Endpoints and error codes in 6.2. The whitelist grows 61 → 64 (writes 37 → 40, reads stay 24). |
| **D11** | **The community must be stronger than the default** | The request body's `community` may be omitted: then the server generates `secrets.token_hex(16)` with a `sim-` prefix. An explicit value must be 8–64 printable ASCII characters without whitespace and **must not** be `public` / `private` (`400 snmp_community_weak`) — onboarding exists to leave the well-known default behind, and accepting it would let an operator believe the face was hardened. |
| **D12** | **Reject when collection is disabled, and decide before writing** | With `LAB_SNMP_ENABLED` off (or no real network this process can drive) all three endpoints answer `409 snmp_collection_disabled` and **write no file**: a credential that can never take effect, plus an "onboarded" response, would make an operator believe the NMS can poll. The order is fixed: validate the request → check enabled → write → restart agents. Never write first and discover afterwards that the agents cannot start. |

### 6.2 Endpoints and the apply order

| Endpoint (same path behind the BFF) | Upstream | Semantics | Failures |
| :--- | :--- | :--- | :--- |
| `POST /api/mininet/snmp/onboard` | `POST /api/mininet/snmp/onboard` | Onboard: write the credential, restart agents, return the one-time secret | Already onboarded `409 snmp_credentials_exist`; weak string `400 snmp_community_weak`; collection off `409 snmp_collection_disabled` |
| `POST /api/mininet/snmp/rotate` | `POST /api/mininet/snmp/rotate` | Rotate: new string, `credential_version + 1`, restart agents | No credential `404 snmp_credentials_missing`; otherwise as above |
| `DELETE /api/mininet/snmp/credentials` | `DELETE /api/mininet/snmp/credentials` | Revoke: delete the file, agents fall back to `LAB_SNMP_COMMUNITY` and restart | No credential `404 snmp_credentials_missing`; collection off `409 snmp_collection_disabled` |

- Revoking is **not** the same as stopping collection: deleting the credential makes the agents fall back to the deployment value (D3's `LAB_SNMP_COMMUNITY`); stopping collection means turning `LAB_SNMP_ENABLED` off. Revoke therefore has exactly one meaning and does not double as a hidden kill switch.
- Applying is a **full restart**: `snmp_runtime.apply_credentials()` calls `stop_all()` and then `start_for_net()` for a running network; the response's `applied` says whether a restart happened. A node that fails to start only shows in `nodes[*].status` and does not fail the whole write (same stance as D4).
- The only body is `{ community?: string }`; `DELETE` carries none (the path segment says what is deleted, matching the existing DELETE convention).

### 6.3 Deliverables and acceptance

| Item | Location | Acceptance |
| :--- | :--- | :--- |
| Credential store | `mininet_gui_backend/snmp/credentials.py`: `onboarded()` / `public_view()` / `onboard()` / `rotate()` / `revoke()`, strength validation, atomic write | `pnpm check:snmp`: the file mode is `0600`, `public_view()` carries no secret, duplicate onboard / rotate without a credential / revoke without a credential each raise their own error, and a rotation bumps the version with a different secret |
| Applying | `snmp/runtime.py`: `collection_enabled()`, `effective_community()` (credential first, then the environment), `apply_credentials()`; `status()` gains `onboarded` / `credential_version` | same check: with a fake process table, `apply_credentials()` puts the new string on every command line and repeated calls leak no old process; both new `status()` fields follow the credential |
| Upstream endpoints | Three write endpoints plus Pydantic request models in `api.py`, error codes as above | `pnpm lab:check` route list + `pnpm contracts:gen` snapshot |
| BFF | Three entries in `mininetRoutes.ts` (`lab:snmp`), `channel.capabilities.snmp`, `writeEnabled` counts that bit | `pnpm check:lab-bff` ⓪ count 64 / ① `endpointCount === 64` / ⑰ three cases (`lab_snmp`'s channel differs by that bit only; a tenant admin onboarding gets 403 with zero upstream hits; `lab_snmp` onboarding gets 200 and hits `/api/mininet/snmp/onboard`); `pnpm check:lab-tenancy` asserts the bit comes from `lab_snmp` alone |
| Real machine | Root backend on 90 with `LAB_SNMP_ENABLED=1`; automated by the two 11.16 cases in `check:lab-real` (root + `/usr/bin/snmpwalk` + a not-yet-onboarded instance, otherwise `⏭`) | After onboarding, the returned string walks and the old one times out; after `rotate` the new string walks and the previous one times out; after `DELETE` the deployment `LAB_SNMP_COMMUNITY` works again (root run 21/21, 2026-11-26) |

### 6.4 Explicitly not in this section

- **v3 / USM**: v2c only. v3 needs an engine ID, clock synchronisation and a user table — a separate decision.
- **Per-node / per-tenant credentials**: one per instance (D8).
- **Config export and NMS wiring**: the reference's vmagent / `snmp-exporter-reset` stay out of this repository (`NMCPS-ADR-0027` R6); the operator takes the secret at onboarding time and pastes it into their own NMS.
- **A page entry point**: this section adds endpoints and a capability bit only; `/scenario/simulator` gains no credential dialog. When the page does consume it, it must render by `capabilities.snmp` and still honour "unauthorised actions are not rendered".

## 7. Addendum (2026-11-26): the lab SNMP dialog (page entry point)

> The only purpose of this section is to revise the last bullet of 6.4 — "/scenario/simulator gains no credential dialog" — into "it gains a dialog whose reads are visible to every session and whose writes render by capability bit", and to record the structural constraints the page must not violate. Sections 1–6 stand unchanged.

- **Entry point**: toolbar "File → SNMP collection…" (`SnmpModal.vue`), in the same group as export and settings. Readings come from `GET /api/mininet/snmp/state` (`lab:read`), so the entry is **visible in every session**: whether collection is on and which credential version is in use is the first thing an operator needs while debugging, and hiding it behind `lab:snmp` would leave a read-only session unable to answer "which string is in use".
- **Write surface renders by capability bit**: the onboard / rotate / revoke buttons exist only when `capabilities.snmp === true`; otherwise the dialog states the read-only reason in place. Never render first and wait for a BFF 403 — a 403 is the boundary, not the interaction.
- **"Shown once" is structural, not copy**: the `community` field of `LabSnmpState` (`layers/scenario/shared/types/labSnmp.ts`) carries only the **deployment default** (that string while not onboarded, with `community_source: deployment`; the upstream sets it to `null` after onboard / rotate); the orchestrated secret exists only in `LabSnmpCredentialReveal`, arrives once from the onboard / rotate response, and the page drops it when the dialog closes — the dialog has no path that renders a secret from `state.community` either. The fake upstream holds the same line (`state.community` is `null` once onboarded), so any implementation that keeps the plaintext on screen after a refresh fails loudly instead of degrading silently.
- **Two-step revocation**: the first click only surfaces the consequence ("any NMS still polling stops immediately") and swaps in a confirm button without sending a request; a `busy` change or closing the dialog resets that intermediate state so an unanswered confirmation never vouches for the next one.
- **Acceptance**: `pnpm check:ui` gains eight 11.15 cases (total 297 → **305**) — initial read shows not-onboarded + deployment default with a single write entry; onboarding posts once and the secret appears only in the dialog; copy really lands on the clipboard; rotation changes the string and bumps the version; closing and reopening drops the secret block; the first revoke click issues zero `DELETE`; confirming issues exactly one and the reading falls back to the deployment default; without `lab:snmp` none of the three write buttons renders. The same run re-checks the eight-item "File" menu (`11.5`) and the whole shape table in `11.6b`.
- **Not included**: v3 / USM, per-node credentials, NMS pulling its own config (as in 6.4); the dialog does not expand per-node `nodes[*].error` detail — that layer stays exactly as `GET /snmp/state` returns it.
