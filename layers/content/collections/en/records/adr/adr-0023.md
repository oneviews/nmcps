# ADR-0023: Reconciling the lab ledger with the upstream instance (explicit adoption)

> **Tier**: Tier 5 records layer — append-only after publication; later corrections go into added `##` sections instead of rewriting published conclusions.
> **Relation to ADR-0021 / ADR-0022**: ADR-0021 P2 made the ledger manifest the tenant visibility boundary, and ADR-0022 made the write path maintain it after a successful write. Neither answered "a write happened outside the manifest": the legacy Vite frontend could still call `:8000` until retirement, and operations scripts can call the upstream directly, in which case the ledger is never told.
> **Evidence (2026-11-17)**: a sample instance held 8 hosts + 7 switches + 14 links upstream while the ledger still listed the previous day's 9 nodes / 8 links. The intersection was `h1 h2 h3 h8 s1 s2` plus 4 links, and `r1 c1 h9` no longer existed upstream. The canvas therefore rendered only part of the topology; the canvas, the coordinates and the `kind` normalisation were not involved.

---

## 1. Decisions (summary)

| Id | Decision | Notes |
| :--- | :--- | :--- |
| **D1** | Reconciliation is an **explicit action**, never implicit auto-convergence | The read path keeps filtering by the manifest; a node that appeared upstream does not silently widen what a tenant can see. A human triggers reconciliation. |
| **D2** | The endpoint lives in the BFF only: `POST /api/lab/networks/{id}/sync` | It forwards no upstream write; it reads upstream and updates the ledger, so it does **not** join `MININET_ROUTES` and is not a write-whitelist entry. The static route wins over `[...slug].ts`. |
| **D3** | Two permission bits, `lab:create` + `lab:delete` | Same tier as `import_json` / `full_reset`: reconciliation pulls out-of-manifest nodes into the tenant boundary, i.e. an adoption; missing either bit returns `403 lab_permission_denied`. |
| **D4** | Typed confirmation `{ confirm: "<network_id>" }` | Same implementation as `full_reset`: missing field, wrong type or wrong value all return `400 lab_confirm_required` **without** touching the upstream or the ledger. |
| **D5** | Audit first, then execute; one write per network | The outbox records `allowed` first, then `succeeded` / `failed`; a lock conflict returns `409 lab_operation_in_progress`, a failed audit `503 audit_unavailable`. |
| **D6** | **A failed read never writes**; an empty upstream writes an empty manifest | If any node kind or the links fail to load, the upstream status and message are returned verbatim and the ledger is untouched ("cannot read" is not "nothing there"). If all six succeed and are empty, `{ nodes: [], links: [] }` is written — that is a fact, not a failure. |
| **D7** | The manifest is **rewritten as a whole**, never merged | Reconciliation means "the upstream is the truth right now"; a union would keep ghost ids forever. The response carries `adopted` / `dropped` so the page can state what was pulled in and what was removed. |
| **D8** | The entry renders only with `lab:create` + `lab:delete` | One item in the `File` menu, with a modal that asks for the network id; without both bits the item is **not rendered** — never render-then-wait-for-403. |
| **D9** | Boundaries unchanged | The tenant comes only from the signed session; `upstream_id` is never a credential; reconciliation does not touch `engine` / `tenant_id` / `state` and creates or deletes nothing upstream. |

## 2. Endpoint contract

```
POST /api/lab/networks/{id}/sync
body: { "confirm": "<id>" }
```

| Stage | Outcome |
| :--- | :--- |
| No session / credential mismatch | `401 bff_auth_required`; missing session secret `503 bff_auth_not_configured` |
| Missing `lab:create` or `lab:delete` | `403 lab_permission_denied`, zero upstream requests |
| Network not in the ledger (including another tenant's) | `404 lab_resource_not_found` |
| Channel not configured / no tenant instance | `503` (`mininet_not_configured` / `tenant_runtime_unavailable`) |
| Confirmation mismatch | `400 lab_confirm_required`, zero upstream requests |
| A write is already in flight | `409 lab_operation_in_progress` |
| Any upstream read fails | upstream status + message; the ledger is unchanged |
| Success | `200`, `data: { network, nodes, links, adopted, dropped }` |

`network` in the success body is a `LabNetworkSummary` (no `upstream_id`); `nodes` / `links` are the post-reconciliation manifest, link keys normalised as undirected `a--b`.

## 3. Read-side rules

- Nodes come from `GET /hosts`, `/switches`, `/routers`, `/nats`, `/controllers`; dictionary keys are used for maps, `id` / `name` for arrays.
- Links come from `GET /links` as `{ from, to }` (the real backend already resolves interface-side node names); the older `identity.source/target` shape is also accepted.
- Controller ↔ switch is an **association**, not a link (same rule as ADR-0022 `import_json`): the upstream `/links` does not contain association edges, so no extra pruning is applied.
- The result is de-duplicated and sorted by id, link keys go through `normalizedLabLinkKey()`, so reconciling the same facts twice yields the same manifest.

## 4. Why not auto-reconcile

1. Auto-reconciliation would widen the tenant boundary the moment someone writes directly upstream, bypassing the `lab:create` / `lab:delete` gate.
2. Reads are spread across hosts / switches / links / flows / stats; converging implicitly would turn every read into a ledger write, with races that far outweigh the benefit.
3. An explicit action lets the audit record who adopted what and when, which is replayable during an incident.

## 5. Out of scope

1. **Controller association**: reconciliation only fixes visibility. In the sample network all seven switches had `controller: null`; the 100% `pingall` loss came from an upstream with no controller (`OVSSwitch` defaults to `failMode='secure'`), not from the ledger. The new frontend also has no `associate_switch` entry yet; that needs its own work item.
2. **Multiple instances / replicas**: the lock is still in-process (ADR-0022 D5 boundary); this endpoint inherits that limit.
3. **State field**: reconciliation does not correct `state`; the run state still comes from `GET /start`.

## 6. Acceptance

- `check:lab-bff` group ⑭: dual-permission 403 / missing confirmation 400 / wrong confirmation 400 (all three with zero upstream requests), success 200 with the ledger manifest equal to upstream, ghost ids removed, ledger untouched on an upstream 500, two audit rows (`allowed` + `succeeded`).
- `check:ui` group 11.6b: the entry renders only with both bits (and is disabled when `lab:delete` is withheld), the confirm button stays disabled while the typed id differs, and confirming reads the six upstream collections without a single write, rewrites the ledger manifest to upstream facts and keeps the canvas unchanged.
