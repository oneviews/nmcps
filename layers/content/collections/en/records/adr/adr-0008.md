# ADR-0008: Restore the Download Landing Page and the Site Entry

> **Tier**: Tier 5 record layer — body is immutable (append-only); changes require a new ADR with `supersededBy`.

- **Background**:
  1. The 2.0 user-preferences refactor (`cc998e9`) replaced `app/pages/index.vue` — a landing page with the logo, platform detection, multi-format download and GitHub Release links — with `onMounted(() => navigateTo('/dashboard/overview'))`. After the removal, `app/layouts/home.vue`, the `pages.index.*` i18n keys (already present in cn and en), the `downloads` data in `app.config.ts` and the `useOS` composable (deleted in the same refactor) were left orphaned.
  2. The download entry is therefore gone: no page tells users the current version, the per-platform installers or the Release links, while the 404 page's "back home" action and the `SiteNavbar` logo both point at `/`, which only performs a redirect.
  3. Installers are uploaded to GitHub Release by CI; `public/downloads/README.md` states that binaries must not live under `public/` (they would be packed into the Tauri binary, adding hundreds of MB). The page only needs to build URLs, not serve files.
- **Decision**:
  1. **`/` is the download landing page again** (`definePageMeta({ layout: "home" })`) and no longer redirects to the console; the console is reached through the `SiteNavbar` navigation, and the 404 "back home" action and the logo return to the landing page. Browser and Tauri share the same behaviour — no environment split.
  2. **Restore `app/composables/useOS.ts`**, detecting `windows / macos / linux / android / ios / unknown` from the user agent. Order matters: iOS before macOS (iPadOS 13+ desktop mode masquerades as Macintosh) and Android before Linux (Android user agents contain `Linux`). `ios` / `unknown` fall into the "no installer, pick another platform" branch.
  3. **The primary button uses that platform's `files[0]`**, its recommended format; the "Other formats (n)" dropdown lists only the remaining `n` formats. The historical implementation also listed `files[0]`, so the label said 5 while the menu showed 6; this ADR fixes the mismatch.
  4. **Download URL = `downloads.basePath` (trailing slashes trimmed) + `encodeURIComponent(file name)`**, avoiding `//` and unencoded characters that make the CDN return 404.
  5. **Version and file names come from `downloads` in `app.config.ts` only**: the page never hardcodes a version, so a release bump touches `app.config.ts` and the bump flow alone.
  6. **No new dependency, i18n key or endpoint**: the page reuses the existing `pages.index.*` keys (`download`, `detectedUsing`, `noPackage`, `downloadVersion`, `otherFormats`, `version`, `otherPlatforms`, `starOnGithub`, `madeBy`).
- **Impact**:
  - `app/pages/index.vue` becomes a landing page again and a `useOS` composable returns; `app/layouts/home.vue`, `SiteNavbar` and `SvgoLogo` are consumed again.
  - The desktop first screen goes back from "straight to the console" to "landing page, then navigate" — matching the behaviour before 2.0.
  - `scripts/check-ui.mjs` gains four landing-page assertions (heading, detection copy, Release URL prefix, link count), raising the total from 21 to 25 checks; the console checks now open `/dashboard/overview` directly instead of relying on the `/` redirect.
- **Alternatives rejected**:
  - **Keep the `/` redirect and add `/download`**: nothing links to it, so the download entry would still be unreachable — effectively not restored.
  - **Redirect only in the desktop app (`isTauri()`)**: one path with two first screens forces `check:ui` and the docs to fork, and clicking the logo in Tauri would bounce users back to the console, making the landing page invisible in the desktop app.
  - **Move installers back into `public/downloads`**: `public/` ships inside the Tauri binary, which is unacceptable for size and upgrade cost (already rejected in `public/downloads/README.md`).
  - **Hardcode version and file names in the page**: inevitably drifts from the bump flow.
- **Open items**:
  - Page data is still the build-time `app.config.ts`. Dynamic publishing (release list, channels, checksums, release notes) should come from the BFF (`NMCPS-ADR-0007`), e.g. `GET /api/ota/releases`; the resource must be registered in `GATEWAY_RESOURCES` and the page must validate that a release exists to avoid dead links or 404s.
  - CPU architecture (x64 / arm64) can only be picked manually from the dropdown: the user agent does not expose it reliably, and `navigator.userAgentData.getHighEntropyValues(['architecture'])` is a viable enhancement.
  - Checksums, signatures and install notes (macOS requires `xattr -c /Applications/nmcps.app` on first run) are not on the page yet.
  - The session / token model is renumbered to **ADR-0009**: `NMCPS-ADR-0007` listed it as "needs ADR-0008", but 0008 is taken by this decision.
