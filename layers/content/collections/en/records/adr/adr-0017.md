# ADR-0017: a data-form interaction baseline — two-pane layout (list / detail), two-level toolbars, view states and record-level breadcrumbs

> **Tier**: Tier 5 records layer — append-only after publication; this is the 0.1.0 first write-up, so baseline detail goes into the body (the `##` follow-up-section style already used by `NMCPS-ADR-0015`).
> **Relation to the baseline**: this ADR records the decision and its evidence; the norm lives in `NMCPS-ARCH-006` (`arch.ui`, Tier 1) and wins on conflict.

---

## 1. Context

### 1.1 What the 1.0 reference implementations actually do

`_reference/nmcps-v1/layers/connector/app/pages/connector/device.vue` (524 lines) is already a full three-pane page; `_reference/nmcps-v1/layers/system/app/pages/system/user.vue` (357 lines) is a single-column list page.

| Dimension | 1.0 `connector/device.vue` | 1.0 `system/user.vue` |
| :--- | :--- | :--- |
| Layout | M pane `UDashboardPanel resizable` (`min 25 / default 30 / max 40`, percent) + a right half `grid-cols-12`: D `col-span-8`, R `col-span-4` | No split: single `UDashboardPanel`, `UTable sticky` + footer pagination |
| Toolbars | **Two levels**: M header toolbar (search + status `UTabs` + create group), D header toolbar (title + create + delete + cancel + save) | **One level**: header toolbar, left search, right bulk delete + status filter + page size + column visibility + refresh + create |
| Selection model | `activeContext = { type, id, data }` as the single source + an `isCreating` flag | None (row actions + modal form) |
| Edit entry | Inline form in D, `<component :is>` per entity type, `<keep-alive>` keyed by `${type}-${id\|\|'new'}` | `UserFormModal` (shared by create and edit) |
| Unsaved protection | `dirtyState{isDirty,id}` + a `requestSwitch(next)` closure with `pendingTarget`; dirty raises "Stay / Discard and switch" | None (closing the modal discards) |
| Delete | D toolbar button → confirm modal → execute, then `activeContext=null` and reload both lists | Row icon buttons / bulk button → delete confirm modal |
| Default selection | `defaultSelectionSettled` runs once; `firstVisibleDevice()` replays the list ordering | N/A (no detail pane) |
| Save action | Toolbar button calls the child's `{ save, cancel }` through a `ref` | Submit inside the modal |
| Empty state | Full-pane block (`UIcon size-32 text-dimmed`, centred `hidden lg:flex`) | `UTable :empty` |

### 1.2 Four things to inherit

1. **Pane-level toolbars**: each pane owns its header toolbar, so an action sits next to the region it affects. The search box in M filters the left pane; "Save" in D saves the record on the right. 1.0 does this in `device.vue` and `system/user.vue` alike, so it is this repository's natural shape.
2. **One selection source plus a switch guard**: a single `activeContext` ref describes "what am I editing", and every switch goes through `requestSwitch()`.
3. **Delete asks first, then acts**, with the confirm copy naming the entity (`entityName()`).
4. **The default selection must equal the first list row**: `firstVisibleDevice()` replays `Device/List.vue`'s ordering (including the Chinese display-name mapping), otherwise the page opens on a record other than the first row.

### 1.3 Three things 2.0 must tighten

1. **Row actions duplicate toolbar actions**: the row `edit` + `trash` group in `system/user.vue` overlaps the create / bulk-delete toolbar, giving delete two entry points; `device.vue` instead puts delete in the D toolbar (correct). Tighten to: **at most one row action; writes and dangerous actions move up**.
2. **The default selection once used a different sort key** from the list (an incident recorded in the code comments: the list ordered by display order, the default selection by Chinese name). Tighten to: **the default selection reuses the list's own `sortKey` function**.
3. **The detail pane is always editable**: `device.vue` has no view state, so the page opens editable and the dirty flag is permanent — every row switch raises a discard prompt. Tighten to: **default view (read-only) → explicit "edit"**; the dirty flag only exists in edit/create.

### 1.4 Why now

`/system/user` is a single-column list with two modals (create / enable-disable), and `/system/log`, `/system/permission`, `/system/policy` are still placeholders. 1.0's `device.vue` proves the split shape works here, but its sizing, toolbar levels and view states are page-local conventions. `usePageToolbar()` is read only by `AppToolbar` itself (a module-level `shallowRef` singleton, so multiple instances overwrite each other; the project runs `ssr: false`, so there is no cross-request sharing), and record-level breadcrumbs exist only as a 15-line `route.meta.breadcrumb` patch in the content centre. **Fix these conventions before the second real form page lands.**

## 2. Decision

### D1 Two-pane skeleton, minimum page width and container budget

Every "collection + single record" page has exactly one target shape: **list pane (left) + detail pane (right)**, provided once by `Layout/Split.vue`; the page fills `#list` / `#detail`. Technical identifiers are always **role names** — `list` / `detail` (`[data-pane="list"]`); "left / right" is the visual position in the two-pane shape, and in the overlay shape the same component renders as "list screen / detail screen" with unchanged roles. **There is no third pane**: related data is implemented as sections inside the detail pane (see D4).

**Minimum page width (assertable constants)**:

| Quantity | Value | Meaning |
| :--- | :--- | :--- |
| `--page-min-w` | **20rem (320px)** | lowest usable width of the single-pane / overlay shape; anything below is a shell defect outside this baseline |
| `--split-min-w` | **56rem (896px)** | **two-pane threshold**: below it only the overlay shape is allowed |
| Detail pane minimum | **32rem (512px)** | never under this in the two-pane shape |
| List pane width | **20–24rem (default 22rem)** | draggable between 18–28rem |
| Viewport floor | 320px | no horizontal scrolling in any mode or shape |

The 56rem figure is arithmetic, not taste: list-pane maximum 24rem + detail-pane minimum 32rem = **56rem**.

**Shape decision** (in priority order; the input is width and device, never author preference):

1. `isMobile` (`mobile` mode or viewport ≤ 1023px) → **overlay**;
2. page content width < 56rem → **overlay** (the narrow-desktop fallback, not a "three-pane downgrade");
3. otherwise → **two panes**.

| Shape | Trigger | List | Detail | Divider |
| :--- | :--- | :--- | :--- | :--- |
| **two panes** | `!isMobile` and W ≥ 56rem | 20–24rem (default 22rem), draggable | flexible, minimum 32rem | 1px `border-default`, no gap |
| **overlay** | `isMobile` or W < 56rem | 100% | 100% (covers the list), a single Back button at the pane toolbar's left | none |

- **The threshold reads container width**, never `md:` / `lg:` viewport breakpoints: sidebar collapse (−12rem), the 1440px `topbar` cap and split-window narrowness all get it wrong.
- **No "collapse the list pane" affordance**: the list is the primary surface; shrinking it to an icon rail makes "which pane holds the data" unstable — go overlay instead.
- **Three drag rules**: (1) a **stable `id`** (`<page>-list`, e.g. `user-list`) remembers the width; (2) double-clicking the handle resets to the 22rem default; (3) the range locks to 18–28rem, never to 0.
- **`UDashboardPanel resizable` is not used**: its theme carries `min-h-svh` (double scrollbars under `bigscreen`), `lg:w-(--width)` (viewport breakpoint) and `hidden lg:block` on the handle, and it stores sizes in a cookie — writing `document.cookie` on every pointer pixel. Use `@container` + `grid` + a local `usePaneResize` (pointer events + rAF batching + a 300ms-debounced `localStorage` write on release + keyboard support).

### D2 List pane rules

**Structure (top to bottom)**: pane toolbar → scrolling list → optional footer (count + pagination).

| Element | Rule |
| :--- | :--- |
| Toolbar left | search (`size="sm"`, 11–16rem, `watchDebounced` 300ms, resets `page=1`) |
| Toolbar right | collection actions: status segments (`UTabs size="xs" :content="false"`), filters, bulk, refresh (with `loading`), column visibility |
| Row height | 40–48px; primary identifier + status badge + one secondary line (time / IP / tenant), truncated with a `title` |
| Row actions | **at most one** (usually just "select", handled by the whole row); writes and dangerous actions never move down into rows |
| Selection state | `bg-elevated` + a 2px primary left bar + `aria-selected` (never colour alone) |
| Grouping | two levels only (group → item), collapse state remembered per group id; no third level |
| Empty | in-pane empty copy + primary CTA (create), never an empty state inside the table |
| Loading | five skeleton rows, no block spinner; a refresh keeps old data plus a thin top progress bar |
| Error | inline error + retry inside the pane; the detail pane stays usable |
| Default selection | on by default in the two-pane shape (the detail pane opens in read-only `view`, so selecting gives context immediately); **reuses the list's `sortKey`**, runs once (`settled` flag); never in the overlay shape |
| Narrow-pane content | at 20–24rem the list shows **at most two lines** (primary identifier + one secondary); a third field moves to a `title` or into the detail pane |

### D3 Detail pane rules

**Three view states**: `view` (default, read-only) → `edit` (explicit) → `create` (empty form). 1.0 lacks view, and the price was "always dirty, prompt on every switch".

**Structure (top to bottom)**: pane toolbar → scrolling form → optional danger zone.

The pane toolbar has a **fixed order** (left → right, no reordering):

1. **Title**: record display name (`text-sm font-semibold`) + subtitle (code / status); "New …" in `create`.
2. **Record actions**: `UFieldGroup` (create, edit / cancel edit, dangerous action such as delete with `color="error"`). In `view` this shows "edit + delete"; in `edit`/`create` the edit entry is hidden.
3. **Submit actions**: `UFieldGroup` pinned right (cancel `neutral`, save `primary`), only in `edit`/`create`, labelled "Save" / "Create".

| Dimension | Rule |
| :--- | :--- |
| Form width | single column ≤ 640px, left-aligned; two columns allowed when the detail pane is ≥ 44rem (labels above fields, never table-style left-aligned labels). **A wide screen must not stretch the single column** (a 1920px screen gives the detail pane ~1200px; cap it with `max-w`, do not widen the inputs) |
| Sections | section headings + dividers, headings sticky at `top-(--content-sticky-top)`; at most 7 sections, otherwise a drawer or tabs |
| Validation | inline field errors + a top summary ("N items to fix", jumps to the first); upstream codes such as `10302` map to a field, never a bare toast |
| Dirty guard | `isDirty` true only in `edit`/`create`; row/page/window/route changes go through `requestSwitch(next)`, dirty state raises "Stay / Discard and switch" (Stay is the default focus) |
| Save success | keep the selection; patch the row in place or refresh silently (no scroll reset, no reselect); `create` turns `?id=new` into the real id (`replace`) |
| Save failure | stay in edit, keep input, show the error nearby; never clear the form or leave edit |
| Empty | nothing selected: "Select a record on the left" + primary CTA (create) |
| Keyboard | tab order = visual order; `⌘/Ctrl+Enter` submits; `Esc` cancels editing (confirm when dirty) |

### D4 Related data inside the detail pane (replaces the former third pane)

- **Placement**: fixed sections inside the detail pane, after the main form; **no new pane and no nested master-detail**. The order is fixed: **overview fields → related tables → activity / audit**.
- **Limits**: at most 2 related tables, each showing ≤ 5 rows plus "view all"; "view all" navigates to that entity's own page — **never a list → detail nested inside the detail pane**.
- **Read-only**: related tables never host the main record's CTA and never write across entities; writes only happen in the main record's own form.
- **Independent tri-state**: each table owns its `pending` / `empty` / `error`; one failure affects neither the main form nor the other table. No data renders "no related data yet", never blank space.
- **Ordering dependency**: wait for `?id`; in `create` show copy ("related data appears after saving").
- **Narrow screens**: in the overlay shape the sections scroll with the form and are **never folded into tabs** (one lookup path per piece of information).
- **Migration**: `device.vue`'s R pane (device interfaces) moves into these sections.

### D5 One toolbar and action ownership

| Area | Owner | Content | Relation to the panes |
| :--- | :--- | :--- | :--- |
| **Left** | `#app-toolbar-left` of the layout's `AppToolbar` (`app/layouts/default.vue`), pages inject via `Teleport` | breadcrumb (`topbar` mode), collection actions (search / filters / sorting / bulk / refresh) | same side as the list pane, operates on the whole collection |
| **Right** | `#app-toolbar-right` of that same toolbar | record actions (including dangerous ones), submit actions, primary CTA (create / save) | same side as the detail pane, operates on the selected record |

**Ownership test (three questions, stop at the first hit; the answer only decides the area)**:

1. Does the action change the **collection** (many / all)? → left area.
2. Does it change **one record** (including dangerous actions)? → right area, "record actions" group.
3. Does it change **only the unsaved draft** (cancel / save)? → right area, "submit actions" group.
4. None of the above (cross-page, read-only navigation, global) → never a new bar: rightmost of the right area, or inside the page content.

**Hard constraints**:

- **One entry point per action per page**; row actions never duplicate toolbar actions (1.0's `system/user.vue` lesson).
- **At most one primary**: "Create" in `create` or "Save" in `edit`; `view` has no primary, the main CTA degrades to `variant="outline"`.
- **Dangerous actions** live in the right area (never in a row), `color="error" variant="outline"`, left of the submit group; bulk dangerous actions live in the left area, appear only when `selectedCount > 0`, and carry a `UKbd` count.
- **Toolbar height comes from a single token `--app-toolbar-h`** (49px-equivalent rem) and never wraps; on overflow the right end folds into a `⋯` menu keeping primary and dangerous actions — never hidden wholesale.
- **The page renders exactly one toolbar**: panes must not add a header of their own (the overlay and the two-pane shape share that one level; its content switches with the current panel: collection actions on the list, the left-area "Back" plus right-area record / submit actions on the detail).
- **Nothing to show means the bar collapses**: teleported content is not a reactive child, so emptiness must be observed on the mount points (`MutationObserver`); with no breadcrumb and no injection the bar collapses to zero height.
- Icon buttons need `aria-label` + Tooltip (`UKbd` for the shortcut); `size="sm"` everywhere.

### D6 Selection, URL and default selection

- Single source of truth: `?id=<record identifier>`; `create` uses `?id=new` (or a page-defined sentinel) and `replace`s itself with the real id after submit.
- **History follows the shape, not the device**: two panes → `router.replace` (both panes are on screen, switching is not a navigation); overlay → `router.push` (back returns to the list, and the browser / system back button is the Back affordance).
- Deep link: select automatically once the list loads; **only a record present in the current `rows` can render** (with no detail endpoint that is the only reliable source). When absent, the detail pane shows "this record is not in the current filter / page" with "clear selection" — **no detail request, no silent page hunt**.
- An `?id` that no longer exists shows the detail empty state plus one notice and **keeps the URL** (an upstream hiccup is not "deleted").
- Changing filters or pages keeps `?id`; if the record is absent from the new result set, take the "absent" branch above and **never reselect silently**.
- Default selection: on in the two-pane shape (same `sortKey` as the list, once only); never in the overlay shape (the first screen would jump straight to the detail).
- Breadcrumb: route segments (`useNavigation`) plus a record segment (last position, no `to`, click clears the selection) whose label updates when data arrives.

### D7 Feedback, empty and error states

- Four channels: **inline** (field errors, in-pane empty/error), **toast** (write success/failure; one toast on success, failure keeps copyable detail), **banner/alert** (page-level scope such as identity visibility), **modal** (destructive confirmation, unsaved confirmation).
- Optimistic updates only for **idempotent and reversible** actions (enable-disable, pin); on failure roll back to the old value with a toast — never reload the page.
- Upstream business codes must map to plain language (the `accountError.ts` pattern); never surface a raw upstream `message`.
- Every write shows a `pending` state (button `loading` + disabled) so it cannot be submitted twice.

### D8 Accessibility, keyboard and density

- Selection uses two channels (background + bar + `aria-selected`); tables use `UTable` semantics, lists may use `role="listbox"`/`option` — but must match the selection model. **List rows must be focusable** (`tabindex="0"`, `Enter`/`Space` selects, `aria-selected`); `UTable` rows are not focusable by default, so add keyboard bindings in the row slot or use a hand-rolled listbox in the list pane.
- Hit areas ≥ 44×44px on mobile, 32×32px for desktop toolbar icons; focus rings are never removed.
- Keyboard: `⌘/Ctrl+K` command palette (`UDashboardSearch` already wired), `⌘/Ctrl+Enter` submit, `Esc` cancel editing, `j/k` or `↑/↓` to move the selection (optional enhancement), `⌘/Ctrl+S` save.
- Density: `comfortable` (default, 48px rows) / `compact` (40px rows, still truncating past two lines), stored in `useUserPreferences`, never switched automatically by breakpoint.

### D9 Forward-looking slots (not implemented here)

- **Offline drafts**: Tauri/mobile keeps `edit` drafts locally (`useStorage`) and offers "restore your unsent changes".
- **Collaboration hints**: a per-`?id` "someone else is editing" slot, without a realtime channel for now.
- **AI slot**: one reserved `ghost` icon button at the far right of the D toolbar for "fill this form from natural language"; it never affects the layout.
- **Command palette actions**: M/D toolbar actions also register with `UDashboardSearch` so keyboard users need not hunt for buttons.
- **Layout memory**: the list-pane width persists per "page id + pane name" in `localStorage` (debounced write, double-click reset) across sessions; collapsed state is not stored (this baseline has no collapse affordance).

## 3. Consequences

- **Code**: new `app/components/Layout/Split.vue` (`#list` / `#detail` → `[data-pane="list"|"detail"]`, `@container` two shapes, draggable list pane, double-click reset, overlay Back); new `usePaneResize.ts` (pointer events + rAF + debounced `localStorage` + keyboard), `useRecordSelection.ts` (`?id` contract + membership test), `useRecordDraft.ts` (`view/edit/create` + `isDirty` + `requestSwitch`), `useRecordContext.ts` (display name / subtitle / breadcrumb record segment); `AppToolbar.vue` + `default.vue` gain `#app-toolbar-left|right` mount points and a single `--app-toolbar-h`; `usePageToolbar.ts` is deleted (no consumers). **Height contract**: outside `bigscreen` the content container changes from `min-h-full` to `flex min-h-0 flex-1 flex-col` and the page root to `flex-1 min-h-0` — without it the two-pane shape only works under `bigscreen`. First case: `/system/user` moves from "single column + modals" to two panes, with `AccountCreateModal` becoming the detail pane's `create` form (reason recorded in `NMCPS-DESIGN-005`).
- **Docs**: `NMCPS-ARCH-006` becomes the norm (condensed D1–D9 + anti-patterns + acceptance); each `NMCPS-DESIGN-00x` carries only its own fields and exceptions; `NMCPS-GOV-003` already registers this ADR.
- **Behaviour**: actions move from card headers and modals into the two toolbar levels; the selection lives in the URL, so it is shareable and refresh-safe; `bigscreen` no longer shows double scrollbars from page-local grids; a 1024px window with the sidebar expanded (768px of content) takes the overlay shape instead of a malformed two-pane split.
- **Risks**: (1) `UDashboardPanel` cannot serve two panes (`min-h-svh`, `lg:` breakpoints, cookie sizing) — `Split.vue` must be hand-rolled or the `bigscreen` double scrollbars return; (2) list-pane widths are remembered per `localStorage` key, so a duplicated key shares one width across pages; (3) `check:ui` needs assertions per shape × minimum width, and any count change must be synced in the script summary and `NMCPS-ARCH-006` §7.

## 4. Rejected alternatives

| Alternative | Why rejected |
| :--- | :--- |
| One global toolbar holding every action (this ADR's own first draft) | 1.0's `device.vue` already uses pane toolbars, and a single level breaks "search filters the left pane, save saves the right"; once the left holds filters, the right grows to 6–8 buttons (`system/user.vue` shows exactly that) |
| **A permanent third pane (related column, always on / collapsible)** | Three pieces of evidence say no: (1) only 1 of 61 pages has a table and `/system/user` has just 3 endpoints with no related data, so the third column stays an empty shell; (2) three panes need ≥ 80rem, which a 1366px default window (1110px with the sidebar expanded) cannot give — it degrades to "two panes + whitespace"; (3) the benefit (one saved click) is dwarfed by the cost (an extra breakpoint, an extra collapse rule, and `UDashboardPanel` has no `collapsible`). **Rejected, so related data moves into detail-pane sections (D4) and the shape count drops from 3 to 2** |
| Percentages for three panes and fixed widths for two (the first draft's hybrid) | Two sizing semantics in one component, plus a one-directional collapse order, encodes "how many panes right now" into three tables; after the two-pane change only one draggable dimension remains |
| Copy 1.0: the D pane is editable by default | The dirty flag is permanent and every switch prompts; "view" is forced to carry a write entry, maximising accidental edits |
| Copy 1.0: row `edit`/`delete` icon groups | Duplicate entry points, undersized touch targets, and two sources for "which row am I changing" |
| Detail in a `UModal` instead of a pane | No URL semantics, mutually exclusive with list scrolling, cannot host related sections; modals stay only for one-off forms that no record can anchor |
| Viewport breakpoints (`md:`/`lg:`) for the shape | Sidebar collapse (−12rem), the 1440px `topbar` cap and split-window narrowness all get it wrong; the threshold must read container width (`@container`) |
| Deriving `push` / `replace` from the device (`isMobile`) | Width varies on one device (window resizing, sidebar toggling), so the shape can change mid-session; history must follow the **current shape**, otherwise Back in a narrow desktop window jumps to the list instead of the previous record |
| A separate page or route for the overlay shape | Two implementations, two regression surfaces, and the `?id` contract maintained twice; two arrangements of one component cover both |
| Keep using `route.meta.breadcrumb` for the record segment | Route records are shared, writers overwrite each other, and labels leak after leaving the page |
| Keep `usePageToolbar()`'s module-level `shallowRef` and enable it | A module-level singleton: multiple instances on one page overwrite each other's writes (the project runs `ssr: false`, so cross-request sharing is not a factor), and it forces an extra SFC just for actions |
| Four independent layouts (one page per mode) | Four regressions, and switching modes rebuilds components, losing selection and scroll |

## 5. Migration steps

1. **Mechanism layer (zero UI change)**: height contract (`default.vue` content container `flex min-h-0 flex-1 flex-col` + page root `flex-1 min-h-0`), toolbar mount points, a single `--app-toolbar-h`, delete `usePageToolbar.ts`; `check:ui` stays at 70/70.
2. **Selection and record context**: the `?id` contract, the membership test, the derived record segment, and an "absent from the current result set" empty-state case.
3. **Split primitive**: `Layout/Split.vue` + `@container` two shapes + `usePaneResize`, verified with placeholder content at 320 / 768 / 1024 / 1366 / 1440 / 1920.
4. **First case**: `/system/user` two panes on desktop, overlay when narrow, tightening row actions and a default selection that shares the list's sort key; the `edit` state and the dirty guard stay **parked** (no upstream `PUT`).
5. **Backfill**: three `/system/user` cases in `check:ui` (including minimum width and shape switching), syncing the script summary and `NMCPS-ARCH-006` §7.

## 6. Acceptance

- Six container widths (320 / 768 / 1024 / 1366 / 1440 / 1920): `!isMobile` and ≥ 56rem → two panes, otherwise overlay; **no horizontal scroll and no nested scrollbars at any width**.
- At 320px `--page-min-w` holds: the list's primary action stays visible and the toolbar folds into `⋯` instead of wrapping.
- Two panes: detail ≥ 32rem; list draggable 18–28rem; double-click resets to 22rem; the width survives a reload.
- Overlay: tapping a row `push`es, and both the system/browser Back and the toolbar's Back return to the list; two panes render no Back button and a row switch adds no history entry.
- Row actions ≤ 1 and never duplicated in a toolbar; ≤ 1 primary per page; the overlay shape renders one toolbar level only.
- Switching rows in `edit` raises the unsaved prompt (Stay focused); switching in `view` raises nothing.
- The default selection equals the first list row (same `sortKey`); the overlay shape never defaults.
- An `?id` outside the current result set shows the detail empty state plus "clear selection", with **zero detail requests**.
- With a record selected the breadcrumb gains a last record segment that clears the selection on click; an `?id` deep link selects it without moving the list scroll position.
- No nested master-detail in the detail pane: related tables only link out via "view all", never an embedded list → detail.
- `rg 'usePageToolbar'` returns zero hits in code (historical docs only).

## 7. Follow-up record

### 7.1 2026-11-01: three panes collapsed into two (list / detail)

- **Changed**: D1 goes from "M/D/R three panes with a collapse order" to "two panes with an overlay fallback"; D4 goes from "R pane (third column)" to "related sections inside the detail pane"; **minimum page width** constants added (`--page-min-w` 20rem, `--split-min-w` 56rem, detail ≥ 32rem); D6 derives history behaviour from the **shape** (two panes `replace` / overlay `push`) instead of the device; D5 gains "the overlay renders one toolbar level" and `--app-toolbar-h` as a single source.
- **Evidence**: (1) `/system/user` has only 3 endpoints (list / create / status) and no related endpoint, so the third column had nothing to show; (2) the first draft's 80rem three-pane threshold conflicts with a 1366px default window (1110px of content with the sidebar expanded), so the third column never appeared in practice; (3) `UDashboardPanel` has no `collapsible`, sizes itself with percentages and cookies, and its theme carries `min-h-svh` plus `lg:` viewport breakpoints — self-contradictory with this ADR's "no viewport breakpoints" rule.
- **Cost**: related information drops from "always-visible third column" to "visible by scrolling the detail pane", so wide record pages scroll once more; a wide detail pane needs `max-w` on the form or it stretches.
- **No-rollback clause**: if a future domain needs related data that genuinely requires its own list + detail, make it a standalone page reached from the related table's "view all" — **do not restore the third column**.

### 7.2 2026-11-01: D5 goes from two levels to one layer split left/right

- **Changed**: the L0 / L1 layering of 0.2.0 is reverted — the reserved `AppToolbar` is the only layer, collection actions inject into `#app-toolbar-left`, record / submit actions and the primary CTA into `#app-toolbar-right`; panes no longer render a header; overlay and two panes share that layer and switch its content with the current panel; the record title (display name + code) moves to the top of the detail pane's content area; "Back" is injected by the page into the left area.
- **Evidence**: (1) two levels always stack into two 49px rows on a narrow window (98px of a 600px viewport), while on a real `/system/user` the reserved top toolbar was permanently **empty** — actions lived in the pane header and the reserved bar idled, which is exactly the "why aren't the buttons in the toolbar" question a reviewer asked; (2) teleported content is not a reactive child of `AppToolbar`, so no `computed` can detect emptiness — only a `MutationObserver` on the mount points makes "collapse when there is nothing to show" work; (3) left/right placement already expresses scope, and the pane header added no information, only a second copy of the same buttons.
- **Cost**: the record title loses its dedicated 49px row (it becomes a content title) and "the search box sits right above the list it filters" weakens — compensated by the left area aligning with the list pane.
- **No-rollback clause**: if a page truly needs its own in-pane control row (a multi-column filter panel, say), first check whether it fits in a fold-out menu in the right area — **do not restore a second 49px toolbar row**.

### 7.3 2026-11-01: single render site for the toolbar (fixes "actions vanish in sidebar mode")

- **Changed**: `app/layouts/default.vue` used to render `AppToolbar` twice by mode (`v-if="isBigscreenMode"` inside the scroll container, `v-if="!isBigscreenMode"` outside it). It now renders **once for every mode, outside the scroll container**; `bigscreen`'s `sticky top-0` therefore becomes a harmless no-op and `--content-sticky-top` is always `0px`.
- **Evidence**: `<Teleport>` binds its target node at mount time. A layout-mode switch destroys and recreates the old mount point, leaving the page's injected content in a **detached subtree** — measured in sidebar mode as `bars=1, h=0, leftKids=0, rightKids=0`: the bar is there, the search box and every button are empty. This is unrelated to D5 of 0.2.0 — it is a render-site count problem, so only the layout changed and the toolbar contract did not.
- **Cost**: no UI cost; the layout layer loses the ability to tune the toolbar's position per mode (it never used it).
- **No-rollback clause**: **never** add a second `AppToolbar` render site for any mode. When a mode needs something different, change `AppToolbar`'s internal styling, not the number of render sites. The `check:ui` case "actions still mounted after switching to Sidebar" guards this.

## Appendix B: 1.0 → 2.0 deltas

| Item | 1.0 | 2.0 |
| :--- | :--- | :--- |
| Page shape | `system/user.vue` single column + modals; `device.vue` three panes | **unified two panes** (list / detail); overlay on narrow screens and mobile; no third pane |
| Minimum page width | none (each page props itself up) | `--page-min-w` 20rem / two-pane threshold `--split-min-w` 56rem |
| Toolbars | one page level (user) / two pane levels (device) | two fixed levels: L0 breadcrumb + global, L1 collection / record / submit; the overlay keeps one level |
| Row actions | edit + delete icon group | ≤ 1, writes move up |
| Detail editing | permanently editable | view → edit → create |
| Selection | component ref, lost on refresh | `?id`, shareable and refresh-safe |
| Paste / back | no URL semantics | `replace` in two panes / `push` in the overlay (by shape, not by device) |
| Default selection | page-local (once with a mismatched sort key) | on in two panes, one `sortKey` + a once-only settled flag |
| Breadcrumb record segment | `route.meta.breadcrumb` patch | derived from the record context |
| Split implementation | page-local `grid-cols-12` / `UDashboardPanel` | `Layout/Split.vue` primitive + `@container` + `usePaneResize` |
| Related info | R pane in `device.vue` (third column) | **fixed sections inside the detail pane** (overview → related tables → activity), ≤ 2 tables |
| Empty states | page-local (`hidden lg:flex` block) | unified in-pane empty + primary CTA |

## Appendix C: industry comparison and trade-offs

| Reference | Adopted | Not adopted |
| :--- | :--- | :--- |
| SAP Fiori **List Report + Object Page** floorplan | list toolbar (filters + bulk + count) separated from the object-page header (title + actions + save/cancel); draft-state switch guard | elaborate filter-bar popovers (few filter fields here, inline is enough) |
| Material 3 **canonical list-detail** | the supporting-pane → two-pane ladder (our 56rem threshold) with the overlay as the narrow fallback | folding panes into labels/tabs (collides with breadcrumbs) |
| Apple HIG **split view** | fixed sidebar width of 320–375pt (our 20–24rem list pane) | three panes plus an overlay sidebar on mobile |
| Azure Portal / AWS Console | draggable divider, remembered width (only one draggable dimension here) | a multi-level "service drawer" navigation |
| Ant Design Pro `ProTable` + drawer detail | bulk actions with counts, column settings | a drawer for the detail (no URL semantics) |
| Carbon **data table + side panel** | side panel 16–24rem, read-only related info as a **reference** | a permanent side panel as a **third column**, or one hosting the main form — no data source here, so the third column is an empty shell (see "Rejected alternatives") |
| Forward-looking: command palette / optimistic UI / offline drafts / AI slot | reserved in D9 | realtime collaboration (slot only) |

> Trade-off principle: **never add a level when one level will do.** The industry pattern of mixing drawer detail + modal editing + split detail is rejected outright — this repository has few pages, and consistency pays more than flexibility.
