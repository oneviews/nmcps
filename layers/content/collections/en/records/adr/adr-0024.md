# ADR-0024: Controller-less switches default to standalone (lab connectivity)

## 1. Context (measured)

Measured 2026-11-17: 8 hosts / 7 OVS switches / 14 links upstream, `POST /pingall` reported **100% packet loss** and `iperf` moved no throughput. The ledger and the canvas were both correct — the topology was drawn right and simply carried no traffic.

The root cause sits in the data plane, not in the ledger (a missing manifest entry is `NMCPS-ADR-0023` (`layers/content/collections/en/records/adr/adr-0023.md`)):

- Mininet's `OVSSwitch` defaults to `failMode='secure'`. In secure mode, a switch with **no connected controller** has no flows and no NORMAL fallback, so every received frame is dropped.
- Switches created through the BFF always carry `controller: null` (`layers/scenario/shared/types/labNodes.ts` maps the draft that way), so `POST /start` calls `switch.start([])` — secure mode with zero controllers, i.e. guaranteed 100% loss.
- The legacy frontend worked because it associated a controller (Ryu / reference controller) before starting the network; the new UI has no association entry yet.

## 2. Decision

Derive the fail mode from the **controller association**; no new field, no new endpoint, no permission change:

- `switch_fail_mode(controller)`: with a controller → `secure`; without one → `standalone`.
- Applied in three places:
  1. `add_switch_to_net()`: all four OVS variants (`OVSSwitch` / `OVSKernelSwitch` / `OVSBridge` / default) receive `failMode` at creation.
  2. `POST /start`: re-apply `failMode` from the current association before starting the switch, because a switch may be associated after creation or changed while the network is stopped.
  3. `POST /associate_switch`: set `secure` before restarting the switch with its new controller.
- `schema.py::Switch.format_switch()` emits the same `failMode`, so an exported script behaves like the live network.

Explicitly not doing:

- **No controller process is started automatically.** That would need `ryu` / `pox` or similar, and a missing install would disguise "no controller" as "controller failed to start" — worse to diagnose than the current state.
- **No change to `POST /flows` semantics.** OVS refuses flow mods on a standalone switch; that error is returned verbatim (400 with the `ovs-ofctl` text) rather than swallowed or turned into a 200.

## 3. Consequences

- A controller-less lab network **works out of the box**: standalone is a classic learning switch, so `pingall` no longer loses everything.
- Networks with an associated controller stay secure: OpenFlow rules (`flow_rules.py`) keep taking effect and an L2-learning controller such as `simple_switch_13` forwards normally.
- Limitations, documented rather than hidden: a standalone switch ignores OpenFlow rules, so "programmed plus flow-table writes" requires associating a controller first; loops between switches get no STP in standalone mode and still need a controller or topology planning.
- Permissions, audit and tenant boundaries are untouched: this is a data-plane default in the upstream service, it never passes through the BFF and it widens no visibility.

## 4. Acceptance

- `pnpm lab:check` gains three static assertions: the `switch_fail_mode()` mapping, `failMode` on all four OVS branches of `add_switch_to_net()`, and `Switch.format_switch()` changing with `controller`. None needs root or creates a Mininet network.
- `pnpm check:lab-bff` / `pnpm check:ui` use a fake upstream and do not cover the real data plane; they only need to stay green (they verify the BFF and the page, not OVS).
- On a real host (root + Mininet, manual): 2 hosts + 1 switch → `POST /start` → `GET /pingall` should report 0% loss; then `POST /associate_switch` to a controller → `pingall` still passes and `POST /flows` succeeds.
