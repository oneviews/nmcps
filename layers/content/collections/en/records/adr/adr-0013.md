# ADR-0013: Unify the Sign-in Page Naming on login and Pre-fill Demo Seed Accounts

> **Tier**: Tier 5 record layer — the body is append-only; changes require a new ADR and a `supersededBy` entry.

- **Context**:
  - **One action, two words**: the auth page was `app/pages/auth/sign-in.vue` (route `/auth/sign-in`), yet the same action is called `login` everywhere else — the BFF endpoint `/api/auth/login`, the server route `server/api/auth/login.post.ts`, the composable `useAuth().login()`, and the body of `NMCPS-ARCH-003` §7. Searching for `login` misses the page itself; searching for `sign-in` only finds the UI side.
  - **The file naming rule was already noun-based**: every other page file is a noun in kebab-case (`overview` / `security` / `plan-generation` / `auto-transmit`), while `sign-in` is a verb phrase and breaks the "page = resource" semantics.
  - **A demo program must be loggable out of the box**: the form started empty, so every demo and screen recording needed the credentials typed by hand, and both identities had to be shown — the **super admin** and the **tenant admin** (`accountLevel` `0` / `1`).
- **Decision**:
  1. **Rename the page and route to `login`**: `app/pages/auth/login.vue` → `/auth/login`. No `sign-in` alias redirect: the allowlist is already `/auth/**`, the old path has no external referrers, and an alias would keep two vocabularies alive.
  2. **Unify the term in source**: the i18n key `auth.signIn` becomes `auth.login`; comments, scripts and documents all say `/auth/login`. The historical `NMCPS-ADR-0011` keeps its body untouched per the record-layer rule, while `NMCPS-ADR-0012` lands in the same uncommitted batch and has its path reference corrected here.
  3. **Single source for seed accounts**: new `shared/constants/demoAccounts.ts` exporting `DEMO_ACCOUNTS` (super admin / tenant admin); the page consumes it and never hard-codes credentials.
  4. **Pre-fill by default, switch in one click**: the initial state is the first seed account (super admin); the "demo identity" buttons refill `accountName` / `password` / `tenantCode` as a set, and the fields stay editable (a real MFA account is not locked out).
  5. **Demo-only boundary**: the prefill serves demos and recordings; before a real deployment the constants must be checked against the upstream IAM seed script, or the prefill removed.
- **Consequences**:
  - `/auth/sign-in` no longer exists; `app/middleware/auth.global.ts`, `app/components/App/AppHeader.vue`, the assertions in `scripts/check-ui.mjs` and `NMCPS-ARCH-003` §7.4 / §7.6 are updated with it.
  - `NMCPS-ARCH-003` gains §7.7 to pin down the demo-seed and prefill behaviour; the login flow itself is unchanged (still `POST /api/auth/login`, the guard still judges by `/api/auth/session`).
  - The login page goes from "empty form" to "prefilled + switchable", so `check:ui` must clear the fields before asserting the empty-submit validation.
- **Seed values verified (owner-specified + 2026-10-31 probe, closes the earlier open item)**: the login API is `POST http://192.168.1.55:8888/api/v1/auth/login`; the seed accounts are `admin / Admin@123456` (super admin) and `tenantadmin / Tenant@123456` (tenant admin), both returning `code: 0` in the probe. The seeds carry no tenant code — upstream resolves the tenant from the account, so an empty `tenantCode` logs in fine (`GET /api/v1/tenant` shows the built-in default tenant code `default`, used only when a tenant must be selected explicitly). The earlier constants (`tenant / Admin@123456 / demo`) were wrong on all three values (probe returned `20201 账号或口令错误`) and are corrected; passwords still live in `shared/constants/demoAccounts.ts` only.
- **Generation switch (2026-11-04)**: the login path `POST /api/v1/auth/login` and the `tenantCode` prefill above belong to the old upstream; the new endpoint is `POST /api/v1/iam/login` (takes `username`, no tenant code), so the three prefilled values collapse to account + password. The seed accounts and passwords are unchanged; the decision lives in `NMCPS-ADR-0018` (`layers/content/collections/cn/records/adr/adr-0018.md`).
- **Default password update (2026-11-16)**: at the requester's instruction the tenant admin `tenantadmin` moves from `Tenant@123456` to `admin_2026`; the super admin `admin` / `Admin@123456` is unchanged. This amends the "passwords are unchanged" wording above: `shared/constants/demoAccounts.ts` remains the single source of truth, and the `check:ui` prefill assertion plus `NMCPS-ARCH-003` §7.7 (0.8.1) were updated in the same batch. If the upstream IAM account is not changed in step, the prefilled value is only the demo default and real logins still follow the upstream account.

- **The lab operator appears only behind a demo switch (2026-11-18)**: a local demo needs an account that can walk straight into `/scenario/simulator` (the fake upstream's `alice` / `p@ssw0rd`, holding `lab:create` / `lab:operate` / `lab:read` / `lab:sniffer` / `lab:terminal` at once), but it is not upstream seed data — the real IAM has no lab role for it (see the AssignRole defect section of `docs/ai/lab-boundary.md`). Hence the new demo switch `NUXT_PUBLIC_DEMO_LAB_OPERATOR` (`runtimeConfig.public.demoLabOperator`, default `false`): with `true` the login page gains a "Lab operator" button and prefills `alice`; with `false` the button is not rendered and the prefill falls back to the super admin `admin`. The selectors live in the constants file (`demoAccountsFor()` / `defaultDemoAccountFor()`); the page only reads the switch — offering a button for an account the real environment cannot log in only teaches users that "the local demo account" means "the production account is broken".
  **Addendum 2026-11-18: `alice` now exists in the real IAM.** It was created with `POST /api/iam/users` on `192.168.1.55:8888` (`department_id = dept_default_ops` → tenant `tnt_default`, password `p@ssw0rd`, id `a6541d3f-7880-4bb9-8917-5338d78e6925`), and both `POST /api/v1/iam/login` and the BFF `/api/auth/login` answer 200 with `tenantId = tnt_default`. The local `.env` with `NUXT_PUBLIC_DEMO_LAB_OPERATOR=true` therefore points at an account that really signs in. Its roles were missing at first (`lab_terminal` existed but `lab_sniffer` did not, and `AssignRole` stored a `NULL` relation `tenant_id` that tenant-scoped reads never returned — evidence in `docs/handoff/iam-assignrole-report-2026-11-18.md`), so `GET /api/lab/channel` answered `read: true` only. **The upstream fix on 2026-11-18 closed the loop**: a freshly assigned `lab_terminal` row carries `tenant_id = tnt_default` and reads back (20 relation rows in total, zero with a null tenant), `GET /api/lab/channel` for alice now says `terminal: true` (with `create` / `operate` / `delete` still `false`), the rail grew from logs / monitor / network to logs / monitor / network / Webshell, and a live session on `h1` returned `root@h1:…$` and ran `id` → `uid=0(root)`. In the same round `lab_sniffer` (`bcadd871-d4f2-40f5-9ac6-1c4ad28e096f`) was created and assigned too: with `sniffer: true` the rail gains reachability, which carries the capture readout only (the start / stop menu was measured pushing upstream `sniffer/state` to `active: true` with the stream turning live, then back to `false`), while the probe button still never appears (`lab:operate` is not granted) — the two-way proof that the capability flags never imply one another. Check that a new upstream instance actually has `alice` before leaving the switch on.

- **Prerequisite for any login (surfaced by the same probe)**: the repository ships `.env.example` but no `.env`, so `NUXT_BFF_UPSTREAM_BASE` is empty and the BFF answers the auth routes with 503 — no seed account can log in. "Seed data cannot log in" is therefore an unconfigured upstream first, not a credential problem. A local `.env` has been filled in (ignored by `.gitignore`, never committed).
- **Rejected alternatives**:
  - **Keep `/auth/sign-in` and add an `/auth/login` alias**: two vocabularies survive, `grep` still misses one of them, and a redirect has to be maintained.
  - **Use `auth/index.vue` (`/auth`) instead of `login.vue`**: the URL loses its action semantics, and `/auth` would be allowed "by accident" through the `/auth/**` prefix without explaining itself.
  - **Put the seed accounts in `.env` / runtimeConfig**: a demo build would need deployment configuration, and the passwords would leak into build metadata; a constants file is reviewable and changed in one place.
  - **Only document the seeds, never prefill**: demos and recordings still need typing, so the "prefilled by default" requirement is not met.

- **Demo accounts ↔ lab capability tiers (2026-11-19, companion to the `NMCPS-ADR-0022` replication acceptance)**: the three demo accounts deliberately cover three **non-implying** capability combinations, so that "capabilities come from the session and never imply one another" (`NMCPS-ADR-0021` D3) can be checked by hand. The `alice` row is measured (evidence below); the `admin` / `tenantadmin` rows are role **design intent** and every cell is checked against this same table during acceptance.

  | Account | Password | Role | `read` | `create` | `operate` | `delete` | `terminal` | `sniffer` | Notes |
  | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
  | `admin` | `Admin@123456` | Super admin | ✅ | ✅ | ✅ | ✅ | ❌ | ❌ | Global management account; lab capabilities still come from the tenant's roles, never from being super admin |
  | `tenantadmin` | `admin_2026` | Tenant admin | ✅ | ✅ | ✅ | ✅ | ❌ | ❌ | Demonstrates "can edit the topology, cannot enter a terminal": no Webshell in the rail, no capture readout |
  | `alice` | `p@ssw0rd` | Lab operator | ✅ | ❌ | ❌ | ❌ | ✅ | ✅ | Demonstrates "can look and connect, cannot edit": Webshell and capture work; probe, drag and add / delete are not rendered at all |

  `alice`'s tier is **measured**: `GET /api/lab/channel` answered `{ read: true, terminal: true, sniffer: true, create: false, operate: false, delete: false }`, so the rail shows five tabs (Webshell / Logs / Monitor / Network / Reachability), and Reachability carries only the capture readout and the live packet list — the probe button never appears because it needs `lab:operate`. That combination proves two things at once: neither `lab:terminal` nor `lab:sniffer` is derived from `lab:read`, and `lab:sniffer` is not derived from `lab:operate` either (`tenantadmin` has `operate` but no capture readout). Check that a new upstream instance actually has all three accounts, and turn off the demo entry for whichever one is missing.
