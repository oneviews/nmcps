# ADR-0011: `/api/v1/auth` Integration and Token Rotation

> **Layer**: Tier 5 record layer — the body is append-only; changes require a new ADR with `supersededBy`.
>
> **Relation to 0009**: this ADR **succeeds and supersedes** `NMCPS-ADR-0009` (0009 now carries `supersededBy: NMCPS-ADR-0011`). All four of its conclusions survive — HttpOnly cookies for the web, Bearer for the desktop, tokens issued only by the BFF, auth endpoints excluded from `GATEWAY_RESOURCES`. What is replaced is the interface-level detail it never covered: route names, refresh semantics, logout idempotency, and the error envelope fields.
>
> **Source of truth**: `http://192.168.1.55:10000/swagger/specs/auth.json` (backend OpenAPI) plus probes against the same instance on 2026-10-31 (seed accounts `admin` / `tenantadmin`).

- **Context**:
  1. `NMCPS-ADR-0009` decisions 1–3 only shape the session model (cookie pair + desktop Bearer + a single upstream `Authorization`), and decision 7 merely states that login / refresh / logout are explicit BFF routes without landing any of them; the repo still has no `/api/auth/*` and no `useAuth`, so authentication was not actually usable.
  2. The new backend converged auth from v1's `/iam/login` onto six `/api/v1/auth/*` endpoints and added a **refresh token** and a **session id** that v1 never had: `login` returns `accessToken` / `refreshToken` / `sessionId`, and `whoami` echoes `sessionId`.
  3. Three observed behaviours change the implementation strategy:
     - **Refresh rotates**: after `token/refresh` the `sessionId` changes and **the previous access token is dead** (old AT → `whoami` 401). Any "refresh ahead of `expiresIn`" or "keep using the old token while refreshing" strategy knocks the user out.
     - **Logout is not idempotent**: a second `logout` with the same token returns 401 `10201`, while logout is a high-frequency UI action (multiple tabs, double click, expired token); passing that through turns a successful logout into an error banner.
     - **Errors use `msg`**: the failure body is `{code,msg,traceId}` with no `message`, and `code` is a **business code** (20201, 20205) rather than the HTTP status; the `ApiResponse` normalisation landed by `NMCPS-ADR-0007` reads `message` and assumes `code === HTTP status`, flattening "wrong password" into `401 unauthorized`.
  4. Two more details: `login` does **not** return `accountName` / `displayName` / `mfaEnabled` (only `accountCode`), so the login payload alone cannot build a complete user; a login with missing fields or an empty body returns **500 `10509`** (internal error) because upstream validation is incomplete, and the BFF should not surface that as a real outage.
  5. Registering `/api/auth/*` in `GATEWAY_RESOURCES` would make it collide with the generic proxy in `server/api/[...slug].ts`, which is stateless and cannot write cookies.

- **Decision**:
  1. **Dedicated BFF auth routes, not on the whitelist**: add `POST /api/auth/login`, `POST /api/auth/refresh`, `POST /api/auth/logout`, `GET /api/auth/session`, `POST /api/auth/mfa/bind`, `POST /api/auth/mfa/confirm`, `POST /api/auth/password` under `server/api/auth/`, all implemented through `server/utils/bff/auth.ts`. `/api/auth/*` is **not** added to `GATEWAY_RESOURCES`, so it cannot collide with `[...slug].ts`.
  2. **Two cookies for the web**: `nmcps_at` (access token, `Path=/`) and `nmcps_rt` (refresh token, `Path=/api/auth`), both `HttpOnly` / `SameSite=Lax` / `Secure` (production or HTTPS). `Max-Age` for the access cookie follows upstream `expiresIn`; the refresh cookie uses `bff.refreshTtlMs` (default 7 days, matching the observed upstream JWT expiry — upstream **does not** return a refresh TTL, so a configured fallback is the only option).
  3. **Tokens echoed for the desktop**: with `x-nmcps-client: desktop`, `login` / `refresh` return `data.tokens` = `{accessToken, refreshToken, expiresIn, sessionId}` for `useAuthTokens()` to persist in `tauri-plugin-store`; no cookies are set and tokens never leak into logs or HTML. The client marker only selects the **response shape**; authentication remains "explicit `Authorization` first, cookie second".
  4. **Refresh lazily, single-flight, on 401 only**: because of the rotation behaviour above, the client must **not** refresh ahead of `expiresIn`. On a 401 with a refresh token available, `useApi` performs one shared (module-level promise) call to `/api/auth/refresh` and replays the original request once; a failed refresh clears the session and sends the user to the sign-in page. `/api/auth/*` never participates in this retry, which avoids recursion.
  5. **Login enriches the user**: after a successful login the BFF immediately calls upstream `whoami` with the fresh token to obtain the authoritative user (`displayName` / `mfaEnabled` only live there). If `whoami` fails it degrades to the login fields with `displayName: null` — the contract forbids faking truth, so `accountName` is not reused as a display name.
  6. **`/api/auth/session` is the single source of session truth**: the web cannot read the cookies back (`HttpOnly` exists for exactly that reason), so only the BFF can call `whoami`. An upstream 401 becomes **HTTP 200** with `{authenticated:false, user:null}`, making "not signed in" a normal SPA startup branch instead of a console error; other upstream failures are reported through the envelope as usual.
  7. **Logout is immune to upstream failures**: read the token (cookie or explicit header) → call upstream `logout` (**empty body + `application/x-www-form-urlencoded`**; a JSON body is rejected) → regardless of 200 / 401 / timeout, clear the cookies and return `{ok:true}`. Non-401 upstream failures are mirrored into `x-nmcps-logout-upstream` for diagnostics but never become business failures.
  8. **CSRF by same-origin check**: for cookie-mode unsafe verbs (POST without an explicit `Authorization`), validate `Origin` — same origin as the request `Host` passes, otherwise it must hit `bff.allowedOrigins`, otherwise 403 `bff_csrf_rejected`. A missing `Origin` is rejected (browsers always send it for unsafe verbs). This keeps LAN-IP development working without per-host allowlists while still blocking cross-site forgery. `login` carries no cookie to abuse and skips the check.
  9. **Validate input first**: `login` / `refresh` / `mfa/*` / `password` validate required fields with zod and answer 400 `bff_invalid_body` when they are missing, keeping upstream's 500 `10509` outside the contract (an upstream 5xx is a defect, not a contract).
  10. **Gateway normalisation picks up `msg` and business codes**: `server/utils/bff/proxy.ts` falls back to `msg` when `message` is absent, and for non-2xx responses keeps the upstream business code when it is `> 599`, otherwise preserving HTTP semantics (the `NMCPS-ADR-0007` convention `code === HTTP status` still holds; `>599` can never collide with a status). `useApi` can then distinguish "wrong password", "session expired", and "unauthenticated" via `ApiError.code`.
  11. **`x-nmcps-client` joins the CORS allowlist**: `server/middleware/cors.ts` adds the header to `Access-Control-Allow-Headers`, otherwise the desktop preflight fails.

- **Consequences**:
  - New: `server/api/auth/{login,refresh,logout,password}.post.ts`, `server/api/auth/session.get.ts`, `server/api/auth/mfa/{bind,confirm}.post.ts`, `server/utils/bff/auth.ts`, `shared/types/auth.ts`.
  - Changed: `server/utils/bff/{proxy,config}.ts` (msg / business-code normalisation, `accessTtlMs` / `refreshTtlMs` / cookie names), `server/middleware/cors.ts`, `app/composables/useApi.ts` (single-flight refresh, desktop token injection, `x-nmcps-client`).
  - New client code: `app/composables/useAuth.ts`, `app/composables/useAuthTokens.ts`, `app/middleware/auth.ts`, `app/pages/auth/sign-in.vue`; the `AppHeader` user menu gains sign-in / sign-out, and `i18n/locales/{cn,en}.json` gains `auth.*` keys.
  - `.env.example` documents `NUXT_BFF_ACCESS_TTL_MS`, `NUXT_BFF_REFRESH_TTL_MS`, `NUXT_BFF_ACCESS_COOKIE`, `NUXT_BFF_REFRESH_COOKIE`.
  - `scripts/check-bff.mjs` gains an auth group: login sets both cookies and leaks no token in the body, `x-nmcps-client: desktop` echoes tokens, a repeated logout still returns 200, `/api/auth/session` returns 200 with `authenticated:false` when signed out, a cookie-mode POST from a cross-site `Origin` is 403, and upstream `msg` / business codes are normalised.

- **Alternatives (rejected)**:
  - **Call `/api/v1/auth` straight from the browser**: tokens would live somewhere JS can read (localStorage), so any XSS steals them, and the BFF's CSRF and input validation are bypassed.
  - **Keep the "refresh ahead of `expiresIn`" idea**: it contradicts the observed rotation — refreshing while other requests are in flight kills their still-valid-but-now-old access token.
  - **Propagate upstream's 401 on logout**: the user sees "logout failed" while the local cookie is already cleared, so the UI and the state disagree.
  - **Flatten business codes into HTTP statuses**: the UI can no longer tell "wrong password" from "session expired" and can only say "please sign in again", which makes sign-in error messages useless.
  - **Use `accountName` as `displayName`**: violates the `NMCPS-CONTRACT-001` rule "unknown is `null`, never fake truth".
  - **Route `/api/auth/*` through the `GATEWAY_RESOURCES` whitelist**: the generic proxy is stateless, cannot set or clear cookies, and the path would race `[...slug].ts` for the same match.

- **Open items**:
  - Whether `password` invalidates the current session immediately is untested (changing a password would poison the seed accounts); the client re-reads the session after a successful change and redirects to sign-in on 401 rather than assuming an outcome.
  - The `mustResetPassword` / `firstReset` flow (forced password change on first login) has no UI yet.
  - MFA only lands the `mfa/bind` + `mfa/confirm` API layer; QR rendering and recovery codes are not implemented.
  - The sign-in guard is now global (`NMCPS-ARCH-003` §7.6): outside the landing page `/` and `/auth/**`, an anonymous visit is pushed to the sign-in page with its original target; the inline guide state remains a fallback only.
  - Multi-tab logout synchronisation (`BroadcastChannel`) is not handled; web sessions are cleared server-side, so only the desktop build is affected.
