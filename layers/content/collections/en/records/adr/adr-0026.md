# ADR-0026: long-operation egress budgets and ledger state reconciliation

> **Layer**: Tier 5, the record layer — published text is append-only; corrections arrive as a new `##` section, never by rewriting a published conclusion.
> **Relationship to ADR-0022**: `NMCPS-ADR-0022` (`layers/content/collections/cn/records/adr/adr-0022.md`) W3 only answered "run controls render by capability bit, and the state is read from `GET /api/mininet/start`"; it never answered "how long may the browser, the BFF and the upstream each wait when one pingall outlives the egress budget", and never answered "when ledger `state` drifts from upstream run state, who corrects whom". Both gaps shipped as user-visible defects, so they are settled here.

## 1. Background (measured on the live instance)

On 2026-11-21 both defects were reproduced against a real backend (`127.0.0.1:8000`, nine nodes: one controller, one router, seven hosts):

- **"pingall / stop fail after start"**: `POST /api/mininet/pingall` takes **42.6 seconds** straight against the upstream, while the BFF egress timeout is `mininet.timeoutMs` (**15 seconds** default). The BFF aborts at 15s and answers `504 mininet_timeout`; the browser's `useApi` default of 20s has already elapsed too, so the page shows a failure with no body (`<no response> Failed to fetch`). **The upstream is still pinging at that moment.**
- **"stop crashes the backend"**: pressing "stop" inside that window makes `stop_network()` run `_stop_mininet_with_timeout()` immediately, tearing down node interfaces while `pingFull()` is iterating them; the upstream dies with `AttributeError: 'NoneType' object has no attribute 'IP'` (`mininet/node.py::IP`) — reproduction in §4.
- **"an imported topology shows running before it was ever started"**: the ledger `.data/lab-ledger.json` carried `state: "running"` (its seed value) while upstream `GET /api/mininet/start` answered `false`. The page renders its "network" readout from the ledger, so a network that was never started showed as running. The field was only written back after a successful `start` / `stop` / `full_reset` (`markLabNetworkState()`); a seed value, a process restart, or an external `mn -c` never triggers that write-back.

## 2. Decision

| ID | Decision | Rationale |
| :--- | :--- | :--- |
| **D1** | **Long endpoints get their own egress budget** | `MININET_LONG_OPERATION_TEMPLATES` (`layers/scenario/shared/constants/mininetRoutes.ts`) lists seven routes: `POST /start` `/stop` `/reset` `/full_reset` `/import_json` `/pingall` `/iperf`. Matches use `config.longTimeoutMs` (default 180000, overridable with `NUXT_MININET_LONG_TIMEOUT_MS`, per-instance `longTimeoutMs` allowed); every read endpoint keeps `timeoutMs` (15s). The list lives in a shared constant rather than a server util because the BFF and the browser need **the same** list; two copies drift. |
| **D2** | **The browser uses the same tier** | Page calls to those seven endpoints pass `timeoutMs: LAB_LONG_OPERATION_TIMEOUT_MS` explicitly (same value as D1). The 20s default keeps serving ordinary reads and writes: raising the global default would make a dead upstream hang reads for three minutes too. `<no response>` exists precisely because the client aborts before the BFF — the client budget must be ≥ the BFF budget, otherwise the user never sees the BFF's `504` or the upstream's own words. |
| **D3** | **Stop waits for a running test to finish** | Upstream `stop_network()` / `full_reset_network()` `await _await_idle_operations()` before tearing anything down: while `pingall_running` or `iperf_running` is true it polls every 200ms for up to 180 seconds, then **continues** stopping and logs with `info()` instead of blocking an operator forever. `pingFull()` cannot be cancelled (Mininet has no cancel hook), so waiting is the honest option: rebuilding the topology mid-iteration is the only path that produces the `AttributeError`. |
| **D4** | **Ledger `state` reconciles against upstream on the read path** | Before responding, `GET /api/mininet/networks` reads `GET /api/mininet/start` once per tenant that has an instance: `true` turns `stopped` into `running`, `false` turns `running` into `stopped` (only these two values; `creating` / `error` are never guessed). When the read fails, returns a non-boolean, or the tenant has no instance, **the stored value stands**. Writes go through `markLabNetworkState()` (still on the `enqueueWrite` chain); a failed write only logs and never breaks the list response. This completes the existing "the two states are not one source of truth" decision: both sources must still be individually correct, without waiting for an operator to press "reconcile". |
| **D5** | **Long operations are not turned into async jobs yet** | A pingall takes seconds to a minute; a job would add a task table, TTLs, cleanup and front-end polling, while D1+D2 already remove the false failure. Re-open triggers (any one): ① a single pingall regularly exceeds the budget cap (180s); ② an operation needs mid-flight progress or cancellation (e.g. a long `iperf` on a large topology); ③ queueing for the single instance becomes visible with more concurrent users. |

## 3. Blast radius and acceptance

- **Touched**: `mininetConfig.ts` (new field + env var), `mininet.ts` (`proxyToMininet()` picks the budget per route), `mininetRoutes.ts` (list + pure helper), the page (seven call sites pass the budget), `services/mininet-api/mininet_gui_backend/api.py` (`_await_idle_operations()`), `networks.get.ts` plus a new `labStateReconcile.ts`.
- **Machine assertions**: `pnpm check:lab-bff` ⑮ proves the split with "short budget 1.2s / long budget 3s + a 2s upstream delay": read endpoints answer 504, long endpoints answer 200. The same section pins the ledger reconciliation (ledger `running` + upstream `false` → the list answers `stopped`; a failed upstream read → the stored value stands). `pnpm lab:check` asserts both `stop_network` and `full_reset_network` await the idle wait. `pnpm check:ui` 11.3 keeps its ledger seed at `state: "running"` with the upstream at `false` and now expects "stopped" — that case *is* the "running before start" regression.
- **Live instance**: the pingall case of `pnpm check:lab-real` needs 40+ seconds against a real backend; before D1 it could only fail spuriously. Skipping it (no `CHECK_REAL_MININET`) still does not count as passed.

## 4. Reproduction record (2026-11-21)

```bash
# start the network, then probe upstream directly and press "stop" while it runs
curl -s -m 600 -X POST http://127.0.0.1:8000/api/mininet/pingall   # 42.6s / 200
curl -s -m 600 -X POST http://127.0.0.1:8000/api/mininet/stop      # 2.6s / 200, but the pingall thread died with:
#   File ".../mininet/node.py", line 573, in IP
#     return self.intf( intf ).IP()
#   AttributeError: 'NoneType' object has no attribute 'IP'
```

Ledger drift: `state` in `.data/lab-ledger.json` was `running` while
`curl -s http://127.0.0.1:8000/api/mininet/start` answered `false`.

## 5. D1 revision (2026-11-23): iperf runs its own subprocess with a hard timeout

**Symptom**: a `tenantadmin` session ran `POST /api/mininet/iperf` (`h1` → `h2`, TCP, 3 seconds) against the real backend and the
request **never came back — still pending after 120 seconds**. `app.iperf_running` stayed `True` and both hosts' shells were left
`waiting`. The next `POST /api/mininet/pingall` could not drive that shell and failed with `AssertionError` (`mininet/node.py:303`),
which the BFF surfaced as **500 plus a Python traceback**; `POST /stop` could only end it through the D3 guard (returned 200 after
**182.3 seconds**, log line `*** pingall/iperf still running after 180s`).

**Root cause**: the backend uses Debian's packaged mininet (`/usr/lib/python3/dist-packages`), whose `Mininet.iperf()` decides it is
done with `while len(re.findall('/sec', servout)) < 2` — the second `/sec` came from the rate line of the telnet connection that
`waitListening()` opens. Local `iperf 2.2.1` no longer prints a rate line for that zero-byte probe (reproduced in an isolated
`unshare -n` namespace: the server output holds exactly one `/sec` line plus `read tcp flags (peer close) failed`), so the loop
condition never becomes true and the endpoint waits forever.

**Decision (execution only — D1's budget tier is unchanged)**: upstream `run_iperf()` no longer calls `Net.iperf()`. It starts the
processes itself: `nsenter -t <host pid> -n iperf -s` for the server (a `Popen`, collected with SIGINT so iperf prints its report and
exits by itself) and `nsenter -t <host pid> -n timeout <t+20> iperf -c <server ip> -t <t>` for the client combined with
`subprocess.run(timeout=…)`. Readiness is probed with `ss` inside the server's own netns (`-ltn` for TCP, `-lun` for UDP —
protocol-agnostic and it opens no connection, so the server text no longer carries the `(null)…` /
`read tcp flags (peer close) failed` leftovers of the old `waitListening()` probe). Every path — exceptions included — collects
the server process in `finally` and resets `iperf_running`; a client timeout answers `504`, a non-zero exit without a rate line
answers `400` with the output tail instead of a traceback. The response is still `{ client, server }` as two text blobs, so the
rendering boundary (`NMCPS-ADR-0025`) is untouched.

**Acceptance**: consecutive calls on the real backend (`192.168.1.90:8000`, four hosts / two switches / one router) — `h1`→`h2`
TCP 3s came back in **4.4s** (28.3 Gbits/sec on both sides, no probe noise in the server text), `h1`→`h2` UDP 2s @10M came back in
**2.3s** (10.5 Mbits/sec), and `h2`→`h1` TCP 1s right after came back in **2.0s** (no 409, so the flag was reset); `pingall` then
answered normally (no more `AssertionError`) and no `iperf -s` process was left behind. `pnpm check:lab-real` gains a real iperf
case (19 items at the time, 21 since 2026-11-26) asserting 200 / `bits/sec` on both sides / completion within 60s / a second call right after still 200,
and `pnpm lab:check` gains static assertions (no `Net.iperf()` again; `Popen` + `subprocess.run` + the `iperf_running` reset must
stay) — CI runs the same assertions through `python3 scripts/check-mininet-api.py --source-only` (the `lab-api` step, zero
third-party dependencies), because a guard that only runs on a developer machine is how this regression reaches `main`. The lesson recorded here: **"it worked in the 1.0 release" is no longer evidence that `Net.iperf()` is usable** — it depends
on the packaged binary's tuple shape and interactive probe output, so the timeout and the teardown must be owned by our own code.

**Guard completed (2026-11-23, second round the same day)**: pinning only "no `Net.iperf()`" is not enough — swapping the readiness probe back to `waitListening()` reintroduces the very same hang trigger. `check_iperf_guard()` now also pins the `ss` probe (`-ltn` / `-lun`, with `waitListening` forbidden in the source), both commands running through `_iperf_namespace_command()` (the node's own netns), the client timeout mapping to `504` with the output tail as the message, a non-zero exit mapping to `400`, and `_drain_iperf_process(server_process)` plus the `iperf_running` reset inside `finally`. Negative case verified: turning `"-lun"` into `"-lunX"` makes `--source-only` exit 1. On the BFF side `pnpm check:lab-bff` ⑮ pins four iperf facts: `POST /iperf` matches the long budget (200 with a 2s upstream delay under a 3s budget), the request body reaches the upstream unchanged, and an upstream `504` (client timeout) or `409` (already running) is passed through together with the upstream's own words — that is how the page tells "try again later" apart from "the upstream is broken", and it is the last layer this decision needs.
