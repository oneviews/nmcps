# ADR-0009: Session and Token Model (Web httpOnly Cookie / Desktop Bearer)

> **Layer**: Tier 5 record layer — the body is append-only; changes require a new ADR with `supersededBy`.


- **Context**:
  1. Decision 7 of `NMCPS-ADR-0007` explicitly kept authentication to passthrough and deferred login / refresh / session storage to a new ADR; its follow-up section named "ADR-0008", which the download landing page took, and `NMCPS-ADR-0008` pushed the topic to **0009**. This ADR closes that gap.
  2. The v1 combination must not be copied: the BFF wrote `auth_token` into an **httpOnly** cookie while the frontend read it with `useCookie('auth_token')` — httpOnly is invisible to JS, `isSignedIn` lived only in memory, and any refresh signed the user out. v2 has to decide *who writes the token and who may read it* first.
  3. v2 runs on two hosts: the browser SPA (same origin as the BFF or cross-origin via `public.bffBase`) and the Tauri WebView (`tauri://localhost` / `http://tauri.localhost` custom protocol). Cookie reliability and attribute constraints differ between them, so a single carrier necessarily compromises one side.
  4. The landing shape is already in place in `buildUpstreamHeaders` of `server/utils/bff/proxy.ts`: forward the client `Authorization` when present, otherwise read `bff.tokenCookieName` (default `nmcps_at`) and send `Bearer ${token}`. This ADR only decides who writes that cookie and what the desktop uses; the proxy structure does not change.

- **Decision**:
  1. **Dual-mode sessions**: the **web** build uses a BFF-issued cookie session; the **desktop** build uses Bearer tokens. No "Bearer everywhere", and no "cookies on the desktop".
  2. **Two cookies for the web**: `nmcps_at` (access token, short-lived, `Path=/`) and `nmcps_rt` (refresh token, long-lived, `Path=/api/auth`, sent only to the refresh endpoint). Both are always `HttpOnly` (invisible to JS, which removes the v1 read/write mismatch at the root), `Secure` in production, `SameSite=Lax` (enough for a same-origin SPA and workable in desktop WebView development without https), and never set `Domain` (no subdomain bleed).
  3. **Bearer for the desktop**: the login endpoint returns `access_token` / `refresh_token` to the desktop client (the web login response carries **no** token plaintext, only cookies); the desktop persists them in the app data directory through `tauri-plugin-store`, and `useApi` injects `Authorization: Bearer`. Refresh-token rotation overwrites them in place.
  4. **Only the BFF issues tokens**: `/api/auth/login`, `/api/auth/refresh`, `/api/auth/logout` and `/api/auth/session` are explicit Nitro routes (`server/api/auth/*.ts`); `auth` is **not** added to `GATEWAY_RESOURCES`. Cookie attributes (HttpOnly / Secure / SameSite / Path) must stay decided by the BFF, and explicit routes also block any `/api/auth/**` pass-through.
  5. **Single egress**: both modes end up as an upstream `Authorization: Bearer` in `proxy.ts` (existing logic kept: header first, cookie fallback). The upstream only understands Bearer and never sees browser cookies.
  6. **CSRF defence only for cookie mode**: in addition to `SameSite=Lax`, cookie-authenticated unsafe verbs (POST / PUT / PATCH / DELETE) must present an `Origin` inside the `bff.allowedOrigins` allowlist (reusing the check in `server/middleware/cors.ts`); missing or not allowlisted → `403 bff_csrf_rejected`. Bearer mode is immune and needs no extra check.
  7. **No server-side session store**: the BFF stays stateless (multiple replicas, no Redis). Revocation relies on short-lived access tokens plus refresh rotation (decided upstream); logout clears the cookies and calls the upstream revoke endpoint.
  8. **Configuration**: `bff.tokenCookieName` (default `nmcps_at`) moves from "read-only" to "written by the BFF"; add `bff.refreshCookieName` (default `nmcps_rt`), `bff.accessTtlMs` and `bff.refreshTtlMs`, all overridable via `NUXT_BFF_*`.
- **Consequences**:
  - Expect new `server/api/auth/{login,refresh,logout,session}.ts` plus `server/utils/bff/session.ts` (cookie read/write and CSRF check), and session types in `shared/types/api.ts`.
  - `app/composables/useApi.ts` gains two paths: inject `Authorization` on the desktop, and retry once after a single-flight refresh on 401; the web side keeps `credentials: "include"` (already the case).
  - A future `app/composables/useAuth` becomes the single source of login state: the web asks `GET /api/auth/session` for the user profile (**never reads tokens**), the desktop derives it from the stored tokens.
  - `scripts/check-bff.mjs` needs a new auth assertion group (cookie attributes, CSRF rejection, Bearer passthrough, 401 → refresh path), so the count grows past 38.
  - `.env.example` and `nuxt.config.ts` gain the four settings above.
- **Alternatives (rejected)**:
  - **Bearer everywhere with `localStorage` (web included)**: one XSS line exfiltrates a long-lived token, and it repeats the v1 "refresh loses the session" lesson with a worse blast radius.
  - **Reuse cookies on the desktop**: cookie-jar behaviour under a custom protocol varies across WebView2 / WKWebView / WebKitGTK, `SameSite=None` demands https, and whether cross-origin requests carry the cookie cannot be guaranteed.
  - **Opaque session id in `nmcps_at` plus a BFF session table**: needs shared storage (Redis) and a cleanup job; with replica count undecided and no Redis, the benefit does not cover the operational cost.
  - **Add `auth` to `GATEWAY_RESOURCES` and let the upstream own login**: cookie attribute decisions move upstream, the BFF loses control over `HttpOnly` / `SameSite`, and a whole path prefix opens for pass-through.
  - **Keep the v1 "httpOnly write, `useCookie` read" pair**: context 2 already shows it fails on every refresh.
- **Follow-ups**:
  - Desktop tokens currently land in `tauri-plugin-store` (plaintext JSON in the app data directory) without OS keychain integration; adopting `tauri-plugin-keyring` or Stronghold needs a new ADR.
  - Server-side revocation ("sign out all devices", refresh-token replay detection) depends on upstream capabilities; there is no BFF token blocklist.
  - The 401 single-flight refresh in `useApi`, the `useAuth` composable and the `/api/auth/*` routes are **not implemented yet** — this ADR fixes the model, implementation follows the docs-first rule in a separate PR.
  - Multi-tenancy binding is undecided (must `x-tenant-id` match a tenant claim in the token, and does switching tenants re-issue tokens?).
