# Topology Monitoring Domain Baseline (NMCPS-DESIGN-001)

> **Responsibility**: single authority for `domain.topology` — topology visualization of devices and links, collection/display of monitoring metrics, and the target-page list, data sources, graphic shapes, empty/degraded states and acceptance assertions of the three sub-pages. Collection: `NMCPS-ARCH-001`; storage: `NMCPS-ARCH-002`; page structure and toolbar rules: `NMCPS-ARCH-006`; the in-house-graphics and second-upstream verdicts: `NMCPS-ADR-0019` (layers/content/collections/cn/records/adr/adr-0019.md).
> **Audience**: implementation engineers / AI assistants.

---

## 1. Positioning

Topology monitoring is the "observation plane" of the NMS: it visualizes device nodes and link relationships, monitors device/link metrics in realtime, and supports fault location and capacity planning.

---

## 2. Functional Scope

| Sub-page | Function | 2.0 location |
| :--- | :--- | :--- |
| monitor | Network topology graph and global overview | `layers/topology/app/pages/topology/monitor.vue` |
| link-metrics | Link metrics (bandwidth, latency, loss) | `layers/topology/app/pages/topology/link-metrics.vue` |
| device-metrics | Device metrics (CPU, memory, port traffic) | `layers/topology/app/pages/topology/device-metrics.vue` |

All three pages **share one fetch core**: the topology structure comes from 8888 `/topology/graph` and metric series from `/metric/datapoint`; the pages differ only in whether the selected object is a node or a link, and in which metric codes (`metric_code`) they display.

---

## 3. Key Data Entities

| Entity | Note |
| :--- | :--- |
| Device Node | Routers/switches/firewalls etc. |
| Link | Physical/logical connections between devices |
| Topology | Visual model of nodes + links |
| Metric | Time-series monitoring data (in TSDB) |

---

## 4. Domain Boundary & Dependencies

- **Upstream**: device collection (SNMP, `NMCPS-ARCH-001`), metric storage (TSDB, `NMCPS-ARCH-002`).
- **Consumers**: dashboard (overview), scenario (modeling input).
- **Out of scope**: device config push (device domain), alarm rule management (system domain).

---

## 5. Roadmap

1. Topology graph rendering (Canvas/SVG nodes + links).
2. Device-type icon auto-matching.
3. Realtime metric refresh with alarm linkage.

## 6. Data Sources

### 6.1 Primary source (the 8888 unified gateway, through the BFF `[...slug]` gateway, authenticated)

| Purpose | Endpoint (8888 `/api/v1`) | Key parameters | Note |
| :--- | :--- | :--- | :--- |
| Topology structure | `GET /topology/graph` | `tenant_id` / `include_virtual` / `include_status` / `group_by` | measured 36 nodes / 48 links / 3 combos; with `include_status=true` nodes carry their status colour |
| Device ledger (list pane) | `GET /metric/device` | `page` / `page_size` / `device_code` / `codes` / `role` / `vendor` / `status` / `include` | the paged envelope's `total` is the count source |
| Link ledger | `GET /metric/link` | `page` / `page_size` / `link_id` / `device_code` / `medium` / `status` / `include` / `from` / `to` | `from` / `to` are the time window (ISO strings) |
| Metric series | `GET /metric/datapoint` | `mode` / `mgmt_ip` / `metric_code` / `from` / `to` / `step` / `rate` / `ips` / `codes` | returns a VM-style matrix (`metric` labels + `values` pairs); the retrieval contract belongs to `NMCPS-CONTRACT-002` |
| Metric catalogue (picker) | `GET /metric/definition` | `page` / `page_size` / `metric_group` / `keyword` | decides which `metric_code` values the picker offers |
| Available metric names | `GET /metric/name` | `mgmt_ip` / `ips` | per-device metric names; prefer this over `definition` when both are viable |
| Alarm overlay | `GET /alarm/alarm-events` | `page` / `page_size` / `severity` / `status` / `target_type` / `target_id` / `first_triggered_at_from` / `first_triggered_at_to` | measured 2026-11-07: `target_type` is **always `device`** (no `node` exists anywhere in the table) and `target_id` is the device management IP = the topology node `id`, so the join needs no mapping table; rule management is out of scope here |

### 6.2 Second source (the 8001 simulator, through the whitelisted BFF `server/api/sim/**` channel)

The simulation control plane fills in only what 8888 lacks: **topology write operations** and **simulation runtime state**. The channel is defined by `NMCPS-ADR-0019` §4 — its own `runtimeConfig.simulator`, a template whitelist, `allowWrite` defaulting to `false`, and no `Authorization` sent.

| Purpose | Endpoint (8001, read-only) | Note |
| :--- | :--- | :--- |
| Runtime inventory | `GET /api/network/runtime-inventory` | **one call, whole picture**: `{ running, scenario, overrides:{…}, nodes[], links[] }`, measured at 36 nodes / 48 links; nodes are joined to 8888 nodes by device identity to overlay a "simulated" badge, links carry live up/down |
| Simulation stats | `GET /api/network/stats` | `node_count` / `link_count` / `nodes_by_type` / `links_by_type` / `nodes_online` / `links_up`, feeding the header badges |
| Neighbour discovery | `GET /api/lldp/summary`, `GET /api/lldp/neighbors/{node_id}` | measured 2026-11-07: summary is `{ node_count, neighbor_entry_count, mode, mib_standard, lldp_mib_oid, local_sys_name, local_sys_desc, local_chassis_id }` (the **scan size plus one sample endpoint**, not a per-switch grouping); a neighbour item is `{ neighbor_id, neighbor_type, neighbor_name, local_interface, remote_interface, chassis_id, chassis_id_subtype, port_id, port_id_subtype, port_descr, sys_name, sys_desc, ttl, link_type, link_status, discovered_at, mib_oids }` (see §6.13) |
| Runtime preview | `GET /api/network/runtime/preview` | candidate topology preview before an add/remove |

> Verbs follow the measured `openapi.json`: `/api/network/runtime/nodes` and `/api/network/runtime/links` are **POST (create — a write)**, while `/api/network/runtime/nodes/{node_id}` and `/api/network/runtime/links/{link_id}` are **DELETE (remove — a write)**. Reads always go through `runtime-inventory`; listing `runtime/nodes` gets a 405. `NMCPS-ADR-0019` §4.2 was corrected against the same measurement on 2026-11-05.

| Purpose | Endpoint (8001, write, `write: true`) | Note |
| :--- | :--- | :--- |
| Link actions | `POST /api/network/links/{link_id}/{down,up,toggle,disable,power,reconfigure}`, `PATCH /api/network/links/{link_id}/{tc,radio}` | one button per action, requiring a second confirmation plus an audit line; `tc` / `radio` are **PATCH** (parameterised attribute change), not POST |
| Node actions | `POST /api/network/nodes/{node_id}/{start,stop,restart,power}`, `PATCH /api/network/nodes/{node_id}/{radio,ip}` | same; `radio` / `ip` are **PATCH** |
| Runtime add/remove | `POST /api/network/runtime/{nodes,links}`, `DELETE /api/network/runtime/{nodes,links}/{id}` | mutates the running simulation, the highest-risk group: needs "writes allowed" plus its own second confirmation |

**Write entries shipped (P1-B, 2026-11-06; link actions completed in 0.16.0)**: the `monitor` toolbar's right area carries **two groups** of actions — two node actions (restart / stop) when a node is selected, and three link actions (down / up / toggle) when a link on the canvas is selected; both share the same "capability bit → second confirmation → action → toast + refresh" routine, and the confirmation's `pendingScope` distinguishes `node` from `link`. Runtime add/remove still has **no entry point** (it needs its own confirmation and a higher privilege level, so it stays P1).

| Page entry | Endpoint | Preconditions | Interaction |
| :--- | :--- | :--- | :--- |
| Restart node | `POST /api/network/nodes/{node_id}/restart` | a selected node + that node present in the simulator runtime (the `runtime-inventory` join gives `marker.simId`) + channel `writeEnabled` | `UModal` second confirmation (naming the simulated node and the action) → success `useToast` plus an immediate `refresh()` |
| Stop node | `POST /api/network/nodes/{node_id}/stop` | same | same |
| Bring link down / up / toggle it | `POST /api/network/links/{link_id}/{down,up,toggle}` | a selected link on the canvas + that link present in the simulator runtime (`simulatorLinkFor(link).simId`) + channel `writeEnabled` | `UModal` second confirmation (naming both endpoints, the **simulator link id** and the "irreversible / the BFF keeps no copy / will not roll back" sentence) → success `useToast` ("link is down / up / toggled") plus an immediate `refresh()` |
| Runtime add/remove | see the table above | not open yet (P1) | no button at all; when opened it follows the same "capability bit → second confirmation → audit" routine |

The client **does not guess** write permission: the page reads `{ configured, writeEnabled, timeoutMs, readinessPath }` from the BFF's own capability probe `GET /api/sim/channel`. That endpoint returns capability bits only and **never `baseUrl`** (the upstream address is not leaked to the browser); with `writeEnabled=false` the buttons are `disabled` and the page sends **no** write request at all — the BFF's 405 is the second gate, not the first. `node_id` comes from `marker.simId` (the simulator-side id), **not** the 8888 node id (one is the simulation engine's key, the other the management IP).

### 6.3 Local engines

**This domain uses no BFF engine** (`NMCPS-ADR-0019` §5.2 registers no triple for it). Layout is a client-side pure function family (`app/utils/graph/*`: `topologyLayout` / `topologyLayering` / `topologyRadialLayout` / `topologyTierTreeLayout` / `topologyEdgeStyle`) that takes node and link arrays and returns coordinates, holding no state.

### 6.4 Fetch constraints

1. **One egress**: 8888 data goes only through `useApi()` → the BFF gateway; pages never call the upstream directly and never roll their own `$fetch`.
2. **Polling**: topology and metrics refresh every 30s by default, pause while `document.visibilityState !== "visible"`, and refetch immediately once visible again.
3. **Time window**: metric pages default to the last hour with `step` chosen from the window; the picker follows `NMCPS-ARCH-006` §4.1 — one summary button plus a `UPopover` (preset column + `UCalendar range`), never two side-by-side `datetime-local` inputs.
4. **Failure classification**: `ApiError.code` 401 takes the shared refresh path; `5xx` shows the error state with retry; `code=0` with empty `data` is an empty state, **not** an error.

### 6.5 Metric Trend Retrieval Contract (A3, landed 2026-11-06; polyline moved to the metrics page 2026-11-08)

The monitor page **no longer draws a polyline**: the `monitor` detail pane only offers a deep-link button (`topology-node-metrics`, carrying the selected node's management IP) that opens `device-metrics`, where the series is drawn (§6.6). Three reasons:

- A single view that draws both a topology and a time series reads badly for both — a topology answers "who connects to whom", a series needs a time axis;
- A monitor page that fetched its own data would have to re-implement the failure semantics in place, giving three entries three vocabularies (A13 / A14 fixed exactly that drift; A15 now pins "the monitor page does not make things up");
- The deep link carries a **management IP** (the identity the topology really has); the target page resolves it into a `device_code` with the ledger it already fetched and writes `?id` (§6.15 requirement 5).

The two retrieval steps (now owned by the metrics page, both through the BFF gateway; pages never call the upstream directly):

| Step | Endpoint (8888 `/api/v1`) | Parameters | Notes |
| :--- | :--- | :--- | :--- |
| ① pick a code | `GET /metric/name` | `mgmt_ip` = the selected node's **management IP** | the device's available metric names (dual shape; normalisation in `NMCPS-CONTRACT-002` §7); only the collector self-monitoring namespace (`up` / `scrape_*`) is skipped — **type is never guessed from the name**. The list can be **empty** while the device still has series (24 of 36 devices, measured 2026-11-08), so this page falls back to the first name the catalog calls `numeric` (the union rule of §6.6) |
| ② fetch the series | `GET /metric/datapoint` | `mode=range` / `mgmt_ip` / `metric_code` / `from` / `to` (ISO strings) / `step=60` | the last hour; `rate` is not sent — no known type means no rate (`NMCPS-CONTRACT-002` §6.5) |

- **Data kernel**: `layers/topology/app/composables/useMetricSeries.ts` (the generic two-request loader plus the catalog join, state and a sequence number against races). After 2026-11-08 the monitor page has **no retrieval layer of its own** (`useNodeTrend.ts` is deleted): it sends no `/api/metric/*` request, so a page-level failure message cannot even exist. Unpacking / ascending sort / de-duplication / downsampling all live in the pure functions of `app/utils/chart/metricSeries.ts` (`NMCPS-CONTRACT-002` §6.6), the three-way classification in `app/utils/metric/metricCatalog.ts` (`NMCPS-CONTRACT-002` §8), and the component only draws.
- **Graphics**: `app/components/Graph/TrendChart.vue` (SVG polyline plus area fill; `vector-effect` keeps the stroke width under stretching; above 2 × column width the series is bucketed per column keeping min/max, so spikes survive).
- **The hand-off is that button in the detail pane**: the deep link is built by `app/utils/metric/metricDeepLink.ts` (`?mgmt_ip=` → resolved by the target page into `?id=`); a node without a management IP gets a disabled button plus a tooltip saying why — never a button that lands on an empty page.
- **Failure semantics all live on the metrics page** (§6.7 S3 / S7): the monitor page renders neither an error box nor "no collected data in this window" — it does not hold that data, so either sentence would be a fabrication (A15).
- **Type verdict** (metrics page): text and event metrics never enter the line panel (`selectable = false`), the decision order is `NMCPS-CONTRACT-002` §8.3; when the catalog is unavailable the loader falls back to name-only (skipping just `up` / `scrape_*`), where a text metric can still flatten — the gap stays registered rather than papered over with name guessing.

### 6.6 Metrics Page Retrieval Contract (device-metrics / link-metrics, landed 2026-11-06)

Both pages share one skeleton — "ledger → select a row → metric picker → `TrendChart`" (`app/components/Layout/Split.vue` two panes plus `useRecordSelection`, which keeps the selection in `?id`):

| Page | Ledger endpoint | What the selection fetches |
| :--- | :--- | :--- |
| `device-metrics` | `GET /metric/device` (`page` / `page_size`; the envelope's `total` is the count) | `mgmt_ip` = that device's `mgmt_ip` |
| `link-metrics` | `GET /metric/link` (same) | `mgmt_ip` = the **source endpoint device's** `mgmt_ip` (a second `/metric/device` call builds the `device_code → mgmt_ip` map) plus the **filter key `ifIndex` = `identity.source.if_index`** |

- **Row copy in the left pane** (both pages: one primary line + one secondary line, the rule lives in `NMCPS-ARCH-006` §3.6): the device page shows the device name plus `mgmt IP · 邻居 N · 端口 up/total` (e.g. `10.0.0.249 · 邻居 2 · 端口 2/2`), with CPU / memory reserved for the right-hand overview; the link page shows the two **device names** `A → B` (e.g. `Wi-Fi胖AP-11 → 接入交换机-1`) plus both `interface:mgmt IP` (e.g. `n20-eth2:10.0.0.245 → n7-eth3:10.0.0.11`). A link endpoint only carries `device_code` + `interface_name`, so names and IPs are both resolved against `/metric/device` (`deviceNameIndex()` / `deviceIpIndex()` in `app/utils/metric/metricLedger.ts`, sharing the same 200-row ledger with no extra request); a missing field renders `—` — never 0, never half a sentence, never a guessed address. Utilisation / latency belong to “the current value of this row” and appear only in the detail overview, so the ledger no longer repeats them (it only answers “which one is this”).
- **Shared kernel**: `useMetricSeries(ip, { code, rate, ifIndex })` — catalog (the `/metric/definition` row of §6.1), name list and series in one pass; pages only bind the returned refs to controls.
- **Picker**: `USelect` options are **the catalog entries with `selectable === true` ∪ the names in the name list** (`NMCPS-CONTRACT-002` §8.6 union: name-list hits first, label from `en_name`, falling back to `code`, with `unit` as the suffix); switching only changes `metric_code` and does not refetch the name list. **An empty name list no longer disables the picker**: measured on 2026-11-08, 24 of 36 devices (18 fat APs + 3 access switches + 3 aggregation switches) answer `[]` while the same AP still returns 4 series for `ifInOctets` — the candidates now come from the catalog and the pane adds one line, "the upstream returned no metric names for this device (candidates come from the metric catalog)", so the user picks one and then sees whether the window holds any samples. The same measurement fixed two same-root causes: catalog rows carry their type under `data_type` (not `metric_type`), and reading only the latter lets `string` metrics into the options as a constant 1 line; and the catalog holds `total=463` rows, so taking only the first 200 leaves 263 rows without type evidence.
- **Link series = that source port (measurement-driven change, 2026-11-06)**: `/metric/datapoint` still has no `link_id` dimension, but a live probe shows the series **carry an `ifIndex` label** (the same interface is scraped by two jobs; 2 interfaces × 2 jobs = 4 results). The link page therefore moves from "the source device's metric of the same name" to "the source device's series **for that port**": it passes `ifIndex = identity.source.if_index`, and `selectMetricSeries` (`NMCPS-CONTRACT-002` §6.9) filters the group and averages across jobs. Three honest labels: ① the endpoint has no `if_index` ⇒ current values only, no polyline; ② the chosen metric carries no `ifIndex` label (device-level metrics such as `sysUpTime`) ⇒ the device-level series is drawn and labelled "device-level, not port-level"; ③ `if_index` was supplied but that metric is interface-scoped without this index ⇒ the `no_interface_series` empty state, **no substitute port**. True `link_id` retrieval still waits for the upstream.
- **Rate switch**: shown only when the catalog entry has `metric_type === 'counter'` (`NMCPS-CONTRACT-002` §6.5); `rate` is an explicit user choice defaulting to `false`, while `gauge` / `duration` hide the switch and always send `false`.
- **Empty and degraded states**: same contract as §6.5 (no data / every point invalid are the empty state, never a zero-value line); a catalog failure only prints one line inside the chart card and **never escalates into a page-level error**; the picker is disabled with the `no_metric_names` copy only when the catalog and the name list are **both** empty.


### 6.7 Node Detail Fact Layer (A21 – A23, landed 2026-11-06)

In 1.0 the node detail pane showed more than name and status: CPU / memory progress bars, three KPI cards (interfaces / neighbours / traffic) and a neighbour list. 1.0 put those fields straight on the node `data` and used `-1` as its "unavailable" sentinel. 2.0 keeps the **same endpoint and the same fields**, but moves the read into the pure function `app/utils/graph/topologyNodeFacts.ts` (the table below lists the **flattened** read model; the upstream `data` shell is §6.10):

| Field (node wire format) | Unit / contract | Unknown when | Rendered as |
| :--- | :--- | :--- | :--- |
| `cpu` / `memory` | % | absent / `null` / `-1` / outside 0–100 | progress bar + one decimal; when unknown only "—" is printed and **no empty bar is drawn** (an empty bar reads as 0%) |
| `interfaces` | count | absent / `null` / negative | the number itself; `0` is a real value and stays `0` |
| `traffic` | Mbps (1.0 contract) | only when all three fallbacks miss | `traffic` → `traffic_in + traffic_out` → `trafficTotalKbps / 1000`, tried in that order |
| `neighbors` | count | — | the page **does not read** this upstream field; `topologyNeighborsOf()` derives it from the **current canvas** links (same source as 1.0's neighbour count), counting only links whose both ends survive cropping, and counting parallel links separately |

- **Neighbour list**: each row is "peer status dot + name + link status badge" and clicking a row selects that peer; with no neighbours the pane states "no other node on this graph links to it directly" instead of leaving a blank block.
- **Never zero-filled**: the one hard rule of this section (`NMCPS-CONTRACT-002` §6.3) — unknown is always `null` → "—", and the three unknown shapes (missing field / `-1` / non-numeric) go through the same check, so the page keeps no second set of defaults.
- **Fake-upstream sample**: the topology graph in `scripts/lib/bff-harness.mjs` deliberately carries four node shapes (all fields / only `traffic_in|out` / `-1` sentinels + a real `0` + legacy Kbps fields / nothing at all), giving A21 – A23 independent evidence for each contract.

### 6.8 Canvas Layouts and Radial Fan Rotation (A24 – A25, landed 2026-11-06)

1.0's `monitor` toolbar carried two view controls: a "2D layout" dropdown (six entries `radial` / `dagre` / `tree` / `force` / `grid` / `circular`, defaulting to `radial`) and, right next to it, a radial fan rotation control (slider −90°…90°, ±5° steps, reset to the default 25°). 2.0 replicates **two layouts plus the rotation control**, porting the geometry line by line from the 1.0 libraries of the same name (since 0.17.15 the `layered` entry is retired and the tower semantics live in the tier tree, see below):

| Layout key (copy under `layouts.*`) | Geometry | Lives in | Difference from 1.0 |
| :--- | :--- | :--- | :--- |
| `radial` (default) | tier wedge fan: centre = **the smallest rank** (i.e. the elected root, radius 0), equal radii `r(t) = (t − apex)/span · R`, per-band sweep generated from the **band count** (outermost band 65°, other non-apex bands 75°, apex 60°) centred on "straight left", per-band grouping by parent with a gap between groups and barycentre ordering inside a group, rotated 25° counter-clockwise by default | `app/utils/graph/topologyRadialLayout.ts` (1.0 library ported line by line) | none. 1.0's explicit parameter abilities (`stretch: 'auto'`, `sweepDeg: 360` full circle, `barycenterOrder` A/B) come along too; the page only opens the defaults |
| `tree` | tier tree = **tower**: one horizontal line per row, ordering inside a row by its parents' barycentre (zero crossings between adjacent rows), a minimum gap of 80 inside a row (1.0's `nodesep`, *not* spread over the full canvas width), every parent sitting on the centre line of its children's group; **the row number is the rank resolution's** | `app/utils/graph/topologyTierTreeLayout.ts` (1.0 library ported line by line plus the two coordinate passes) | 1.0's `dagre` ran inside the G6 engine with a hidden anchor chain pinning tiers; 2.0 draws its own graphics (`NMCPS-ADR-0019` D1) and has no engine, so the two core steps of dagre (crossing minimisation / coordinate assignment) are written by hand; the reading direction is the same top-down one |
| `force` / `grid` / `circular` | — | **not landed** | all three were 1.0 leaning on G6's built-in engines (`d3-force` / `grid` / `circular`); 2.0 draws its own graphics (`NMCPS-ADR-0019` D1) and has no layout engine, so a replica would need a hand-written force simulation ⇒ **registered as not replicated, and the dropdown never shows these fake options** |

- **Why only two entries** (0.17.15, a requester ruling): by 0.17.14 `layered` and `tree` were already **two implementations of the same rank resolution and the same parent-over-children centring** — both entries drew nearly the same picture for one dataset, leaving readers to judge "which one looks more like dagre", i.e. asking the user to pick an implementation for the product. With `layered` retired, every tower semantic (barycentre ordering, minimum gap 80, parent centred over its children, radius shrinking per tier, ring colour by tier) lives in `tree` alone, and `topologyLayeredLayout.ts` keeps only the rank resolution `resolveLayeredRanks()` (A42 / A43 / A44 / A46 are now measured in `tree`).

- **Rotation semantics**: counter-clockwise is positive, range −90°…90°, step 5°, default `RADIAL_ROTATE_DEG = 25` (the value the requester ruled in 1.0 v0.30); it rotates the whole fan while the centre stays put, so per-tier sweeps, equal radii and intra-group spacing all keep their geometry. The two ±5° buttons use `carbon:rotate-counterclockwise` / `carbon:rotate-clockwise` — before 0.17.16 they named `carbon:rotate-ccw` / `-cw`, which are not valid Carbon names, so the buttons drew **nothing at all** (a pair of empty `<svg>`s); A48 therefore measures icon content instead of merely checking that the `[data-testid]` exists.
- **When the control exists**: the rotation control is **rendered only** in the `radial` layout and is absent entirely elsewhere — not "rendered but greyed out", because a disabled slider implies dragging it would change something, while the other layouts never read the angle at all.
- **Cropping versus layout**: nodes are cropped to 400 and links to 1,200 by "tier + id" *before* the layout function runs, and both layouts consume that same cropped input **and the same rank resolution**, so switching layouts never changes what was trimmed nor who sits above whom, and the canvas badge shows the same numbers in every layout.
- **Control placement and order** (second / third pass 2026-11-09): the layout dropdown **and the canvas controls share the page toolbar's left zone** (`#app-toolbar-left`, one row in `topology-controls`), reading left to right **layout dropdown → rotation → zoom → show names → reset view → refresh**: they all read "how is this graph presented" (geometry, viewport, readings), the leading ones are settings and the trailing "refresh" is the data action. 0.17.8 had gathered them into a **row in the canvas' top-right corner**, but that row covered the topmost nodes and links (A48's old assertion only measured "within 12 px of the canvas' top-right", which cannot see occlusion); the canvas' bottom-right corner belongs to the **legend** (a reading, not a control, §6.15) and the top-left corner to the status badges (cropped / collapsed groups / collapsed subtree / alarms / focus). A48 therefore pins: the control row **belongs to** `#app-toolbar-left`, sits **on the same line** as the layout dropdown (vertical centre within 12 px), **does not overlap the canvas**, and the last three `[data-testid]`s are exactly "show names → reset view → refresh".
- **Two resets are gone** (a 2026-11-09 requester ruling): the separate `carbon:reset` buttons next to the rotation and zoom controls (`topology-rotate-reset` / `topology-zoom-reset`) are deleted outright — resetting the angle and resetting the viewport were only steps 2 and 3 of the three-in-one "reset view", and three identical icons in one row leave users unsure which to press. To reset, press "reset view" (it disables itself when all three are at their defaults, §6.9). A48 pins this negatively: neither testid may appear anywhere on the page.
- **Canvas size**: `radial` / `tree` coordinates are computed against a logical viewport of 1000 × 660 (`TOPOLOGY_CANVAS_WIDTH` / `TOPOLOGY_CANVAS_HEIGHT`); content smaller than the viewport is centred, content larger grows the `viewBox` — the latter comes from the library's `bbox`, the page never guesses. The tier tree takes its **width from the widest row** (21 access devices × 80 = 1600, so `bbox` ≈ 1740 with padding; the height is `110 × (rows − 1)` plus padding on both sides) and grows the `viewBox` accordingly — the equivalent of 1.0's `graph.fitView()`: the tower shrinks to fit the viewport and the user zooms back in with the wheel or the zoom buttons. It **never** squeezes 21 devices into a 1000-wide canvas (that is when neighbouring labels stack on top of each other).
- **Why the tier tree has to be a tower** (the 2026-11-08 report "the layering result is wrong"; the sole owner of that semantics since 0.17.15): the old implementation stopped at banding by `tier` and spread each band over the full canvas width in `id` (= management IP) order, so ① who sits next to whom had nothing to do with the topology and the distribution → access links crossed massively (21 crossings measured on production; 12 after the change — the rest belong to the fully meshed 3 × 3 core/distribution edges and cannot be removed), ② the three core devices were spread over 80 / 500 / 920 with no alignment to their children, so the tower was unreadable, and ③ 21 access devices crammed into 840 px (42 px apart) with overlapping labels. The two steps now match 1.0's dagre: **in-row ordering** sweeps down and up by the adjacent row's barycentre and keeps the version with the fewest crossings; **in-row coordinates** start from the neighbours' mean, are packed to the minimum gap, and a fifth pass then re-centres **every parent on the mean of its children** (`packRow()` / `mean()` in `topologyTierTreeLayout.ts`). The "hole even-out" step inside the packing is what makes it converge: without it the spread-out parent coordinates are fed back as the next round's expectation and widen the row every round (~330 px per two rounds, measured).
- **Parent centred over its children** (A24, 2026-11-09): coordinates start from the neighbours' mean and then converge **bottom-up** — each parent's `x` becomes the mean of its visible children's `x` (with a single child the two align). That turns "the distribution switch sits centred above its access devices, the core above the distribution" into an assertable geometric fact rather than a typesetting side effect; the root row does not take part in the convergence (it has no parent to centre, and a mean would drag it off the canvas centre); after the convergence the whole picture is **re-centred on the terminal row** (next item).
- **Rank resolution: root election plus demotion of childless nodes** (A43, 2026-11-08; 1.0 had no such capability): `tier` only answers "which band does this device belong to", never "who sits above whom inside one band" — the three production cores are fully meshed, their edges are **equivalent**, and dagre can only put them in the same row. So after banding, the ranks go through two rules that **only change which row a node lands in**, implemented as the pure function `resolveLayeredRanks()` (`topologyLayeredLayout.ts`, no DOM, directly unit-testable):
  - **Root election**: when the first band holds more than one node, pick one as the root by its **device name's** naming convention (word list `LAYERED_ROOT_KEYWORDS`: 网控 / 控制中心 / 管理中心 / 管理平台 / 管理服务器 / 中心 / manager / controller / management / mgmt / center / centre / nms; the score is the length of the longest matching keyword, ties broken by degree and then by id for determinism) and lift it into **its own first row** (rank 0, role `root`). When no device matches, **no election happens** and the flat top stays — guessing "who is the parent" by id or degree on an equivalent graph is a coin flip. A single node in the first band is already the apex, so nothing is elected there. The production sample elects 「网控中心」.
  - **Childless nodes move down**: a node with no neighbour in a **strictly lower** band has no business occupying a middle row (the space below it is empty, and readers take a wrong-looking band for a fact). Such nodes all move to the **last band** (sharing the row with the terminals); the first band is exempt (a childless node there is an isolated device, and moving it would drag it from the entry position to the very bottom) and so is the last band (already at the bottom). Moving one node down can turn its own band into leaves, so the pass **iterates to a fixpoint** and splices out empty bands (ranks must stay contiguous, otherwise `y` leaves a gap per empty band). In the production sample 「Wi-Fi胖AP10」…「Wi-Fi胖AP18」 therefore drop from band 3 to band 4.
  - **The role never follows the row number**: roles always come from `tier` (`roleOfNode()` — a childless node reads as the terminal tier, §6.15.2 item 3; an elected root is overridden to `root`). A demoted access device stays a blue access node and a core device left in row 2 stays a red core — moving down one row only says "there is nothing under it", it does not say "it became a terminal" (colouring by row number would paint those 9 APs terminal-green, i.e. rewrite the device class).
- **The rank resolution applies to both layouts** (A45, from the 2026-11-08 report "the radial fan and the tier tree do not render with the new ranks"): the two rules above answer "who sits above whom", which is **graph semantics**, not one geometry's private business. 0.17.6 wired them into the tower's geometry only, while `radial` / `tree` still fed the raw `tier` to their libraries ⇒ on the other layout the root was flattened back into the first ring and the childless access node climbed back to a middle ring: one dataset, two hierarchies, i.e. "look at it in another layout" turned into "look at another fact". The resolution is now lifted into the layout entry point `layoutTopology()` (`resolveRanks()`) and shared by both:
  - **Band ordinal = rank + 1**: `radial` / `tree` are 1.0 libraries ported line by line; their input field is called `tier` but is only ever used as "which ring / which row" (radius `r = (t − apex)/span · R`, row `y = (t − minTier) · gap` derive from it alone), so they are fed the resolved **band ordinal** (`rank + 1`, see `bandNodesOf()`) — the libraries' internal contract (and therefore their existing regression geometry) is untouched.
  - **The per-band sweep is generated from the band count**: `RADIAL_SWEEP_BY_TIER` was hard-wired to "4 bands"; once the band count differs (an election adds one, a demotion merges two) a fixed per-band table goes out of step — a 5-band graph's outermost band would miss 65° and fall back to the 60° baseline, i.e. narrower than the band inside it (65°). `radialSweepForBands(bandCount)` replaces it: outermost band 65°, other non-apex bands 75°; at 4 bands it matches `RADIAL_SWEEP_BY_TIER` entry for entry, so the default six-node sample keeps exactly the same geometry (A24 / A25 / A27 / A42 pass unchanged).
  - **Roles are shared too**: `radial` / `tree` also go through `roleOfNode()` (an elected root overridden to `root`), and the old row-number function `roleOfRank()` is deleted — a device that is a blue access node in the tier tree must still be a blue access node in the radial fan.
  - **What it looks like**: the radial fan's **centre** is always the elected root (distance 0 to itself) and the demoted access node shares the **outermost ring** with the terminals; the tier tree's **first row** is always the root and the demoted access node shares the **last row** with the terminals.
- **The centring anchor is the terminal row, not the bounding box** (A24 / A43, the 2026-11-09 ruling "centre the terminal tier first, then align the levels"): after the parent-over-children convergence the tier tree **translates the whole picture** so that the **mean `x` of the last row (the terminal band) equals the canvas centre** (half the current `viewBox` width, ±1 px). The last band holds the most devices and spans the widest (21 access / 9 terminal on production), so centring it is what makes the tower look "seated in the middle"; centring on the bounding box instead pushes the last row off to one side whenever an upper row is wider than it — 37 px on the 20-node sample (the last row spans 274…800 while the `bbox` midpoint is 537). Once the last row is centred, every upper row is already centred over its children, so the tower reads bottom-up as "who owns whom".
  - **Read the canvas centre from the current `viewBox`**: when the content is wider than the base viewport the `viewBox` grows (§6.8 "Canvas size"), and `500` is only half of a 1000-wide viewport. The 20-node sample's last row spans 1074 px ⇒ its centre is `537`, not `500`; both the implementation and the assertion read `width / 2` and never hard-code the constant.
  - **No second "overflow guard"**: `bbox` is computed from the final coordinates and `layoutTopology()` derives the `viewBox` plus the overall offset (`overflowShift()`) from it, so the content always stays inside the canvas with `padding` on both sides. A former guard clamped the translation again by `padding` and thereby destroyed the terminal-row centring (the whole picture moved 37 px to the right on the same sample) — the centring ruling comes first and the padding is its result; mixing the two makes "the last row is off-centre" look like a layout bug.
  - **The radial fan stays bounding-box centred** (the alternative of reusing the same terminal anchor was rejected): a fan's weight sits on its centre (= the root) and its last band is an **arc**, for which "the mean of the last row lands on the canvas centre" has no geometric meaning (the `x` mean of the arc's points is always the centre's `x`, so the shift is identically zero — it would do nothing); its centring comes from `bbox`, matching the radial geometry ported from 1.0 (A24's "switching back restores the radial coordinates point for point" pins exactly this). Two layouts centring differently is not an inconsistency: the tower's centre is its **last row**, the fan's centre is its **circle centre**.


### 6.9 Node Drag Offsets and "Reset View" (A26, landed 2026-11-06)

1.0 v0.36 asked for one thing: "in 2D mode, dragging a node with the mouse should stick", plus a "reset configuration" that pulls a messed-up graph back in one click. 2.0 replicates it as three layers, with the same contract as 1.0:

| Layer | Lives in | Contract |
| :--- | :--- | :--- |
| geometry | `layoutTopology()` (§6.8) | the only producer: the same data plus the same options always give the same picture, and the page may not rewrite coordinates |
| offsets | `app/utils/graph/topologyNodeOffsets.ts` | node id → delta `{ dx, dy }` relative to the geometry, written immutably; anything under `OFFSET_EPSILON = 0.5` (px) counts as "not moved" and **never enters the table** |
| composition | `applyNodeOffsets()` (before rendering, inside `TopologyCanvas`) | geometry + delta = final position; link endpoints read the same table, so edges follow the node automatically |

- **Why a delta layer instead of absolute coordinates**: polling (30 s), status events, container resizes, zoom and pan all trigger a repaint, and absolute coordinates would be overwritten by the recomputed geometry (that was exactly the 1.0 v0.36 defect: "I drag it, it springs back"); a delta on top of the geometry survives the repaint.
- **Dragging only touches this layer**: "reset view" clears the delta layer, leaving the geometry untouched (no layout re-run), so the page never holds a second set of coordinates.
- **Switching layouts clears the offsets**: a delta is relative to the *current* geometry; carrying it into another layout puts the node neither at its new geometric position nor where the user dropped it (under `tree` a whole row gets pushed off the canvas centre). `setLayoutMode()` therefore clears the layer, while a rotation change **keeps** it (the same fan is rotated as a whole, so the delta still holds — 1.0's file-header note 2).
- **"Reset view" is a three-in-one** (button **second from the end** of the toolbar's left-zone control row, `data-testid="topology-reset-view"`): clear offsets → rotation back to `RADIAL_ROTATE_DEG` → viewport reset (zoom 100%, pan zero). The button is enabled when any of the three differs from its default and `disabled` — with a "nothing to reset" tooltip — when all three are at their defaults: "clicked it and nothing happened" and "there was nothing to reset" are two different things.
- **Three-in-one is the only** reset entry point (a 2026-11-09 requester ruling): the `topology-rotate-reset` beside the rotation control and the `topology-zoom-reset` beside the zoom control are deleted — three identical `carbon:reset` icons give no clue which one to press, while the combined button's `disabled` state already answers "is there anything to reset". The row's placement, members and order are in §6.8 / §6.15.4.
- **Residue**: once a node disappears from the upstream its offset entry no longer participates in composition (the geometry table has no such id), which is harmless residue cleared by "reset view"; no "trim along with the data" coupling is introduced (same as 1.0).
- **This is not "dragging edits the topology"**: the offset is local view state — no request is sent, nothing is written back; it survives a refresh in the same session and resets to the geometry on a page reload (as in 1.0).

### 6.10 Two-Layer Wire Format and Flattening (A27, landed 2026-11-07)

The nodes and links of 8888 `/topology/graph` are **not** the flat fields listed in §6.7 — they are G6 **element shapes** with every fact under `data`, the geometry under `style` and the grouping on `combo` (re-measured 2026-11-07 against 36 nodes / 48 links):

| Element | Measured shape (excerpt) |
| :--- | :--- |
| node | `{ id: "10.0.0.1", data: { deviceName, label, type, tier, status, ip, cpu, memory, interfaces, traffic, traffic_in, traffic_out, uptime, … }, style: { x, y }, combo: "combo-10.0.0.251" }` |
| link | `{ id, source, target, data: { linkType, bandwidth: "100 Mbps", status, bandwidth_util_pct, medium, relation, telemetry: { traffic_in, traffic_out, … } } }` |

- **Flattening happens once, at the fetch boundary**: `flattenTopologyNode()` / `flattenTopologyLink()` / `normalizeTopologyGraph()` (`app/utils/graph/topologyNormalize.ts`) lift `data.*` into the flat slots of §6.7, and `useTopologyMonitor.loadGraph()` is the only call site; layouts, the fact layer and the canvas read only the flat model and never guess again where `data` lives. Precedence matches 1.0's `normalizeTopologyInput()` (`data.*` first, top level as fallback), and the name comes from `data.deviceName → data.label → top-level name / hostname / label` — **never** from `id` (that is the management IP).
- **Skipping it degrades silently**: with `data.tier` unreachable, `normalizeTier(undefined)` always falls back to 3, so the layered layout crams every node into a single band (**one horizontal line**, measured `rows = 1`), names degrade to management IPs, every status becomes `unknown` and the detail pane prints "—" everywhere. That is exactly what the 2026-11-07 report ("the page did not change") turned out to be: every feature worked (drag, reset view and zoom verified), the geometry was what degraded.
- **`style.x / y` is not reused**: upstream pre-computed coordinates play no part in the 2.0 layout (geometry comes only from `layoutTopology()`, §6.8). Keeping the field is evidence only — it proves upstream does ship a layout — and changes nothing in this domain.
- **`tier` measured across all four bands** (1: 3 core / 2: 3 distribution / 3: 21 access / 4: 9 terminal), so the layered layout is 4 rows with a `viewBox` height of `140 + 150 × (4 − 1) = 590`; the "outside 1–4 falls back to 3" rule in `normalizeTier()` only fires on genuinely dirty data.
- **`bandwidth` is a string**: measured `"100 Mbps"` (the earlier "all zero" finding only held for some links), and the contract type keeps `number | string`; the page does not display bandwidth yet, so no unit parsing is introduced (that needs its own contract when it is shown).
- **The fake upstream answers with the two-layer shape by default**: the sample body in `scripts/lib/bff-harness.mjs` is still the flat table, but it is wrapped by `nestTopologyGraph()` on the way out (`control.topologyNested` defaults to `true`) — so the self-check now covers "wire format → flattening" **by default**, and A21 – A26 all run on the two-layer shape. `__control/topology-flat` switches back to the flat body, and A27 uses it to prove both shapes render **point for point identically**.

### 6.11 Link Facts, Region Group Collapsing and Wi-Fi Facts (A28 – A30, landed 2026-11-07)

While fixing §6.10 the same 36-node / 48-link production sample was probed field by field, and the findings were shipped as three read-only facts (link card / group collapsing / wireless card). The table below is the **raw evidence** (2026-11-07); the shipped contract follows it.

| Probed surface | Measured (36 nodes / 48 links) | Verdict |
| :--- | :--- | :--- |
| link `data` basics | `linkType` (`radio` / `100FE` / `1GE` / `fiber`), `bandwidth` (`"100 Mbps"` / `"1 Gbps"` / `"4 Gbps"`), `status`, `medium` (`wifi24` / `eth100m` / `copper1g` / `optical`), `relation` (`up` / `peer` / `down`), `admin_status` — **present on 48/48** | enough for an honest link tooltip without any new fetch |
| link `data.telemetry` | `{ traffic_in, traffic_out, in_util_pct, out_util_pct, packet_loss, error_rate, metric_updated_at }` on 48/48; `in_util_pct` / `out_util_pct` / `packet_loss` / `error_rate` measured **all zero** while `traffic_in` / `traffic_out` are non-zero on 21/48 (e.g. `traffic_out: 16.18` next to `out_util_pct: 0`) | **the utilisation dimension is unusable today**: those zeros mean "not computed", not "idle", so printing `0%` would be a lie — the only honest label is "not computed" |
| node `data` facts | 13 basics on 36/36; Wi-Fi facts (`band` / `channel` / `dbm` / `clients` / `util` / `ssid` / `tx_power`) on 27/36, `bssid` and `temperature` on 9/36; `neighbors` is a **count** (e.g. `5`), not a list | the wireless facts shipped as the AP fact card (A30); a neighbour list can only be derived from `edges` (which is what A21 already does) |
| node `style.x / y` | `y` lands exactly on `180 / 360 / 540 / 720` by `tier` (**one row per band**), `x` spans `120 ~ 4520` | this is the raw "one row per band, spread out" sketch; reusing it needs scaling plus cropping and still paints a flat single row — **it buys no 2.5D** |
| `combos` | 3 groups of 11 `children` each, carrying `data.label` / `layer` / `root` / `counts: { distro, access, terminal }`; 30/36 nodes carry `combo` | region grouping with per-group counts shipped (A29) and answers "how many boxes are in that area", which 2.5D does not |

- **Link fact card (A28)**: every connector on the canvas is clickable (`emit('selectLink', topologyLinkKey(link, index))`, clicking it again clears it) and the detail pane shows a "link detail" card: both endpoint names (the name the graph can show wins, falling back to the management IP), `linkType` / `medium` / `relation` / `admin_status`, the bandwidth **verbatim** (`"1 Gbps"`, never converted), `traffic_in` / `traffic_out` in Mbps, and the four utilisation dimensions — three different semantics, all read through `app/utils/graph/topologyLinkFacts.ts`: ① basic facts are strings as given, missing → `null` → "—"; ② `traffic_in|out` are real counters (a `0` is printed), missing → "—"; ③ `in_util_pct` / `out_util_pct` / `packet_loss` / `error_rate` **only carry a value when `> 0`**, so a `0` becomes `null` → "not computed", with one line under the card explaining why. The canvas `<title>` hover text uses the very same read model (basic facts + both traffic directions + utilisation or "not computed"), so **hover and card can never disagree**.
- **Region group collapsing (A29)**: `combos` were lifted into the read model (`flattenTopologyCombo()`: `data.label` / `data.children` / `data.counts` → `label` / `children` / `counts`). The group list lives in a **popover at the canvas' top-left corner** (`topology-groups-toggle` → `topology-groups`): group name, the upstream-reported layer counts (`distro` / `access` / `terminal`, translated when the vocabulary has the word, verbatim otherwise), "visible / declared" member counts, a collapse switch, "expand all" and "focus this group". It decides "what this picture includes", which is a reading of the canvas, so it no longer occupies the sidebar (the sidebar only answers "what is this selected thing", §6.15 requirement 7). Collapsing **changes only the view input** (`collapsedCombos`): the layout is laid out again over the remaining members, the edges hanging off the hidden ones disappear with them (an edge with an endpoint outside the canvas cannot be drawn) and the canvas badge reads "N nodes hidden (M groups)"; the per-group counts **do not change by a single character** — they are an upstream-reported fact, not a canvas tally. Collapse / expand clears the offset layer for the same reason switching layouts does (the membership changed, so in-band positions changed).
- **Wireless fact card (A30)**: a node carrying Wi-Fi fields gets a "wireless" card (`band` / `channel` / `dbm` / `clients` / `util` / `ssid` / `tx_power`, read through `wifiFactsOf()`). All seven empty ⇒ `null` ⇒ **the block is not drawn at all**: a row of "—" would claim "this AP's SSID is unavailable" about a device that is not an AP. Unlike link utilisation, a node `util` of `0` is a trustworthy real value (the node contract carries no "not computed" semantics).
- **2.5D still does not come from upstream coordinates**: `style` is proven to be a "one row per band" sketch, whereas 2.5D needs multiple rows per band plus a z offset, which only `layoutTopology()` can produce; reusing `style` yields a "wider fake 3D row" and contradicts the geometry contract of §6.8. The canvas' existing "2.5D look" comes from the isometric styling (§7), not from upstream coordinates.

### 6.12 Alarm Overlay, Focus on One Group and Link Actions (A31 – A35, landed 2026-11-07)

The three capabilities fetch and degrade independently: alarms come from 8888 `/alarm/alarm-events` (§6.1), focusing a group only changes the **view input**, and link actions go through the whitelisted 8001 write channel (§6.2). Inside `useTopologyMonitor()` they are **three concurrent channels that never block each other** (`Promise.all([loadGraph(), loadSimulator(), loadAlarms()])`): an alarm failure never takes the topology down, and a simulator failure never takes the alarms down.

| Capability | Fetch / criterion | Landing point |
| :--- | :--- | :--- |
| Alarm overlay (A31) | `GET /api/alarm/alarm-events` (through the BFF `[...slug]` gateway, **no local route on the server**) → unwrap `{ list, page, page_size, total }`, keep only events with `status=firing` and a non-empty `target_id` | read model `app/utils/graph/topologyAlarms.ts` (pure functions); the canvas badges and the detail pane's "active alarms" card share the single `alarmIndex` table |
| Focus on one group (A33) | `focusComboId` → the layout filters nodes first (`node.combo === focus`), and the edges hanging off them disappear with them | `focusCombo()` / `clearComboFocus()` in `useTopologyMonitor()`; header badge `topology-focus-badge` plus `topology-focus-clear` |
| Link actions (A34 / A35) | `POST /api/sim/api/network/links/{sim_link_id}/{down,up,toggle}` | `performLinkAction()`; button group plus a `UModal` second confirmation (sharing `pendingScope: "node" \| "link"` with node actions) |

- **Three hard rules of the alarm read model** (header of `topologyAlarms.ts`): ① **only targets that join** — an event with an empty `target_id`, or with an id that is not on the current canvas, takes no part in the aggregation (`alarmIndexOf()`'s `keep` parameter is exactly the set of node ids really on the canvas); ② **an unknown severity never escalates** — anything outside the registered three (`critical` / `warning` / `info`) becomes `info`, never `critical` just because it could not be read; ③ **a badge reports the count and the highest severity only**, while the detail pane lists the top 3 from the same ordering (severity descending → last triggered descending) and writes "N more" for the rest — the two never compute twice.
- **`status=firing` is filtered upstream**: the request carries `status=firing` and the client re-checks with ③ — but **a missing `status` counts as firing** (the upstream not saying ≠ resolved). An event that explicitly arrives as `status=resolved` is dropped, exactly so "read it, but it already recovered" never becomes a badge.
- **"read failed" ≠ "no alarms"** (the same rule as §8): when the alarm channel fails the canvas badges disappear entirely, the header alarm reading prints "—", and the detail pane prints "alarm channel unavailable: <upstream message verbatim>"; it **never** prints "this node has no active alarms" — that is a conclusion, not a default. Topology and simulation keep rendering as usual.
- **Join loss is by design, not a missing drawing**: of the 77 firing events measured in production, 43 hang off devices that are not on the canvas and 9 carry an empty `target_id` — which is why the header reads "N alarms on canvas / M devices" instead of "N alarms network-wide". Those off-canvas events stay upstream; the page neither drops them silently nor pretends they belong to some on-canvas device. Without those two ratios, "only two devices have alarms on the canvas" looks like the page lost 43 entries instead of like the shape of the data.
- **Focus and collapse are mutually exclusive**: when the focused group happens to be in the collapsed set, `focusCombo()` removes it from `collapsedCombos` first (otherwise the canvas would be empty); both change the membership, so both clear the offset layer (same reason as switching layouts, §6.9). Once the upstream drops that group, `focusedCombo` expires back to "all groups" instead of leaving an empty canvas. The header badge uses the **upstream-reported group name** (`data.label`, falling back to the id), never an invented one.
- **A link action must use the simulator-side link id**: `performLinkAction()`'s `simId` comes from `simulatorLinkFor(link).simId`, **not** the `source→target` shown on the canvas — the latter is built from node ids (management IPs) and the simulator does not know it, so it would only 404. `down` / `up` / `toggle` each get a button, and the disabled reason follows the order "channel state → write switch → selection → present in the simulation", naming **only the missing layer**; with `writeEnabled=false` the page sends no write request at all (the BFF's 405 is the second gate). The confirmation text names both endpoints, the **simulator link id** and the action verbatim, plus one sentence that the step is irreversible, that the BFF keeps no copy and that it will not roll back automatically.

### 6.13 What the neighbour-discovery upstream actually returns (prerequisite of §6.14, measured 2026-11-07)

Neighbour discovery (LLDP) is the last P1 read-only face of the topology domain. The first step before writing code was not to draw a card but to **sample production once**: the probe hit `GET /api/lldp/summary` and `GET /api/lldp/neighbors/{node_id}` on 8001 (artefacts `/tmp/lldp-summary.json`, `/tmp/lldp-probe.out`, not committed). The shapes did **not** match `shared/types/simulator.ts`, so the contract was corrected first and the page section moved to the next patch (landed in 0.17.0, see §6.14).

| Item | Old contract (wrong) | Measured (now mirrored in the type) |
| :--- | :--- | :--- |
| `summary` shape | `{ neighbor_count, switches[] }` | `{ node_count: 36, neighbor_entry_count: 96, mode: "native", mib_standard: "IEEE 802.1AB", lldp_mib_oid: "1.0.8802.1.1.2.1.4.1.1", local_sys_name, local_sys_desc, local_chassis_id }` |
| `summary` meaning | "neighbour counts grouped per switch" | **scan size plus one sample endpoint**: the three `local_*` fields describe only the first scanned node (measured `n1`), so reading them as a network-wide summary would be inventing data |
| Neighbour fields | `{ id, name, local_port, remote_port, ttl, mib_oids }` | `{ neighbor_id, neighbor_type, neighbor_name, local_interface, remote_interface, chassis_id, chassis_id_subtype, port_id, port_id_subtype, port_descr, sys_name, sys_desc, ttl, link_type, link_status, discovered_at, mib_oids }` |
| Peer identity | a single `id` + `name` | **two sets coexist**: `neighbor_id` / `neighbor_name` come from the platform ledger (`n1` / `N1`) and `sys_name` from the MIB (`核心路由器-1`) — render both verbatim, never one standing in for the other |
| `chassis_id` | treated as the unique key | measured as a constant `00:00:00:00:00:00` (the simulator leaves it empty), so it **cannot** be a key; `mib_oids` is a field→OID map, not values |

- **An empty array is a real answer**: a node without collection enabled answers `{ node_id, neighbors: [] }` (not a 404). In the page section (§6.14), "this device has no neighbours" may only be said after the upstream explicitly returned an empty array; a failed request may only print the failure reason (same rule as §8).
- **Node alignment**: the `node_id` of `neighbors/{node_id}` shares its source with `runtime-inventory` `nodes[].id` (`n1`, `n4`, …), while canvas node ids are management IPs — go through the §6.2 simulator-node alignment (`buildSimulatorIndex()`) once; never pass a canvas node id straight to this endpoint.
- **The fake upstream is in sync**: both LLDP endpoints in `scripts/lib/bff-harness.mjs` answer the shapes above (`n1` two neighbours — `n2` on canvas and `n10` off canvas —, `n4` two, everything else an empty array), so the §6.14 assertions stand on the measured shape instead of on a sample "cleaner" than production (the same lesson as the §6.10 shape gap).

### 6.14 The Neighbour Section (A38 – A40, landed 2026-11-07)

The detail pane gains an "LLDP neighbours" card. It is the **upstream's per-node neighbour ledger**, which is not the same thing as the older "neighbours" list in the same pane (`topologyNeighborsOf()`, which only lists edges **on this canvas**): the former is what the device reports, and a peer may not be on this canvas at all. Because the two names are so close, they stay in separate cards with their own one-line scope, and neither stands in for the other.

| Item | Fetch / criterion | Landing point |
| :--- | :--- | :--- |
| Fetch | `GET /api/sim/api/lldp/neighbors/{sim_node_id}` (through the `SIMULATOR_ROUTES` whitelist), where `sim_node_id` is `selected.marker.simId` — the simulator-side id (`n1`) a canvas node was aligned to in §6.2, **never** the management IP | `useTopologyMonitor()`'s `loadNeighbors()`: `watch` keyed on `selected.marker.simId` alone, with a request sequence number so a stale response is dropped |
| Read model | keeps upstream order; `local_interface` / `remote_interface` stay two fields instead of one spliced string; `neighbor_name` (ledger) and `sys_name` (MIB) render side by side | pure functions `app/utils/graph/topologyNeighbors.ts` (`neighborRowsOf()` / `canvasIdIndex()` / `neighborCanvasCount()`) |
| Peer on canvas? | `neighbor_id` → `runtime-inventory` `nodes[].id` → `ip_address`, a hit against the canvas node id set means "on canvas" | the row reads "peer on canvas: <management IP>" or "peer not on this canvas (off-canvas device)", and the card carries both "N entries · M on canvas" |
| `chassis_id` | **never used for any decision** (measured as a constant `00:00:00:00:00:00`) | only `discovered_at` (a local timestamp without a timezone, as given) and the `ttl` in seconds are shown |

- **Four states, written apart** (`data-lldp-state`): `idle` (nothing selected / the node is not in the simulator runtime, so there is no ledger to read), `loading`, `ok`, `error`. The `idle` copy says outright that this "is not the same as having no neighbours"; `error` prints only the upstream message ("neighbour channel unavailable: <message>").
- **Only an empty array may say "no neighbours"**: with `ok` and `neighbors: []` the card reads "upstream returned an explicit empty array: this device has no neighbours"; on a failed request that sentence **never appears** (the same rule as §6.12 and §8). - **A failure clears the rows, not the screen**: opposite to alarms (which keep the previous reading), a neighbour failure drops the previous device's rows — a per-node list left in place would be read as "this device has these neighbours too".

- **Why items 2 and 6 are self-drawn rather than "turning on a G6 behaviour"**: the 2.0 canvas is hand-drawn SVG (`NMCPS-ADR-0019` D1) and the project has no G6 runtime dependency — this implements the **same semantics** as G6 v5's `click-select` / `hover-activate` (related-element activation) / `collapse-expand`, instead of pulling G6 in and rewriting layout injection, the drag-offset layer, alarm badges and the no-rAF constraint. The four traits of `collapse-expand` map one to one: the default trigger is a **double click** (a clickable badge and `Enter` offer the same action), the `enable` predicate is "only a node that really has children can collapse", the collapsed element **stays on the canvas** showing `+N`, and expanding restores the geometry (the equivalent of `graph.expandElement()`).
- **The collapse direction comes from `tier`**: children are the neighbours **strictly further down**. A meshed top layer (three mutually linked cores) would have each of them treat the others as children if edge direction were used, and the recursion would never terminate; `tier` is a measured upstream field (§6.10), so the direction is unambiguous.
- **On the same tier, only the side that "still has an uplink" wins** (added in 0.17.14, A52): between same-`tier` neighbours, if one side has a **strictly higher** device next to it (it "still has an uplink") and the other does not, the one with the uplink is the parent; when **both or neither** have an uplink there is **no direction** (two access switches both uplinked to the same distribution switch, two distribution switches both uplinked to the same core, the meshed top layer — the same reasoning: no invented hierarchy). This is the direct fix for the 2026-11-09 user report: the 18 production fat APs are registered as `tier 3`, the same tier as the access switch they uplink to, so with the "strictly further down" rule alone collapsing a distribution switch removed the access switch but left the APs on the canvas — and their edges were dropped with it, leaving 18 nodes connected to nothing. The rule lives in the `hasUplink` set of `childIndex()`, shared by the badge reading (`hiddenCounts`) and the `data-collapsed` subtree filter, so canvas and detail pane change together.
- **After collapsing**: the node itself stays on the canvas and its descendants plus the links that only reach them leave the **render** — but the geometry is still computed over the **pre-collapse** complete set, so the remaining nodes keep their coordinates point for point. The old implementation pulled the subtree out of the layout input and re-spread the whole row, so collapsing one leaf moved the entire picture — it looked like "you switched to another graph" (fixed 2026-11-08; A46's "coordinates equal point for point after expanding" went from "re-spread then restored" to "never moved at all"). The offset layer therefore is **not** cleared: collapsing decides what is drawn, not how things are laid out (unlike switching layouts or collapsing a combo, which change the set and do clear it, §6.9). If the collapsed node was the selected one, the selection is cleared too (the pane must not keep describing a device that is no longer on the canvas).
- **Collapse is not persisted**: unlike combo collapsing (keyed by combo id, §6.11), a subtree collapse is a temporary view of the **current** structure; it becomes invalid by itself when the upstream drops that device or it no longer has children (`watch(graph)` prunes it), and persisting it would carry a stale state into the next session.
- **Grey links do not lose the status**: the semantics still exist (link badges in §6.12, the detail pane, the `<title>`); they simply no longer ride on hue — with 48 links painted in six colours the reader sees a rainbow before the hierarchy.
- **Emphasis never recolours** (second ruling of 2026-11-08, §6.15.1): selected and related states **only change the width**; the stroke stays that one neutral grey / that one tier colour. The old implementation painted emphasised links `stroke-(--ui-primary)`, which collides with the only colour meaning ("grey = a connection"), and when two `stroke-*` classes are both present the winner is decided by Tailwind's generation order rather than the order they are written (grey ate the primary colour once). The emphasis tier now comes from a single function, `linkStrokeWidthOf(link, emphasis)` (`none` / `incident` / `selected`), and the template carries no second `stroke-*`.
- **The deep-link identity is kept separate, never stitched together**: a topology node id is a management IP, `/metric/device`'s `?id` is a `device_code` and `/metric/link`'s `?id` is a `link_id` (`device_code:iface--device_code:iface`). The deep link therefore carries `?mgmt_ip=` (device page) and `?source_ip=&target_ip=` (link page), and each target page resolves those against **the ledger it already fetched** before writing its own `?id` (the single source of truth in `useRecordSelection` is untouched): the device page matches its `mgmt_ip` column, the link page uses the existing `device_code → mgmt_ip` index (§6.6) to look up both ends, orientation-insensitive.
- **A deep link may page, `?id` still may not**: the ledger shows 15 rows per page while production has 36 devices / 48 links, so the target sits past page 1 more often than not — resolving on the first page alone means "clicked Telemetry, nothing got selected". `resolveDeepLink()` therefore looks at the current page first and then scans page by page (cap `DEEP_LINK_MAX_PAGES = 20`, stops on a failed request); on a hit it **moves the list to that page** before writing `?id`, on a miss the default selection stays. The rule `NMCPS-ARCH-006` §5.2 forbids is unchanged: `?id` is not part of any request key and never triggers a scan — only a deep-link parameter does.
- **The legend lists only the roles that actually appear** (`presentRoles()`): no elected root means no "boundary" entry; the legend exposes `data-role` / `data-status` so `check:ui` can assert colours and roles. The swatch is drawn with **`border-*` on an HTML `<span>`** (`roleDotClass()`), not with SVG's `stroke-*`: HTML elements ignore `stroke`, so `stroke-*` plus `border-2` leaves the width only and lets the colour fall back to `currentColor` — all four tier swatches then render the same colour (the legend and the canvas disagree). Both class sets live side by side in one table in `topologyRoleStyle.ts` (never concatenated at runtime — Tailwind has to see the literals).

#### 6.15.3 Neighbour link halos take the selected device's tier colour (A47 tightened, landed 2026-11-09)

Once §6.15.2 had moved emphasis into the halos, those halos inherited the link body's grey — selecting a distribution switch only made four related links "a slightly wider grey", so colour answered nothing. The 2026-11-09 ruling: **the halo on a link that reaches the selected device takes that device's own tier colour** (select a distribution switch → amber, select an access switch → blue) while the body stays the one neutral grey (§6.15 requirement 1 untouched):

| # | Requirement | How it is done | Where |
| :---: | :--- | :--- | :--- |
| 1 | "When a node is selected, the links attached to it should light up too, in that node's colour" | `linkHaloTintOf(link, index)` returns the **selected node's role** for the `incident` step only (a link reaching the selected device) and an empty value for `selected` (the clicked link) / `focus` (keyboard focus), so those keep the grey. `linkHaloClass()` picks between `roleStrokeClass(role)` and `linkStrokeClass(status)` accordingly, and `data-link-halo-tint` exposes which role was applied | `TopologyCanvas.vue` (`selectedRole` / `linkHaloTintOf()` / `linkHaloClass()`) |

- **Why only the `incident` step is tinted**: `selected` / `focus` say "this link is the one that was clicked / has keyboard focus", and their step (wider, more opaque) already carries that. Adding colour would squeeze "the clicked link" and "who it reaches" into one stroke.

- **Assertion**: A47, in the tier tree, clicks `10.0.1.4` (a distribution switch); all four `incident` halos must carry a `data-link-halo-tint` equal to that node's `data-node-role` (`distro`), their `stroke` must equal the node body's tier colour and **not** `--topology-link`, while the body stays grey at `1.5px` with an unchanged `stroke-width`.

- **Why no truncation** (the requester's words: "no ellipsis"): a canvas name such as 「汇聚交换机…」 gets carried over to the asset ledger, and a half name identifies the wrong device, which costs more than slight crowding. Staggering already doubles the usable width (`2 × 74 − 6 = 142 px`), and at 10 px 「无线终端设备-01」 takes about 77 px, so production scale never truncates anyway; when it truly does not fit, slight crowding beats losing characters.
- **Why the smaller font comes first**: `TIER_TREE_MIN_NODE_GAP = 74` is the geometric floor for "circles that do not overlap"; at 11 px seven CJK characters take about 77 px, already beyond the 66–68 px single-line width, so a full row could only be handled by truncation. At 10 px both the single line (≈ 68 px) and the staggered line (142 px) have slack, which is what makes "never truncate" more than a slogan.
- **Why "Refresh" goes last**: everything before it answers "how is this graph drawn"; it alone refetches. Sitting at the end it abuts the right-zone readings, so a reader who just took a number can press it. The left zone order is therefore fixed to **layout dropdown → rotation → zoom → show names → reset view → refresh** (A48 asserts the testid order of the last three).
- **Assertion**: A48 additionally pins "neither retired reset testid exists", "the trailing order and the Refresh text", "both rotation icons have non-empty and different icon content", "the layout icon changes with the mode" and "both containers above the canvas are fully transparent"; A44 now pins "no ellipsis anywhere + exact full names + 10 px font" instead of `data-label-truncated`.

#### 6.15.5 Tighter selection, five tier colours and "centre the terminal row" (A24 / A43 / A47 rewritten, landed 2026-11-09)

Four remarks from the same review round, split across **styling** and **geometry** (the palette and the centring rule live in §7 "Tier palette" and §6.8 "The centring anchor"; this subsection records cause and assertions):

| # | Requirement | How it is done | Where |
| :---: | :--- | :--- | :--- |
| 1 | "The root node should be tier 0" | the elected root **is** band 0 in the read model: `ROOT_TIER = 0`, so the detail pane prints `0`, the canvas exposes `data-node-tier="0"`, and the "boundary" colour now maps to a real tier (`normalizeTier()` clamps upstream to 1..4, so `0` can only come from the election). The `tier <= 0` branch of `roleOfTier()` still reads `root`, keeping five tiers and five roles one-to-one | `topologyRoleStyle.ts` (`ROOT_TIER` / `roleOfTier()` / `tierOfNode()`) + `topologyLayout.ts` (`tierOfNode()` written back into the read model) |
| 2 | "Centre the terminal tier first, then align the levels" | after the parent-over-children convergence the tier tree **translates the whole picture** so the last row's mean `x` lands on **half the current `viewBox` width** (±1 px); the former `padding`-based overflow clamp is gone (it pushed the last row off centre) | `topologyTierTreeLayout.ts` (the sixth pass plus `bbox`) |
| 3 | "Tighter ring and a thicker body for the selection" | node `selected`: halo `r + 2` / 4 px / 50% (0.17.16 was `r + 5` / 3 px / 45%) and the body stroke goes 2 px → **3 px**; the one-hop `neighbor` step is unchanged (`r + 3` / 2 px / 22%, body 2 px) | `TopologyCanvas.vue` (`NODE_HALO` / `nodeStrokeWidth()`) |
| 4 | "Links attached to the selected node should light up in that node's colour" | the `incident` halo opacity goes 16% → **30%** and `selected` 30% → **45%** (narrowed again to **35%** in 0.17.18, see §6.15.6): at 16% a tier colour over the canvas is almost swallowed by the background, i.e. tinted but invisible. - **Why the ring is tighter rather than wider**: the selected step sits outside a body already thickened to 3 px; expanding the halo (`r + 5`) leaves a visible gap and reads as two unrelated circles, while hugging the edge (`r + 2`) with 4 px at 50% reads as "this one is circled". The neighbour step stays at 22%: it only answers "which links reach it" and must not compete with the selection.
- **Why thickness goes back to the node body**: on links, width is the bandwidth reading, so thickening rewrites data; a node has no second width semantic (always 2, thickening only for selection), so `2 → 3` collides with nothing and makes the selected node easier to hit and to recognise without inflating its radius.
- **Leaf normalisation yields to the root**: a childless device that gets elected as the root of a single-device graph is an apex, not an endpoint — `tierOfNode()` checks `isRoot` before `isLeaf`, otherwise one device would be required to sit in row 0 *and* read as the terminal tier.
- **Assertion**: A24 now pins "the last row's mean `x` equals the canvas centre (half the current `viewBox` width — 537 on this sample, not a hard-coded 500) ±1 px"; A43 adds `data-node-tier` values `0` / `1` and "the 14-node last row is centred on the canvas"; A47 pins "selected body 3 px + halo `r+2` / 4 px / 0.5 in the node's tier colour" and "4 `incident` halos at 0.3", with A49's selected halo at 0.35 / 7.5 px and A51's focus halo at 0.3 following the same table (the selected link's halo narrows again in §6.15.6).

Four remarks from the same monitor-page review, split across **how the current item is expressed** and **how labels are placed**:

| # | Requirement | How it is done | Where |
| :---: | :--- | :--- | :--- |

## 7. Graphic Shapes

All graphics are drawn in-house (`NMCPS-ADR-0019` D1 / D2). This domain may use only the components below; pages must not create their own canvas or start their own `requestAnimationFrame`.

| Component | Where | Carrier | Requirements |
| :--- | :--- | :--- | :--- |
| `TopologyCanvas` | the `monitor` main view | SVG (≤ 400 nodes) plus an isometric projection for a 2.5D feel | layout injected as a pure function; caps of 400 nodes / 1,200 links with weight-based trimming reported as "N trimmed"; drag / zoom / rubber-band hit testing comes from `app/composables/useGraphInteraction.ts`; a manual node drag is booked as an **offset delta** in `app/utils/graph/topologyNodeOffsets.ts` and composed right before rendering (§6.9); links are always neutral grey and selecting a node also highlights its related links and one-hop neighbours (§6.15, `topologyHighlight.ts`); a node with children can collapse / expand its subtree (§6.15, `topologyCollapse.ts`); the canvas **paints no background of its own** (transparent inside the frame, keeping only its border and radius, since 0.17.16); the control row (rotation / zoom / show names / reset view / refresh) lives in the page toolbar's left zone and the legend in the canvas' bottom-right (§6.8 / §6.15.4) |
| `TrendChart` | the `device-metrics` / `link-metrics` main chart (`monitor` no longer draws one — its detail pane only offers the deep-link button, §6.5) | SVG polyline plus area fill | threshold bands, range selection, cursor readout; above 2,000 points aggregate per pixel column keeping the extremes |
| `SparkStat` | page headers and detail-pane mini cards | SVG | single value + mini trend + status colour, replacing the scattered unovis mini charts of 1.0 |

- **Status colours** come from the semantic palette in `app.config.ts`; hard-coded hex is forbidden.
- **How the root looks** (A43 / A45, revised 2026-11-09): the elected root takes the **boundary red** (`--topology-tier-boundary`, `#f33`) plus the largest radius (19). Before 0.17.16 it borrowed the neutral dark stroke (`--ui-text`) because only four tier colours existed and a fifth hue risked being confused with access blue; with the five-colour palette the root owns its own red, so `one tier = one colour` holds for the root too and the legend can list it as a colour. The root is unique and sits at the apex (the centre of the radial fan, the first row of the tier tree), so a bigger circle plus its own colour is distinction enough. The legend lists **only the roles that actually appear** on this graph (`presentRoles()`: no election means no "boundary" entry, and since 0.17.8 the `roles.root` copy reads "Boundary" (中文「边界层」) while the role id stays `root`), so it never advertises a tier the canvas does not contain; the role comes from the rank resolution **shared by both layouts** plus `roleOfNode(tier, isLeaf)` (leaves always normalise to the terminal tier, §6.15.2 item 3), so switching layouts never repaints anything (A45).
- **Label avoidance staggers, never truncates** (A44, `app/utils/graph/topologyLabelLayout.ts`, pure functions, a 2026-11-09 requester ruling): dagre only keeps **circle centres** apart (`nodesep 80`, narrowed to `TIER_TREE_MIN_NODE_GAP = 74` on narrow canvases), while names are far wider than the circles, so naive placement stacks text. There is exactly one rule: fits (`width ≤ gap − LABEL_GUTTER`) ⇒ a single line as-is; too wide ⇒ **every other label lifts one line** (odd/even baselines buy twice the usable width). Since 0.17.16 **truncation is gone entirely** (`fitText()`, `LabelPlan.text`, `data-label-truncated` and the explanatory `<title>` all retired): a half name like 「汇聚交换机…」 gets carried over to the asset ledger and identifies the wrong device, which costs more than slight crowding. Character widths are estimated (CJK = 1.0 × font size, Latin = 0.56 × font size, space = 0.28, with `LABEL_GUTTER = 6 px` slack), so the planner finishes at layout time and never needs a post-render `getBBox()`. **Direction comes from the layout** (§6.15.6): away from the fan apex for the radial fan and straight down `(0, 1)` for the tier tree, spaced `radius + LABEL_GAP(12) + stagger step` and centre-anchored (`text-anchor` and `dominant-baseline` are both `middle`), so every label keeps the same distance from its own circle and no longer lands on the next node.
- **The 10 px font size is the precondition for "no truncation and no crowding"** (2026-11-09): `LABEL_FONT_SIZE = 10` / `LABEL_LINE_HEIGHT = 11` (the canvas carries the same `text-[10px]`). At 11 px seven CJK characters take about 77 px, more than the single-line width at the minimum gap (74 − 6 = 68 px), so a full row could only fit by truncating; at 10 px the staggered width is `2 × 74 − 6 = 142 px` and a single line is 68 px, while 「无线终端设备-01」 needs about 77 px and still fits when staggered ⇒ at production scale nothing is truncated and nothing overlaps. Going smaller hurts legibility and widening the gap pushes the tower out of the viewport, so 10 px is where those two constraints meet.
- **The "show names" toggle** (A44): a `UButton` in the toolbar's left-zone control row with `data-testid="topology-labels-toggle"` (`aria-pressed` reflects the state; it moved there with the other controls in 0.17.15, and sat in the canvas' top-right in 0.17.8); switching it off leaves only the nodes and their status dots. It only affects **rendering**: layout, geometry and the drag-offset table stay untouched, and switching it off and on again must restore the exact same picture (for reading the tiers on a narrow screen, or for screenshots).

- **Node visual language (replicating 1.0, 2026-11-08; palette revised 2026-11-09)**: the ring is **always the tier colour**, the fill is always a very pale neutral, and the radius shrinks with the tier (root 19 / core 17 / distribution 16 / access 14 / terminal 12 logical units); **status lives only in the centre dot** (radius = node radius × 0.38), so a status change never repaints the ring. The five tier colours are a fixed palette the requester specified, with a **single source** in `app/assets/css/main.css` (`--topology-tier-*`: `boundary #f33` / `core #f3c` / `distro #c63` / `access #369` / `terminal #0c6`); `topologyRoleStyle.ts` only references the variable names, so no component carries a hex (see the "Tier palette" table at the end of this section). The tier comes from the node's **band order**, not from the upstream `type` (the same rule as 1.0's ADR-012: colouring by `type` gives an access switch and a core router the same colour); the single source for role → stroke/radius is `topologyRoleStyle.ts`, and the canvas only exposes the result as `data-node-role` / `data-node-tier` / `data-node-status`. **Why stop borrowing Nuxt UI's four semantic colours** (`error` / `warning` / `info` / `success`): there are five tiers but only four semantic slots, so two tiers inevitably share a colour (the root used to borrow the neutral `--ui-text`, which the legend cannot name), and semantic colours carry a "severity" meaning of their own — a red core reads as "this device is broken". 1.0 used "diameter × 0.2" for the dot; 2.0 uses 0.38 because the tower's `viewBox` scales down to 0.3–0.5 (at 0.2 the dot is 1 px on screen, i.e. status becomes invisible) — the semantics are unchanged, only 1.0's readable ratio at a 1:1 canvas is carried over. The legend only answers "which tier is each ring colour" (it lists only the roles that actually appear and sits in the canvas' **bottom-right corner**; the status group was removed in 0.17.13 because the dot already reads it out).
- **Header readings live in the toolbar's right zone** (ruled 2026-11-08; narrowed to four in 2026-11-09): the nodes / links / combos / alarms badges inject into `#app-toolbar-right` (`topology-stats`) instead of a row of `SparkStat` cards eating the first 100 px of the content area just to show a few numbers (the "simulated" badge is gone: no simulator configured is a deployment shape, not a reading, §6.15.4). The reading rules are unchanged: missing data prints "—", never 0 (0 alarms while the alarm channel is down is a misreading). The `SparkStat` component stays (the `dashboard/overview` stat cards keep that shape and `dashboard.md` B2 references the same test id).
- **Where the 2.5D feel comes from**: the isometric projection is canvas **styling** (elliptical base, slanted connectors, shadow), while geometry still comes only from `layoutTopology()`; upstream `style.x|y` is never read (§6.11 proves it is a "one row per band" sketch spanning `x` 120 ~ 4520, which would need scaling and cropping and would still paint one flat row).

**Tier palette** (specified by the requester on 2026-11-09; single source in `app/assets/css/main.css` under `--topology-tier-*`, same values in light and dark mode):

| `tier` | Role | Copy | CSS variable | Colour |
| :---: | :--- | :--- | :--- | :---: |
| 0 | `root` | Boundary | `--topology-tier-boundary` | `#f33` |
| 1 | `core` | Core | `--topology-tier-core` | `#f3c` |
| 2 | `distro` | Distribution | `--topology-tier-distro` | `#c63` |

- **Sizing** is always `ResizeObserver` + `useDevicePixelRatio`; reading `window.innerWidth` to decide layout is forbidden (container-query convergence, `NMCPS-ARCH-006`).

- **Accessibility**: the graph and its legend carry `role="img"` + `aria-label`, and an equivalent keyboard-navigable list view is provided.
